DEV-357 에서 분리(그쪽은 캐시 헤더만 처리하고 닫음).

## 문제

퀘스트 상세 → 목록으로 돌아갈 때마다 `/api/quests?slim=true` 를 다시 받는다.
실측(실제 길드, 퀘스트 500여 개):

| 요청 | 전송 | 해제 |
|---|---|---|
| `/api/quests?slim=true` | 36 KB (gzip) | **275 KB** |
| quest-dependencies / statuses / types | 5 KB | 5 KB |

왕복 1회당 약 280KB 를 다시 받고 **500여 개 객체로 다시 파싱**한다. 상세 문서
자체는 13KB 뿐이므로, 목록을 오가는 사용 패턴에서는 이 재적재가 비용의 대부분
이다(GUI 메모리 측정에서 "문서당 2MB" 로 보였던 것의 정체 — BUG-228 참조).

BUG-210 이 고친 것은 cross-link **인덱스**의 강제 재적재였고, 목록 페이지가
자기 데이터를 다시 받는 것은 그대로 남아 있다.

## 방향

목록 응답을 클라이언트에 캐시하고 변경 시점에만 무효화한다.

무효화 트리거(놓치면 "고쳤는데 목록에 안 보인다" 가 된다):
- 퀘스트 생성/삭제/상태·긴급도·제목 변경, 관계 변경
- reindex (`reindexBump` — BUG-210 의 `loadQuestIndex` memo 가 이미 이걸 구독한다)
- 원격 모드에서 **다른 클라이언트가 바꾼 경우** — 이건 클라이언트가 알 수 없다.
  폴링/ETag 재검증 중 하나가 필요하다.

## 설계 메모

서버에 이미 ETag 기반 조건부 요청 인프라가 생겼다(DEV-357 의 첨부 처리).
목록 API 에도 ETag 를 주고 클라이언트가 `If-None-Match` 로 물으면, **304 + 빈
본문**으로 끝나 275KB 파싱이 사라지면서도 신선도는 서버가 보장한다. 클라이언트
캐시 무효화를 직접 관리하는 것보다 이쪽이 안전하다 — 위 "다른 클라이언트"
문제도 자동으로 해결된다.

다만 ETag 계산이 목록 쿼리 전체를 돌리는 비용이면 의미가 없으므로, 길드의
마지막 변경 시각(또는 journal 시퀀스) 같은 싼 값으로 만들 수 있는지 먼저 확인할 것.
