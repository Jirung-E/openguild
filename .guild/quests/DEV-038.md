## 구현 (2026-05-21)

- `gui/frontend/src/lib/components/QuestHistory.svelte` 신설:
  - props: `questId: number`, `statuses?: QuestStatus[]`.
  - `$effect` 로 `questId` 바뀔 때마다 `questsApi.listHistory(id)` 호출.

## 후속 (2026-05-22, GUI vs CLI 일관성)

테스트 중 user 가 "GUI 와 CLI 의 변경이력이 다르다" 보고. 실제 데이터는
동일하지만 표시 형식 (op 라벨 / 시각 표현) 이 달라 다른 사건처럼 보임:

| 비교 | 변경 전 CLI | GUI | 변경 후 CLI |
|---|---|---|---|
| 시간 | `2026-05-22T22:26:51+09:00` | `방금` | `2026-05-22T22:26:51+09:00  3분 전` |
| op 라벨 | `change_status` (raw) | `상태` | `상태` |
| 상태 | colored name_en | colored pill | (그대로) |

수정:
- `core::time::format_relative(ts)` 신설 — frontend `formatRelative` 와
  동일 규칙 (`방금` / `X분 전` / ... / 7일 초과 또는 미래 시각 → `None`).
- CLI `quest history` 출력에 relative 시각 컬럼 추가 (절대 ts 도 유지 — script
  친화).
- op 라벨 번역 (`change_status` → `상태`), 알 수 없는 op 는 raw 그대로.

자동 테스트 +4 (core::time): format_relative 의 recent / old / future /
legacy 형식 입력.

## 추가 보고 (2026-05-22, returned 2회차)

User: "변경 상태가 저거보다 많은데 축약으로 보여주는거임? ... 중간에 써있는
'상태' 는 뭐임?"

조사 결과:
- DB total 53 행 (이 시점). `quest history DEV-042` → 8 행 모두 출력 (CLI
  자체는 절단 안 함).
- "상태" 라벨은 `change_status` 의 op 번역이었음. 현재 유일한 op 라 매 줄마다
  동일하게 표시되어 noise. 사용자가 "이게 뭐지" 라고 의문 가짐.
- BUG-011 history 0 행 — 일부 변경이 no-op skip (BUG-011 자체 fix) 으로
  안 기록된 것. 절단은 아니지만 사용자 인지가 떨어짐.

수정:
- **`change_status` 의 op 라벨 제거** — old → new pill (또는 색칠된 status
  name 변환) 이 이미 "상태 변경" 의미를 시각적으로 전달. 미래의 다른 op
  (update_title 등) 가 추가될 땐 `[op]` 형태로 표시.
- **CLI 끝에 `-- N entries` 푸터** — 절단 의심 방지 (사용자가 "총 몇 개인지"
  확인할 수 있게).
- GUI `QuestHistory.svelte` 동일 — change_status 면 op pill 자리를 빈
  placeholder 로 (grid 컬럼 자리 유지).
