6건 전부 처리했다.

## 1. journal count 무제한

`JournalQuery::clamped_count()` — 1..=1000 클램프. SQLite 가 음수 LIMIT 을
"제한 없음" 으로 해석하는 것이 요점이라, 상한만이 아니라 **하한**도 필요하다.

테스트 2건. `-1` / `0` / `i64::MIN` → 1, `999999` / `i64::MAX` → 1000, 정상값은
그대로. 기본값 50 불변도 함께 고정했다.

실 길드 journal 이 17건뿐이라 HTTP 로는 차이가 관측되지 않았다 — 그래서
단위 테스트로 고정했다.

## 2. 배너 파일 누락 → 404

`e.kind()` 가 `NotFound` 일 때만 `AppError::NotFound`, 나머지는 종전대로
`Internal`. `admin.rs` 의 `get_guild_file` 이 처음부터 하던 방식이다.

**drift 재현 실측**: 캠페인 frontmatter 에 `image = "assets/사라진배너.png"` 를
심고 reindex 한 뒤 요청.

| | 응답 |
|---|------|
| 수정 전 | `500` `{"error":"internal server error"}` |
| 수정 후 | `404` `{"error":"배너 파일 없음: assets/사라진배너.png"}` |

(처음엔 `image_path` 로 심어 재현이 안 됐다 — 그건 DB 컬럼명이고 파일
frontmatter 는 `image` 다.)

## 3. 대용량 첨부 전체 버퍼링 → 스트리밍 + Range

`std::fs::read`(전체 메모리 적재, 동기 I/O)를 `tokio::fs::File` +
`ReaderStream` 으로 바꾸고 Range 를 지원한다.

`parse_range` 를 **순수 함수로 분리**해 테스트 가능하게 했다. 단일 범위만
지원한다 — multipart/byteranges 는 응답 형식이 완전히 달라, 잘못 만드느니
전체를 보내는 편이 낫다.

테스트 6건: 헤더 없음/미지원 형식 → 전체, `N-M`, `N-`, **`-N`(마지막 N
바이트 — 헷갈리기 쉬운 형식)**, 범위 밖 → 416, 공백 허용, 끝이 파일을 넘으면
잘라주기(416 아님).

**실측**:

| 요청 | 응답 |
|------|------|
| 전체 | `200`, `accept-ranges: bytes`, `content-length: 6088` |
| `bytes=0-99` | `206`, `content-range: bytes 0-99/6088`, 100 바이트 |
| `bytes=-50` | `206`, `bytes 6038-6087/6088` |
| `bytes=99999-` | `416`, `content-range: bytes */6088` |
| 두 조각 이어붙이기 | **원본과 바이트 동일** |
| `If-None-Match` | `304` (DEV-357 캐시 회귀 없음) |

## 4. 댓글 생성 201

`add_comment` / `camp_add_comment` 를 201 로. 전환 전에 프런트
(`res.ok`)와 CLI(`status.is_success()`) 둘 다 2xx 를 균일하게 다루는지
확인했다 — 깨질 곳이 없다.

**실측**: 퀘스트 댓글 / 캠페인 댓글 / 캠페인 생성 / 규칙 생성 **전부 201**.

서버 테스트 4곳이 200 을 기대해 깨졌다. 경로가 정확히 `/comments` 로 끝나는
**생성** 요청만 골라 고쳤다 — 처음엔 일괄 치환으로 GET 단언 하나까지 바꿔
다른 테스트를 깼고, 전수 확인 후 되돌렸다.

## 5. `--table --json` 처리 불일치

도움말은 **8개 전부** "--json 과 상호배타" 라고 적혀 있는데 `quest list` 만
수동 검증으로 막고 나머지는 조용히 무시했다.

`conflicts_with = "json"` 으로 선언해 통일하고, `quest list` 의 수동 검사도
`conflicts_with_all` 에 합쳤다.

**기존 주석이 틀렸다.** "`json` 은 전역 인자라 conflicts_with 대상이 못 됨
(debug assert 가 subcommand 스코프에서 못 찾음)" 이라 적혀 있었는데, 실측해
보니 정상 동작한다 — `--table --json` 은 거부되고 단독 사용은 그대로다.
주석을 실측 내용으로 정정했다.

## 6. 상태 slug 하드코딩

`quest start/done/reopen` 이 표시명(`"In Progress"`)을 넘기던 것을 정규
slug(`in_progress`)로. 원 보고가 스스로 정정한 대로 당장 깨지는 건 아니지만,
의도가 "이 정규 상태로 옮긴다" 이므로 그대로 표현하는 편이 낫다.

**실측**: `start` → In Progress, `done` → Done, `reopen` → Open 정상. 표시명
입력(`move DEV-001 "In Progress"`)도 여전히 동작(회귀 없음).
