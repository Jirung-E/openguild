## 조사 결과 — JS 힙 보존은 관측되지 않음 (라우트 이동 70회 기준)

브라우저(Chromium 148 기반 pane)에서 `openguild-server --port 8813` + 실제 길드 데이터(퀘스트 500여 개, `gui/frontend/build` 정적 자산)로 측정했다. 소스는 수정하지 않았고 `git` 도 쓰지 않았다.

### 0. 함정 회피 절차 (BUG-212 재발 방지)

- `document.hidden === true`, `visibilityState === "hidden"` — 오염된 환경 확인.
- 네이티브 rAF 발화 계측: **1.5초 동안 0회** (`rafCount: 0`). 즉 렌더 루프가 멈춘 상태 맞음.
- 그래서 측정 전 shim 설치: `requestAnimationFrame = (fn) => setTimeout(() => fn(performance.now()), 16)`.
- **추가 함정 발견**: 숨겨진 탭이 5분을 넘기면 Chromium 이 타이머를 "intensive throttling"(약 1분에 1회)으로 얼려버려 setTimeout 기반 shim 도 멈추고, **GC 도 돌지 않아** 힙이 245 MB / 424 MB 로 보이는 가짜 수치가 나왔다. 무음 `AudioContext`(gain 0.0001) 를 켜서 페이지를 "오디오 재생 중" 으로 만들자 타이머 cadence 가 100 ms 로 복구되고, 힙도 즉시 14.7 MB 로 회수됐다. 이 트릭 없이 잰 수치는 전부 버렸다.

### 1. 증명된 것 — 라우트 이동은 JS 힙을 보존하지 않는다

정착 바닥값 = 큰 배열(30 × 200k 요소 × 8라운드)을 반복 할당/폐기해 major GC 를 유도한 뒤, 압박을 멈추고 유휴 상태에서 읽은 `performance.memory.usedJSHeapSize` 최저값.

| 시점 | 정착 바닥값 | DOM 노드 |
|---|---|---|
| 로드 직후 (홈, 이동 0회) | **16.62 MB** | 299 |
| 홈/목록/규칙/도서관/퀘스트상세 25회 이동 후 | 19.72 MB (미정착) | 310 |
| 같은 경로 50회 이동 후 | **13.84 MB** | 310 |
| 보드 포함 7개 라우트 56회 이동 후 (유휴 2회 재측정) | **14.97 MB / 14.98 MB** | 314 |
| 위 + 캠페인 상세까지 총 70여 회 이동 후 | 16.86 MB | — |

- **이동 56회 후 바닥값(14.97 MB)이 이동 0회 바닥값(16.62 MB)보다 오히려 낮다.** 즉 이동 횟수에 비례하는 보존은 검출되지 않았다.
- 25회 지점의 19.72 MB 는 GC 가 덜 돈 미정착 값이었다(같은 조건 50회 후 13.84 MB 로 내려감). 정착 판정을 서두르면 그대로 오탐이 된다.
- DOM 노드 수: 299 → 314. 70회 이동 동안 사실상 평평(detached 트리 누적 징후 없음).
- `document.createElement` 를 패치해 WeakRef 로 추적한 결과, 세션 전체에서 **canvas/img 생성 0건**.

### 2. 증명된 것 — 보드는 더 이상 canvas 를 쓰지 않는다

`/?view=board` 를 16회 왕복해도 `document.querySelectorAll('canvas').length === 0`, canvas 생성 카운터 0. 소스상으로도 DEV-317 이후 보드는 실제 DOM 카드다(`lib/utils/quest-node-svg.ts` 주석). 남은 canvas 사용처는 텍스트 폭 측정용 **메모된 1개**(`getMeasureCtx`, 모듈 스코프 캐시)뿐이다. 번들에 있는 `cytoscape` 는 mermaid 의 의존성이며 우리 코드에서 import 하지 않는다(`src` 전체 grep 0건). **BUG-212 의 전제(보드 canvas 누적)는 현재 빌드에는 존재하지 않는다.**

### 3. 증명된 것 — 이동당 네트워크 수신량은 이미 작다 (BUG-210 수정 효과)

resource timing 버퍼를 비우고 14회 이동:

- 요청 76건, transfer 0.34 MB, **decoded 1.88 MB → 이동당 평균 약 137 KB**
- 상위: `/api/quests` 1.61 MB(14회 이동 중 3회 정도만 재적재), `/api/library` 0.08 MB, `/api/rules` 0.07 MB
- 이동마다 1.1 MB 를 받던 BUG-210 이전 양상은 재현되지 않는다.

### 4. 증명되지 않은 것 / 판정 불가

- **+141 MB 의 정체는 판정하지 못했다.** 위 측정이 커버하는 것은 V8 JS 힙뿐이다. WebView2 renderer 의 나머지(Blink DOM/레이아웃 구조, 디코드된 이미지, 폰트/글리프 캐시, GPU 로 넘어간 비트맵, HTTP 메모리 캐시)는 페이지 안에서 볼 수 없다. `performance.measureUserAgentSpecificMemory()` 는 `crossOriginIsolated === false` 라 사용 불가였다.
- 따라서 "우리 코드의 보존"은 **JS 힙 범위 안에서만** 부정됐다. 네이티브 측 보존(예: 렌더링 레이어, 이미지 디코드 캐시)은 여전히 열려 있다.
- A/B(수정 전 커밋 빌드) 비교는 `git` 사용 금지 제약으로 수행하지 않았다.
- 7분 연속 실사용(스크롤, 첨부 미리보기, 편집기 열기 등)은 재현하지 않았다. 측정한 것은 라우트 이동 70회뿐이다.

### 5. 측정 환경의 한계

- WebView2 가 아니라 Electron(Chrome 148) 브라우저 pane. 버전·메모리 회계가 다르다.
- pane 이 숨김 상태라 rAF shim + AudioContext 언스로틀 트릭을 썼다. 실제 앱은 가시 상태이므로 rAF 가 정상 발화한다 — 이 차이는 "숨김 쪽이 더 누수처럼 보이게" 하는 방향이므로, 그 환경에서도 보존이 없었다는 결론은 보수적으로 안전하다.
- 측정 중 SvelteKit 이 한 번 전체 리로드로 떨어진 적이 있으나, 그 시점은 setTimeout 을 MessageChannel 로 갈아끼운 공격적 계측이 걸려 있던 구간이라 **계측 아티팩트로 본다**. 이후 정상 shim 상태에서 `/campaigns/C-005` 왕복은 SPA 로 정상 동작했다(컨텍스트 유지 확인).

### 6. 다음 단계 제안

1. **실제 앱(WebView2) 안에서 재기**: devtools 를 붙여 7분 시나리오 동안 `performance.memory.usedJSHeapSize` 를 1분 간격으로 기록. 브라우저에서 나온 결론(JS 힙 평평)이 WebView2 에서도 성립하면, 원인은 확정적으로 renderer 의 비-JS 영역이다.
2. **플래토 확인**: 7분이 아니라 20~30분을 돌려 236 MB 가 계속 오르는지, 아니면 캐시 상한에서 평평해지는지 본다. 평평해지면 회수 가능한 캐시이고 버그가 아니다.
3. 계속 오른다면 비-JS 영역을 좁힌다 — 첨부/이미지 미리보기 디코드 캐시, 마크다운(mermaid/katex) 렌더 결과, 폰트 글리프 아틀라스 순.
4. 이 퀘스트의 조사 설계 중 "보드 canvas" 가설은 (2) 근거로 폐기해도 된다.

측정 스크립트는 전부 페이지 콘솔에서만 실행했고, 저장소 파일은 전혀 건드리지 않았다. 임시 서버(8813)는 조사 종료 후 정리했다.
