## 증상

페이지 내 검색([[REQ-018]])에서 **찾기 창을 닫아도 강조가 남는다**
(admin 보고). 일반 강조(노랑)와 현재 항목(파랑) **둘 다** 남는다.

## 코드는 지우고 있었다

`clearHighlights()` 는 `close()`(✕·Escape)와 `onDestroy`(페이지 이동) 세 경로
모두에서 불린다. jsdom 에 `CSS.highlights` 대역을 세우고 확인했더니 **세 경로
전부 `delete:og-find` / `delete:og-find-current` 가 나간다.** 이름도 색도
`global.css` 의 `::highlight()` 와 정확히 짝이다(노랑 = `--warning`,
파랑 = `--accent`).

즉 호출은 되는데 화면이 안 지워진다 — **레지스트리에서 빠져도 다시 그리지
않는 것**으로 보인다. WebKit 계열에서 알려진 무효화 문제다.

## 고친 방식

지우는 순서를 바꾼다. 등록해 둔 `Highlight` 객체 참조를 들고 있다가,

1. 먼저 `Highlight` 자체를 **비운다**(`clear()`) — Range 를 다 빼면 그 자리는
   확실히 다시 그려진다.
2. 그다음 레지스트리에서 뺀다(`delete`).

어느 쪽이 듣든 결과는 같다. 남아 있던 Range 참조도 함께 놓아준다.

**순서가 규칙의 일부다.** 뺀 뒤에 비우면 그리기와 무관해지므로 의미가 없다 —
테스트가 이 순서를 고정한다.

## 확인 못 한 것 (정직하게)

**재현을 못 했다.** jsdom 에서는 원래 코드도 정상 동작하고, 이 세션에는
브라우저를 띄울 수단이 없다. 그래서 위 원인은 **추정**이고, 이 수정은 "지우기
경로를 완전하게 만드는" 방어적 변경이다. 추정이 틀렸다면 증상이 그대로일 수
있으니 admin 재확인이 필요하다.

재확인 시 알려 주면 좋은 것: 데스크톱 앱인지 브라우저인지, 브라우저면 어떤
것인지. WebKit(사파리/WKWebView)에서만 나는지가 갈리면 원인이 확정된다.

## 검증

`FindBar.test.ts` 5건 신규. jsdom 에 Highlight API 대역을 세워
(컴포넌트 초기화 **전에** — `canHighlight` 는 그때 한 번 계산된다) 칠하기가
실제로 동작하는지부터 확인하고, ✕ / Escape / 언마운트 세 경로와 비우기 순서를
고정한다. 되돌리기 시험 통과 — `clear()` 를 빼면 1건 실패.

frontend 653 pass, `npm run check` 0 errors.

## 테스트 방법 (실기)

1. 문서형 화면에서 검색 → ✕ 로 닫기 → **강조가 사라진다.**
2. Escape 로 닫아도 같다.
3. 검색한 채 다른 페이지로 이동 → 강조가 남지 않는다.
4. 검색 → 닫기 → 다시 검색 → 이전 강조가 섞이지 않는다.
