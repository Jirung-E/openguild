릴리즈 페이지의 릴리스 노트가 두 번씩 표시되고, 플랫폼 빌드 잡들이 동일한 GitHub Release를 각자 갱신한다.

## 실제 본문 (v0.4.1-beta)

```
**Full Changelog**: https://github.com/Jirung-E/openguild/compare/v0.4.0-beta...v0.4.1-beta

**Full Changelog**: https://github.com/Jirung-E/openguild/compare/v0.4.0-beta...v0.4.1-beta
```

자동 생성 릴리스 노트를 Windows/Linux 잡에서 각각 실행해 기존 본문에 새 노트가 다시 붙은 것이 직접 원인이었다. 또한 자동 생성 노트는 PR 목록 중심이라 직접 커밋을 사용하는 이 저장소의 CHANGELOG 내용을 보여주지 못했다.

## 1차 수정

- `scripts/extract-release-notes.ps1`가 태그에 맞는 CHANGELOG 절과 compare 링크를 추출한다.
- 플랫폼 잡의 `generate_release_notes`를 없애고 `body_path`를 사용한다.
- CHANGELOG 절이 없거나 요약이 없으면 릴리스 전에 실패시킨다.

### 추출 스크립트 검증 기록

- v0.4.1-beta 기준 추출 결과 1565자이며 CHANGELOG 0.4.1 절과 완전히 일치하고 compare 링크만 뒤에 추가됐다.
- Windows PowerShell 5.1의 ANSI 기본 인코딩으로 한글이 깨지는 문제를 피하려고 `[IO.File]::ReadAllLines(..., UTF8Encoding($false))`를 사용한다.
- PowerShell 5.1/.NET Framework에 없는 `[IO.Path]::GetFullPath(a, b)` 2인자 오버로드를 쓰지 않고 rooted 경로를 직접 판정한다.
- 스크립트 자체는 Windows PowerShell 5.1이 한글 주석을 파싱할 수 있도록 BOM 있는 UTF-8로 저장하고 출력 파일은 BOM 없는 UTF-8로 쓴다.

이 방식은 본문 중복은 막지만 Windows·macOS·Linux가 같은 노트를 각각 추출하고 동일한 Release를 최대 세 번 갱신한다. `workflow_dispatch` artifact에도 같은 내용의 `release-notes-Windows`, `release-notes-Linux`가 따로 나타나며 macOS 미리보기는 없어 구조를 오해하기 쉽다.

## 최종 구조 (2026-08-12)

릴리스 메타데이터 생성과 실제 게시를 플랫폼 빌드에서 분리한다.

1. `release-notes` 잡이 CHANGELOG에서 `release-notes.md`를 한 번만 만들고 `release-notes-preview` artifact로 올린다.
2. Windows·macOS·Linux 잡은 패키지만 빌드해 각 플랫폼 artifact로 올리고 GitHub Release를 직접 건드리지 않는다.
3. 마지막 `publish-release` 잡이 릴리스 노트와 세 플랫폼 artifact를 내려받는다.
4. 같은 배포 파일의 `.sig`에서 Windows/macOS/Linux가 모두 포함된 `latest.json`을 합성한다.
5. 태그 실행에서만 릴리스 본문, 모든 패키지, 서명, `latest.json`을 한 번의 `Create GitHub Release` 단계로 게시한다.
6. `workflow_dispatch`에서는 실제 Release를 만들지 않고 공용 릴리스 노트와 updater manifest 미리보기만 제공한다.

플랫폼 하나라도 실패하면 `publish-release`가 실행되지 않으므로 불완전한 Release가 먼저 만들어지지 않는다. 대신 최종 잡이 빌드 artifact를 다시 내려받아 GitHub Release로 올리므로 실행 시간과 artifact 전송량은 소폭 늘어난다.

## 테스트 방법

### workflow_dispatch

1. `release notes` 잡이 한 번만 실행되고 성공하는지 확인한다.
2. artifact 목록에 `release-notes-preview`가 정확히 하나 있고 `release-notes-Windows`, `release-notes-Linux`, `release-notes-macOS`가 없는지 확인한다.
3. Windows·macOS·Linux 패키지 artifact가 모두 존재하는지 확인한다.
4. `assemble & publish release` 잡이 성공하고 `updater-manifest-preview/latest.json`에 `windows-x86_64`, `darwin-aarch64`, `linux-x86_64`가 모두 있는지 확인한다.
5. 수동 실행이 새 GitHub Release를 만들거나 기존 Release를 수정하지 않았는지 확인한다.

### 실제 0.5.0 릴리스 태그

1. `Create GitHub Release` 단계가 `assemble & publish release` 잡에서 한 번만 실행되는지 확인한다.
2. Release 자산에 Windows installer, macOS DMG/updater/CLI·Server tar.gz, Linux deb/rpm/AppImage, 각 updater 서명, `latest.json`이 모두 있는지 확인한다.
3. 릴리스 본문이 CHANGELOG 해당 절과 일치하고 compare 링크가 한 번만 표시되는지 확인한다.
4. 한글이 깨지지 않고 플랫폼 잡의 완료 순서와 무관하게 결과가 동일한지 확인한다.
