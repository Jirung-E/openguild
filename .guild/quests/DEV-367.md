## 배경

[[BUG-249]] 에서 검색 발췌가 한글 중간에서 패닉했다. 그 자체는 고쳤지만,
**패닉이 났을 때의 서버 거동**이 따로 문제였다.

현재 라우터에 catch-panic 계층이 없다. 핸들러가 패닉하면 그 연결이 그냥
끊긴다 — 500 도 아니고 본문도 없다.

```
$ curl .../api/search?q=근데
  HTTP 000            ← ERR_EMPTY_RESPONSE
```

## 왜 문제인가 — 조용히 잘못된 답을 준다

클라이언트는 이걸 **네트워크 오류**로 본다. 강화 검색은 실패 시 "기존(로컬)
동작으로 되돌림" 이 설계라([[REQ-010]] / [[REQ-011]] / [[REQ-012]] 공통),
결과적으로 사용자에게는 **"검색 결과 없음"** 으로 보인다.

BUG-249 를 사용자가 "검색이 잘 안 된다" 로 겪은 이유가 이것이다. 서버가
죽고 있다는 신호가 화면 어디에도 없었고, 서버 로그를 직접 열어보고서야
드러났다.

## 고칠 방법

`tower_http::catch_panic::CatchPanicLayer` 를 가장 바깥쪽에 얹는다.

```toml
# server/Cargo.toml
tower-http = { version = "0.6", features = [..., "catch-panic"] }
```

```rust
// server/src/main.rs — 압축보다 바깥. 압축 계층 자체가 패닉해도 잡히도록.
.layer(CatchPanicLayer::custom(panic_to_500))
```

응답 본문은 기존 에러 형식(`{"error": "..."}`)에 맞춘다 — 프런트의
`transport.ts` 가 그 필드를 읽어 메시지를 띄운다. 패닉 메시지 원문을 그대로
노출할지는 판단이 필요하다:

- **내부 경로·변수가 드러난다.** 이 서버는 인증이 없고 LAN/Tailscale 로
  열어 쓴다.
- 반대로 감추면 사용자가 신고할 근거가 사라진다.

절충안: 응답에는 고정 문구 + 서버 로그에는 전체(패닉 메시지 + 백트레이스).
`TraceLayer` 가 이미 있으므로 `tracing::error!` 로 남기면 같은 로그에 모인다.

## 확인할 것

- **정적 자산 fallback 도 덮이는지.** 압축 계층이 "가장 바깥" 인 이유가
  정적 fallback 까지 덮기 위해서였다(DEV-332 주석). catch-panic 도 같은
  위치 논리가 필요하다.
- **스트리밍 응답**(첨부 zip, [[BUG-241]])에서 패닉이 헤더 전송 **후에**
  나면 500 으로 바꿀 수 없다. 그 경우는 연결 끊김이 그대로일 텐데, 최소한
  로그에는 남아야 한다.
- Tauri 경로(`gui/src/commands.rs`)는 별개다. 커맨드가 패닉하면 invoke 가
  에러로 돌아오는지 확인 — 아니면 GUI 도 같은 조용한 실패가 된다.

## 테스트

일부러 패닉하는 라우트를 테스트 전용으로 두고 500 + 에러 본문을 확인한다.
`#[cfg(test)]` 로만 등록해 배포 빌드에는 없게 한다.
