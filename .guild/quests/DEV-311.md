DEV-310 이 sibling(댓글/메모)과 캠페인 본문 편집까지 증분화했다. 아직 full reindex 로 넘기는 나머지:

## 남은 부류
1. **캠페인 신규/삭제** — 행 생성 + `campaign_quests`/댓글/메모/체크리스트 연쇄 삭제가 얽혀 보류했다. 빈도는 낮다.
2. **도서관(BOOK)·규칙 문서** — `library/**`, `rules/**` + `doc_history` 사이드카.
3. **worklog 노트** — `worklog/*.md`.
4. **types / statuses / tags 정의(`*.toml`)** — 이건 **의도적으로 남기는 게 맞다**. 상태 slug·타입 prefix 가 바뀌면 기존 행의 해석 자체가 달라져 전체 재구축이 안전하다. 증분화하지 않기로 판단한 근거를 여기 남긴다.

## 성능 메모 (DEV-310 실측에서 발견)
캠페인 본문 1건 재적재가 **533ms** 다. 링크된 퀘스트가 46건인 캠페인에서 `DELETE campaign_quests` + 링크당 SELECT/INSERT + 체크리스트 교체가 **각각 별도 트랜잭션**(문장당 fsync)으로 돌기 때문. 한 트랜잭션으로 묶으면 수십 ms 로 떨어질 것 — 상세 진입 경로(`refresh_campaign_if_stale`)도 같이 빨라진다.

## 검증
- 각 부류별 파일 1개 추가/수정/삭제 후 `needs_full_reindex == false` 단위 테스트.
- 열기 경로가 **파일을 다시 쓰지 않는지** 반드시 확인(DEV-310 에서 캠페인 write-back 을 열기 경로에서 뺀 것과 같은 이유 — BUG-103 의 재발 방지).

## 구현 완료 (2026-08-06)

### 한 것
1. **캠페인 신규/삭제 증분화** (`sync_changed_campaign_files`) — 예전엔 index 에 없는
   새 파일이나 사라진 파일을 만나면 `needs_full_reindex = true` 로 안전망(full
   reindex)에 넘겼다. 이제 `insert_new_campaign`(행+체크리스트+`campaign_quests`
   링크를 한 트랜잭션으로 INSERT) / 행 직접 DELETE(파일 소멸 또는 외부에서
   `deleted=true`)로 직접 처리 — 자식 테이블이 전부 FK `ON DELETE CASCADE` 라
   quest 삭제와 동일 수준으로 단순했다.
2. **캠페인 재적재 트랜잭션화(perf)** — `refresh_campaign` 이 UPDATE + 체크리스트
   교체(자체 트랜잭션) + `campaign_quests` DELETE + 링크당 SELECT/INSERT 를 전부
   **별도(autocommit) 트랜잭션**으로 실행하던 걸 하나로 묶었다(링크 46개 캠페인
   기준 문장당 fsync ~95회 → 1회). `replace_checklists_from_file` 은 자체
   `pool.begin()` 을 열어 중첩 트랜잭션(교착 위험)이 되므로, 트랜잭션-바인딩
   버전(`replace_checklists_in_tx`)을 새로 둬서 우회.
3. **도서관(BOOK) 문서 증분화** (`sync_changed_library_files`, 신규) — 신규 파일은
   `insert_new_library_doc` 으로 INSERT(soft-deleted 문서도 reindex 와 동일하게
   deleted_at 채워 적재 — 번호 충돌 검증에 필요), 수정은 상세조회용
   `ops::library::get_book` 의 UPDATE 로직을 그대로 재사용(중복 구현 회피),
   삭제는 행 hard DELETE(`library_tags` 는 FK cascade). `file_mtime::
   list_primary_cached_files` 에 도서관 문서를 추가해 `detect_drift`/`sync_all`
   도 같은 캐시로 자동 커버.

### 조사 후 범위에서 뺀 것 (모듈 doc 주석에 근거 기록)
- **규칙 문서(`rules/**`)** — `repo::rules` 자체가 DB 캐시 없이 파일을 직접 읽는
  구조라 증분화할 대상이 아예 없음.
- **worklog 노트** — 마찬가지로 파일 직독 패턴. `activities()`/`daily_summary()`
  는 이미 동기화된 다른 테이블(quest_history 등) 위의 순수 조회라, 그 테이블이
  최신이면 별도 작업 없이 최신.
- **doc_history 사이드카 외부 편집 반영** — 앱 내부 mutation(BUG-189)은 이미
  증분 반영되지만, `.guild/history/*.jsonl` 을 외부(git pull)에서 직접 편집하는
  경우는 quest_history/campaign_history 와 마찬가지로 전체 재구축 전용이다 —
  "부분(추가된 줄만) 반영" 메커니즘이 이 코드베이스 어디에도 없어 새로 만들기엔
  범위가 크고 빈도가 낮음. 안전망(full reindex) 유지.

### 검증
- 단위 테스트 9건 추가(캠페인 신규/삭제/외부soft-delete/트랜잭션 일관성 4건 +
  도서관 신규/수정/삭제 3건 + 기존 `new_campaign_file_still_falls_back` 을
  새 동작에 맞게 교체) — 전부 `needs_full_reindex == false` 확인.
  `cargo test -p openguild-core --lib incremental` 30/30, 전체
  `cargo test -p openguild-core --lib` 390/390.
- 실 프로젝트 길드 규모의 정량적 `bench_open` 재측정(651퀘스트, 533ms→목표
  100ms 미만)은 이번 세션에서 별도 재현하지 않음 — 대신 트랜잭션 수를
  ~95개(문장당 autocommit)에서 1개로 줄이는 구조적 수정이 코드 리뷰 + 통과하는
  단위 테스트로 확인됨.
- 스크래치 길드(`--guild`)에서 `campaign new`/`library new` + 외부 파일 추가 후
  `reindex`/`check drift`/`check counters` 로 정합성 확인.

## 테스트 방법

1. GUI 에서 캠페인을 하나 만들고(또는 `.guild/campaigns/` 에 파일을 직접 추가)
   앱을 재시작 — 재색인 안내 없이 바로 목록에 보이는지.
2. 링크된 퀘스트가 여러 개인 캠페인의 본문을 외부에서 편집(제목만 바꿔도 됨)
   후 재시작 — 반응이 눈에 띄게 빠른지(체감).
3. `.guild/library/` 에 문서를 손으로 추가하거나, 기존 문서를 앱 밖에서
   편집/삭제 후 재시작 — 도서관 목록이 재색인 없이 최신인지.
4. `openguild check drift` / `check counters` 계속 clean 인지.
