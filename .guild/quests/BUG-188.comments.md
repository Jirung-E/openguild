수정 완료 — 첨부는 백업 대상에서 제외한다(admin 결정).

## 무엇이 잘못돼 있었나
`save_attachment` 이 파일을 쓴 **뒤** 같은 바이트를 `attachment_blobs` 에 INSERT 했다. SQLite blob 상한(약 1GB)을 넘기면 코드 18 로 실패하는데, 그 시점엔 이미 파일이 디스크에 있다 → 참조 없는 대용량 파일이 남고, 그 뒤로는
- `reindex` 의 `sync_attachment_blobs` 가 그 파일을 다시 담으려다 같은 에러
- 스냅샷도 `attachments/` 를 소스에 포함하므로 같은 상한에 걸림

즉 첨부 한 번 실패가 재색인·백업을 **계속** 깨뜨리는 상태였다. BUG-168 은 전송 한도(서버 2 MiB, IPC base64)만 고쳤고 저장 계층은 손대지 않았다.

## 변경
- `save_attachment`: blob UPSERT 제거. 파일 write 만.
- `save_attachment_from_file` 신설 — 경로를 받아 `std::fs::copy` 로 옮긴다. 데스크탑 첨부(`save_attachment_from_path` 커맨드)가 이 경로를 탄다. 예전엔 경로를 받고도 `std::fs::read` 로 통째로 읽어 1.5GB 를 메모리에 올렸다. 복사 실패 시 조각 파일을 지운다.
- `sync_attachment_blobs` 삭제 + reindex 호출 제거. `ReindexReport` 의 attachments 필드/출력도 제거.
- 마이그레이션 0029: `DROP TABLE IF EXISTS attachment_blobs`. index.db 는 파생 캐시라 삭제가 안전하다(공간은 다음 VACUUM 때 회수).
- 스냅샷 `SOURCE_SUBDIRS` 에서 `attachments` 제거 — 왜 빠져 있는지 주석으로 못박았다(다시 넣으면 같은 사고).
- `referenced_attachments`(blob GC 전용) 제거. 파일 GC 는 기존 per-path 판정 유지.
- 어드민 > 백업 섹션에 범위 안내 추가(ko/en): 포함(길드 문서) / 미포함(첨부 — git 또는 별도 보관 권장). 백업이 하나도 없을 때도 보이도록 목록 밖에 뒀다.

## 문서·규칙
- `docs/storage-design.md`: 첨부 절을 "백업 대상 아님" 으로 교체 + 왜 폐기했는지(1GB 상한 / 용량 / 임계값 안을 버린 이유)를 접이식으로 보존.
- 규칙 `file-truth-db-cache`: "큰 바이너리를 캐시에 욱여넣어 백업을 대신하지 말 것".
- 규칙 `restore-behavior`: 복원이 첨부를 지우지도 되살리지도 않는다 — "스냅샷에 없으면 삭제" 로직을 넣지 말 것.

## 테스트
- `attachments_are_not_backed_up_into_index_db` — 저장 후 blob 테이블 자체가 없고, 파일을 지운 뒤 reindex 해도 되살아나지 않음.
- `save_from_file_copies_source` — 경로 저장의 내용 보존·확장자 정규화·빈 파일/없는 파일 거부.
- `snapshot_excludes_attachments` — 스냅샷에 첨부 bytes 없음 + **복원해도 첨부 파일이 그대로 남음**.
- 기존 blob self-heal 테스트 2건 제거, 도서관 스냅샷 테스트는 "sidecar 만 포함"으로 정정.
