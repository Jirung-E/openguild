## 배경

macOS 에서 맨 위에서 위로 더 스크롤하면 WKWebView 가 문서를 고무줄처럼
당긴다(rubber-band). 그때 타이틀바가 **같이 내려온다**(admin 보고, 스크린샷).

## 지금 상태 — 색으로 가렸을 뿐이다

바운스 때 드러나는 띠는 **캔버스**가 칠하는데 그게 `--bg`(본문색)라 크롬
(`--nav-bg`)과 달라 흰 띠로 보였다. 캔버스 배경을 뷰포트 기준 그라디언트로
바꿔 위쪽 크롬 높이만큼을 `--nav-bg` 로 칠했다 — 바운스 때 크롬이 늘어난
것처럼 보이고 흰 띠가 사라진다.

**타이틀바가 움직이는 것 자체는 그대로다.** 눈에 덜 띌 뿐이다.

## 위치로는 못 막는다 (실기 확인)

`.titlebar` 를 `position: sticky` → `fixed` 로 바꿔 봤다. sticky 는 스크롤이
음수 구간일 때 고정이 풀리므로 fixed 면 될 것이라 봤는데, **WKWebView 는
iOS 처럼 fixed 요소도 바운스에 포함**시킨다. 실기에서 그대로 재현돼 되돌렸다
(커밋 2945baf2 → revert).

`overscroll-behavior: none` 으로 바운스 자체를 끄는 방법도 있고 실제로
동작하지만, admin 이 "아예 막는 것보다는" 이라고 해 채택하지 않았다.

## 남은 정답 — 문서 말고 안쪽 컨테이너를 스크롤

문서가 스크롤하지 않으면 문서 바운스도 없다.

```
html, body { height: 100%; overflow: hidden; }
main { overflow-y: auto; overscroll-behavior: contain; }
```

크롬은 흐름에 그대로 두고 `main` 만 스크롤한다. 바운스는 `main` 안에서만
일어나므로 타이틀바는 절대 안 움직인다.

## 그래서 안 한 이유 — 문서 스크롤에 매인 곳이 많다

| 대상 | 무엇을 쓰나 |
|------|-------------|
| `lib/utils/scroll-restore.ts` | `window.scrollTo` / `documentElement.scrollHeight` |
| `routes/+layout.svelte` | path 별 `window.scrollY` 저장·복원 |
| `lib/components/OverlayScrollbar.svelte` | `window.scrollY` / `documentElement.scrollHeight` |
| `routes/quests/[id]` | `window.scrollY` (맨 위로 버튼, snapshot 복원) |
| `routes/campaigns/[slug]` | 위와 같음 |

**다행인 점**: `OverlayScrollbar` 는 이미 `target` 이 HTMLElement 인 모드를
지원한다(컨테이너의 `scrollTop/scrollHeight/clientHeight` 를 읽는 경로가 이미
있다). `QuestList` 도 이미 자체 `overflow-y: auto` 로 스크롤한다 — 선례가 둘
있다.

## 주의

- **`position: sticky` 를 쓰는 페이지 내부 요소**들의 기준이 문서에서 `main`
  으로 바뀐다. 전수 확인이 필요하다.
- 스크롤 복원(`scroll-restore`, layout 의 path 별 저장)은 대상 요소를 바꿔야
  하고, 복원 시점에 `main` 이 이미 마운트돼 있어야 한다.
- macOS 전용 증상이지만 수정은 **전 플랫폼 동작을 바꾼다** — Windows/Linux
  회귀 확인이 필요하다(개발 환경이 macOS 라 실측 못 함).

## 테스트 방법

1. macOS 데스크톱 앱에서 맨 위에서 위로 스크롤 — 타이틀바가 **안 움직여야**
   한다.
2. 맨 아래에서 아래로 스크롤 — 본문만 출렁이고 크롬은 그대로.
3. 페이지를 옮겼다 뒤로가기 — 스크롤 위치가 복원되는지.
4. 우측 오버레이 스크롤바가 정상 동작하는지(드래그 포함).
5. 퀘스트 상세의 '맨 위로' 버튼, 댓글로 점프.
6. 퀘스트 목록(이미 자체 스크롤)이 이중 스크롤이 되지 않는지.

## 구현 — 무엇을 했나

`utils/page-scroll.ts` 를 새로 두고 **스크롤 대상을 여기 한 곳으로 모았다**.
흩어진 `window.scrollY` / `window.scrollTo` 가 각자 다른 것을 가리키면 복원이
조용히 깨지기 때문이다. `html, body` 는 `height: 100%; overflow: hidden`,
`main` 이 정확한 높이 + `overflow-y: auto` + `overscroll-behavior: contain`.

## 하면서 걸린 것 셋 — 전부 '조용히 죽는' 종류였다

1. **SvelteKit 의 스크롤 처리가 더 이상 닿지 않는다.** 라우터는 window 를
   스크롤하는데 window 는 이제 항상 0 이다. 이동 시 맨 위로 가기·뒤로가기
   복원을 layout 에서 직접 해야 했다.

2. **`beforeNavigate` 는 popstate 에서 주소가 바뀐 뒤에 실행된다.** 그래서
   떠나는 페이지의 위치를 **도착 페이지 키에** 덮어썼다 — 뒤로가기 복원이
   항상 0. `nav.from` 의 주소를 명시적으로 넘겨 고쳤다. 코드를 읽어서는 못
   찾았고, sessionStorage 를 찍어 보고 잡았다.

3. **모달 스크롤 잠금(BUG-199)이 무력화됐다.** `lockBodyScroll` 이 body 에
   `overflow: hidden` 을 걸었는데 body 는 이제 CSS 로 이미 hidden 이라 아무
   일도 안 일어나고, 모달 뒤 페이지가 그대로 스크롤됐다. 잠금 대상을 그때의
   스크롤 컨테이너로 바꾸고, 되돌리는 테스트로 검사가 무는 것까지 확인했다.

4. **점프 버튼 cluster('맨 위로' / 댓글로 / 메모로)가 영영 안 뜬다.** 퀘스트
   상세와 캠페인 상세가 표시 여부를 `window` 의 scroll 이벤트로 갱신했는데,
   컨테이너 스크롤은 window 로 버블하지 않는다. `onPageScroll` 로 옮겼다.
   함께, '한 화면 이상 내려갔나' 의 기준 높이도 창이 아니라 컨테이너로
   맞췄다 — `pageScrollTop()` 이 컨테이너 기준이 됐으므로 짝이 맞아야 한다.

같은 이유로 layout 의 주기적 스크롤 저장 리스너도 `window` 에 붙어 있었다 —
그대로 뒀으면 새로고침 복원이 죽는다. `main` 의 `min-height` 를 물려받아
가운데 서던 길드 전환 스피너도 같이 고쳤다.

**남아도 되는 것**: 팝업 위치 보정들이 쓰는 `window.addEventListener('scroll',
h, true)` 는 **capture** 라 컨테이너 스크롤도 그대로 잡는다 — 손대지 않았다.

## 검증 (1400×900 / 375×812)

- 문서가 넘치지 않는다(`documentElement.scrollHeight === clientHeight`).
- `main.scrollTop = 300` 에서 `header` 의 top 이 0 그대로, `window.scrollY` 0.
- `main` 은 52→900 을 정확히 채운다(잘림 없음). 모바일도 동일.
- 앞으로 가는 이동은 맨 위에서 시작, 뒤로가기는 400 → 400 복원.
- 퀘스트 목록·보드에서 `main` 이 이중 스크롤 되지 않는다.
- 모달을 열면 `main` 에 `overflow: hidden` + `overscroll-behavior: contain`,
  닫으면 원래대로.
- 오버레이 스크롤바가 컨테이너를 따라간다(스크롤 0 에서 thumb top 52 = main 의
  위쪽, 600 에서 324).
- 점프 cluster 가 뜨고, `scrollIntoView` 가 `main` 을 스크롤한다(header 는 top 0
  고정). `behavior: 'smooth'` 는 이 미리보기 환경에 애니메이션 프레임이 없어
  관찰 불가 — `'auto'` 경로로 대신 확인했다.

**남은 실측**: macOS 데스크톱 앱에서의 러버밴드 자체(브라우저 미리보기로는
재현 불가) 와 Windows/Linux 회귀.
