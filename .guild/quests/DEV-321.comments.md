구현 완료 — 불확정 바를 실제 진행률로 바꿨다. DEV-298 이 후속으로 미뤄둔 청크 업로드 API 없이 해결된다.

## 데스크탑(경로 기반) — 진짜 %
- core: `save_attachment_from_file_with_progress(store, src, ext, on_progress)` — 4 MiB 버퍼로 직접 옮기며 `(복사 바이트, 전체)` 를 콜백으로 흘린다. `std::fs::copy` 는 한 번에 끝나 중간을 볼 수 없었다. core 는 Tauri 를 모르므로 콜백까지만 책임진다.
- gui: 커맨드가 `upload_id` 를 받아 `attachment://progress` 이벤트로 emit. 청크마다 보내면 초당 수백 건이라 **100ms 또는 1% 단위**로만(마지막 값은 항상) 내보낸다.
- 프론트: 업로드마다 id 를 만들고 자기 이벤트만 걸러 % 로 환산.

## 브라우저/원격 — XHR
`fetch` 는 요청 본문 전송 진행을 주지 않는다(응답 스트리밍만). 첨부 POST 하나만 `postWithUploadProgress()` 로 분리해 `XMLHttpRequest.upload.onprogress` 를 쓴다. 서버·프로토콜 변경 없음. Tauri invoke 경로(로컬 붙여넣기/드래그&드랍)는 관측 수단이 없어 기존 호출로 넘어가고 불확정 바 그대로다.

## '준비 중' 단계
브라우저 경로는 전송 **전에** base64 변환이 있다(파일을 메모리에 올림). 이 구간은 %가 없어 0% 정지처럼 보이므로 `phase: 'preparing'` 으로 분리해 "준비 중…" 을 표시한다.

## UI
`AttachProgress` 에 `phase` / `percent` 추가. %를 알면 결정형 바 + 숫자, 모르면 기존 불확정 애니메이션. `role="progressbar"` + `aria-valuenow`/`aria-valuetext` 로 스크린리더에도 숫자가 간다.

## 한계 (정직하게)
- **로컬 서버(localhost)에서는 진행 이벤트가 사실상 1건**이다 — 12MB 가 소켓 버퍼로 즉시 들어가 100% 로 한 번에 온다. 실제로 의미 있는 건 원격 서버 연결과, 아래 데스크탑 경로다. localhost 브라우저 모드에서는 '준비 중' 단계 표시가 체감상 더 유용하다.
- **데스크탑 경로는 미검증** — Tauri 앱을 띄워야 확인 가능하다. Rust 쪽 진행 계약은 단위 테스트로 고정했지만, 이벤트 수신·바 갱신은 실제 앱에서 봐야 한다.
  1. 큰 파일(수백 MB)을 `+ 첨부` 로 선택 → 숫자가 0→100 으로 오르는지
  2. 여러 개 선택 시 파일별로 0→100 이 반복되고 순번(n/N)이 맞는지
  3. 복사 속도가 예전(`fs::copy`)보다 눈에 띄게 느리지 않은지 — 느리면 작은 파일은 기존 경로로 되돌리는 임계값을 두면 된다
