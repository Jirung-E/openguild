도서관 페이지에서 검색 가능해야 함 (제목/본문 대상).

## 방향(안)
- rules 페이지의 좌측 목록에는 검색이 없음 — 도서관은 문서 수가 늘어날 걸 감안해
  좌측 목록 상단에 검색창 추가, 제목 우선 + 본문 부분일치 (SQLite LIKE 또는
  FTS5 고려 — 문서 수 규모에 따라 LIKE 로 충분할 수 있음).
- 서버/CLI 도 `library list --query <q>` 형태로 확장 필요할지, 아니면 GUI 에서
  이미 로드된 목록을 클라이언트 필터링만 할지는 문서 수 규모에 달림 — 소규모면
  클라이언트 필터링으로 충분.

## 선행
- 없음 (독립). DEV-239(폴더 기능)과 UI 상 같은 좌측 패널을 다루므로 폴더 기능과
  함께 설계하면 좋음 — 폴더 트리 + 검색 결과를 어떻게 같이 보여줄지 결정 필요.

## 구현 (2026-07-07)
- 클라이언트 필터링으로 결정 — 이 프로젝트 규모에서 문서 수가 서버 LIKE/
  FTS5 가 필요할 만큼 크지 않다고 판단(DEV-239 도 이미 `libraryApi.list()`
  로 전체를 한 번에 적재하는 전제). 서버/CLI 변경 없음.
- `lib/utils/library-tree.ts` 에 순수 함수 `searchBooks(books, query)`
  추가 — 제목 매칭 우선, 본문만 매칭은 그다음(각 그룹 내 제목 가나다순).
  빈 쿼리는 `null`(검색 비활성 — 평소 폴더 렌더와 구분), 매칭 없으면 빈
  배열([]).
- `library/+page.svelte`: 검색창을 tree 모드 사이드바 + explorer 모드
  툴바 양쪽에 추가(`searchQuery` 공유 상태). 검색 활성 시(`searchResults
  !== null`) 두 모드 다 현재 폴더 위치/트리 구조를 무시하고 매칭 문서만
  평평한 목록/타일로 렌더 — "찾았나"가 "어느 폴더에 있나"보다 우선이라는
  판단. 결과 항목에 소속 폴더 경로를 작은 글씨로 표시(트리 모드).

## 테스트 방법
- `cd gui/frontend && npm run check && npm run check:no-hex && npm test --
  --run` (`searchBooks` 단위 테스트 4건).
- 실기: 도서관에 문서 여러 개(일부는 폴더 안) 만든 뒤, 트리/탐색기 모드
  각각에서 검색어 입력 → 폴더 구조 무시하고 매칭 문서만 보이는지, 제목
  매칭이 본문 매칭보다 위에 오는지, 검색어 지우면 원래 트리/탐색기로
  복귀하는지.
