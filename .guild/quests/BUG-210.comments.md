원인 2 수정 — 목록 응답에서 본문 제외 (`?slim=true`).

## 왜 인덱스 적재가 컸나 (admin 질문)

인덱스 **자체**는 작다 — 메모리에 남는 건 `Map<ID, {title, kind}>` 531개,
50KB 남짓. 큰 건 그걸 만들려고 받는 **응답**이었다:

- `/api/quests` 는 목록 전용 API 인데 `description` 을 전부 싣는다.
  531건 × 평균 1,095자 = 약 580KB 가 본문.
- 응답 JSON 문자열 827K자 → UTF-8 **1,156,414 바이트**. 한글이 3바이트라
  글자 수보다 바이트가 40% 더 크다.
- 정작 목록·보드·홈·태그·캠페인 상세·검색 팔레트·cross-link 인덱스 중
  **본문을 읽는 곳은 하나도 없다**(검색 팔레트는 미리보기를 열 때
  `questsApi.get(id)` 로 따로 받는다).

## 구현

- `ListQuery.slim` 추가. 쿼리스트링이 그대로 `ListQuery` 로 역직렬화되므로
  서버(`Query<ListQuery>`)와 Tauri(`list_quests` 커맨드) 양쪽이 동시에 지원됨
  — transport 분기 추가 불필요.
- `services::quests::list` 가 slim 이면 행의 `description` 을 None 으로.
  SELECT 에서 빼지 않은 이유: `search` 가 본문을 봐야 하고, SQL 분기를 늘리면
  필터 조합마다 경로가 갈라진다. 로컬 SQLite 읽기는 싸고 비용은 네트워크다.
- `QuestRow.description` 에 `skip_serializing_if` — slim 응답은 필드 자체가
  없다(널이 아니라 부재). TS `Quest.description?` 로 반영.
- 프런트 8개 호출부 전부 `list(true)` / `listRecent(true)`.
- CLI 는 본문을 출력·검색에 쓰므로 `slim: false`.

## 측정

- `/api/quests` 응답: **1,156,414 → 258,404 바이트** (-78%).
- 라우트 이동 16회(/?view=list ↔ /rules): 수신 9.14MB → **2.25MB**,
  힙 증가 +37.1MB → **+8.6MB**.
- 이동 100여 회 후 힙: 수정 전 260MB(계속 상승 중) → **약 100MB**.

## 남은 것

이동당 약 1MB 씩은 여전히 쌓인다(수정 전 2.5MB). GC 후 바닥값도 조금씩
오르므로 순수 보존 문제가 남아 있다 — 별도 조사 대상.

부수 발견: **서버가 압축을 전혀 하지 않는다**(`content-encoding` 없음,
tower-http 의 `compression` feature 미사용). 한글 JSON 은 gzip 이 잘 먹는
데이터라 별도 퀘스트로 등록한다.
