   체감 차이가 커질 수 있음.

## 2차 조사 + 시도한 수정 (2026-08-01)

내장 Retina 화면만 쓰신다고 확인해주셔서 pixelRatio 낭비 가설은 배제.
makeSvgUrl(노드 SVG 생성)도 테마 전환시에만 호출되고 pan/zoom 중엔 안 불림 —
핫패스 아님. onBoardWheel/syncLanes 도 이미 rAF 배칭 + 캐시로 최적화돼 있음.

코드 리뷰로 더 이상 뚜렷한 자체 버그는 못 찾음 — 남은 게 cytoscape 기본
설정에 pan/zoom 퍼포먼스 옵션이 하나도 안 켜져 있던 것. `textureOnViewport`
(pan/zoom 중 뷰포트를 단일 텍스처로 캐싱, 개별 노드/엣지 매 프레임 재드로우
생략) / `hideEdgesOnViewport`(pan/zoom 중 엣지 숨김) 를 cytoscape 생성자에
추가 — cytoscape 공식 문서가 정확히 이런 "pan/zoom 시 버벅임" 증상에
권장하는 표준 옵션들. 실제 원인(WKWebView canvas 합성 비용 추정)을 없애는
근본 수정은 아니고, cytoscape 자체 렌더 부하를 줄이는 완화책 — 그래도 노드
수/엣지 수와 무관하게 전 플랫폼에 안전하고 다운사이드가 거의 없어 우선
적용.

## 테스트 방법
1. macOS 실기에서 퀘스트가 여러 개 있는 보드(이 repo 자체 길드 등)를 열고
   빠르게 pan/zoom 반복 — 이전 대비 체감 버벅임이 나아졌는지.
2. 노드 드래그/선택/토론 배지 등 기존 상호작용에 시각적 회귀가 없는지

   passed).

그땐 BUG-144(리눅스 성능) 처럼 on_hold 로 넘기고 실측 프로파일링(Web
Inspector Timeline)이 필요.

## 3차 시도 — 근본 원인 재파악 + forceRender (2026-08-01)

textureOnViewport 원복 후에도 "배경 먼저 움직이고 노드가 뒤늦게 따라오는"
증상이 그대로 재현됨(사용자 재확인) — 애초에 이게 처음 보고했던
"프레임드랍"의 더 정확한 서술이었을 뿐, 별개 회귀가 아니었던 것으로 보임.

## 원인 재분석

cytoscape 의 캔버스 리렌더는 cy.zoom()/cy.panBy() 호출 즉시 일어나지
않는다 — 내부적으로 dirty flag 만 세우고, 실제 리페인트는 cytoscape 자체의
내부 requestAnimationFrame 루프(우리 코드의 wheelRaf 와는 별개 스케줄)의
다음 tick 에 실행된다. 반면 lane 배경(syncLanes)은 cy 의 'pan'/'zoom'
이벤트 리스너에서 동기 실행 — cy.zoom()/panBy() 호출과 **같은 tick**에
DOM 이 바로 갱신된다. 두 레이어(DOM 배경 vs 캔버스 노드)의 실제 갱신
시점이 구조적으로 어긋나 있었던 것 — WKWebView 의 canvas 프레임 처리가
상대적으로 느려서(또는 내부 rAF 스케줄 순서 차이로) 이 격차가 macOS 에서
특히 눈에 띄게 드러난 것으로 추정.

## 수정

flushBoardWheel() 끝에 cy.forceRender() 추가 — cytoscape 의 내부 dirty
flag 를 이번 tick 안에서 바로 소비시켜 캔버스 리페인트를 강제. DOM
갱신(syncLanes)과 같은 tick 에서 캔버스도 리페인트되도록 스케줄 격차를
제거하는 시도. textureOnViewport 와 달리 렌더링 방식 자체는 안 바꾸고
"언제" 그리는지만 조정하는 거라 이전처럼 새로운 시각적 아티팩트를 만들
가능성은 낮음.

## 테스트 방법
1. macOS 실기에서 보드 pan/zoom 하며 배경-노드 디싱크가 없어졌는지 확인.
2. 여전히 어긋나 보이면 — 캔버스 자체 리페인트 소요 시간이 진짜 느려서
   forceRender 로 "빨리 그려라" 해도 그 안에서 못 끝내는 것 → 스케줄
   문제가 아니라 순수 렌더 처리량 문제로 결론, 그때는 노드 시각 복잡도를
   줄이는 방향(그림자/배지 단순화 등) 검토 필요.
3. `npm run check` / `npm test -- --run` — 이미 통과 확인.

## 4차 시도 — WebGL 렌더러 (2026-08-01)

cytoscape 3.33.3 에 내장된 WebGL 렌더러(`webgl: true`, texture atlas +
인스턴싱 기반 GPU 직접 렌더)를 시도. 결과: 화질 저하만 발생하고 지연/
GPU 사용률은 그대로 — 무효. 원복.

## 최종 결론

시도한 것 총 4가지:
1. textureOnViewport — 무효(리눅스 때 이미 화질 저하로 기각된 선택지)
2. hideEdgesOnViewport — 무효(위와 세트)
3. forceRender() (스케줄 강제) — 무효
4. webgl: true (렌더 방식 자체 교체) — 무효

**렌더링 "방식"을 Canvas2D → WebGL 로 바꿔도 증상이 그대로라는 게 결정적** —
병목이 cytoscape 의 그리기 파이프라인 내부가 아니라, WebKit 이 트랙패드
제스처 입력을 받아 프레임을 스케줄링/컴포지팅하는 더 아래 레이어에 있다는
뜻. 이건 cytoscape 설정은 물론 앱 코드 레벨에서 손댈 수 있는 범위 밖.

리눅스(BUG-144/BUG-141)에서 이미 WebKit Inspector 실측 후 "WebKitGTK
렌더링 성능의 알려진 한계"로 보류한 것과 정확히 같은 결론 — macOS 는
WebKit/WKWebView, 리눅스는 WebKitGTK. 같은 WebKit 계열 엔진의 공통
한계로 최종 판단.

프레임워크 레벨 대안(Electron=Chromium 번들, egui/wgpu=네이티브 GPU
렌더 서페이스)도 검토했으나 전자는 이 이슈 하나 때문에 프레임워크
전체를 바꾸는 격이고, 후자는 보드 UI 전체 재작성 + 웹 배포 별도 대응이
필요한 큰 공사라 이 세션 범위 밖으로 판단.

BUG-144/BUG-141 선례와 동일하게 on_hold 처리.
