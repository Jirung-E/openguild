BUG-180 조사 결론: WebKit(Safari/WKWebView/WebKitGTK) 이 트랙패드 2손가락
제스처를 인식하면 `<canvas>` 요소의 메인스레드 페인트 커밋을 미룬다 —
DOM 요소의 `transform`/`opacity` 전용 변경(컴포지터 전용, 페인트 불필요)
은 이 지연이 없다. Canvas2D→WebGL 전환, textureOnViewport, forceRender
전부 "캔버스 안에서" 해결하려 해서 무효했음(BUG-180 참조).

## 제안 (사용자 아이디어)

렌더링을 제스처와 분리한다 — 제스처(wheel 연속 입력) 중엔 캔버스를 아예
안 건드리고, 캔버스 내용을 DOM 스냅샷(이미지)으로 띄워서 그 스냅샷에만
`transform`(컴포지터 전용) 적용. 제스처 종료(입력 idle) 시 스냅샷 내리고
실제 캔버스 재렌더.

애플 제품 페이지 스크롤 애니메이션도 유사 원리 — 네이티브 스크롤(컴포지터
최적화 경로) + 캔버스는 값싼 프레임 blit만. 우리는 네이티브 스크롤을 못
쓰지만(pan/zoom 은 커스텀 제스처), 같은 원리로 "제스처 중 캔버스 안 건드리기"
는 적용 가능.

## 구현 개요

1. 제스처 시작(첫 wheel 이벤트) 시 canvas 스냅샷 1회 캡처(연속 캡처 X —
   비용 큼).
2. 스냅샷을 캔버스 위에 겹친 오버레이 엘리먼트(`pointer-events: none`)로
   표시, pan/zoom 델타를 CSS `transform`으로 적용(syncLanes 의 lane 배경과
   동일 패턴).
3. wheel idle(예: 150ms) 감지 시 오버레이 제거 + 캔버스를 최종 위치로
   진짜 재렌더.
4. 클릭: 오버레이는 `pointer-events: none` 이라 제스처 중이 아니면(대부분의
   클릭 시점) 그대로 캔버스가 받음 — cytoscape 자체 tap 핸들러 안 건드림.

## 리스크 / 확인 필요

- Windows(WebView2/Chromium) 는 이 문제가 원래 없었음(크롬에서 재현
  안 됨 확인) — 스냅샷 캡처를 제스처당 1회로 제한하면 추가 비용은 미미할
  것으로 예상되나, 실기 검증 전엔 확신 불가. 구현 후 반드시 Windows 에서도
  회귀(오히려 더 느려짐/깜빡임 등) 없는지 확인 필요.
- 스냅샷↔실제 캔버스 전환 시점의 미세한 위치/스케일 불일치로 인한 "튐"
  가능성 — 정밀한 pan/zoom 좌표 매핑 필요.
- `canvas.toDataURL()`/`createImageBitmap()` 캡처 자체의 비용 측정 필요.

## 테스트 방법
1. macOS 실기 — pan/zoom 중 노드가 배경과 함께 움직이는지, 클릭이 정상
   동작하는지.
2. Windows 실기 — 회귀(추가 지연/깜빡임) 없는지.
3. 웹 브라우저(Safari + Chrome) 양쪽 확인.
4. `npm run check` / `npm test -- --run`.
