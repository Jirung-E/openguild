BUG-180 조사 결론: WebKit(Safari/WKWebView/WebKitGTK) 이 트랙패드 2손가락
제스처를 인식하면 `<canvas>` 요소가 화면에 반영되는 시점(컴포지팅) 자체를
정책적으로 미룬다 — 얼마나 빨리/무엇을 그리는지와 무관. DOM 요소의
transform 전용 변경(lane 배경 등)은 이 지연이 없음.

## 시도한 것들 (전부 원복, 순서대로)
1. cy.png() 스냅샷 오버레이(1회 캡처 + CSS transform)
2. hideEdgesOnViewport/textureOnViewport/forceRender (cytoscape 자체 옵션)
3. WebGL 렌더러(webgl:true)
4. 스냅샷 더블버퍼링(<img> 2장, onload 확인)
5. CSS transform 만 쓰는 가상 pan/zoom(캡처 없음, 제스처 종료 시 1회
   커밋 + reveal 캡처)
6~8. 위 5번 구조에서 깜빡임 수정 시도(순서 변경/decode()/유예시간
   400→900ms)
9. 원안(BUG-144, 직접 cy 호출) + makeSvgUrl 사전 디코드 — 그리기 자체는
   빨라졌으나 WebKit 표시 지연은 그대로(정책 문제라 속도와 무관 확인)
10. 5번 재도입 + 유예시간 축소(200ms) — 도로 깜빡임/여백 재발
11. 유예시간 추측 대신 120ms 주기 재캡처 가리개 — cy.png() 반복 호출
    자체가 예상보다 비싸 **크롬에서까지 저하** 발생, 즉시 원복

## 최종 결론

이 문제는 앱/cytoscape 설정 레벨에서 해결 불가능한 것으로 최종 판단.
근본 원인은 브라우저 엔진(WebKit)이 제스처 인식 중 캔버스 컴포지팅을
미루는 정책 자체이고, 어떤 방식으로 우회를 시도해도(느리게 하든 빠르게
하든, 캡처하든 안 하든) 이 정책 자체를 못 바꾼다.

**유효했던 부수 개선**: makeSvgUrl() 사전 디코드(9차) — 노드 배경 SVG를
로드 시점에 미리 Image 로 디코드시켜 브라우저 캐시를 데워둠. 이건
독립적으로 유효한 성능 개선이라 유지.

**진짜 근본 해결책(사용자 제안, 후속 퀘스트로 분리)**: lane 배경/그리드
스냅 점이 지연이 전혀 없는 이유가 정확히 "캔버스가 아니라 DOM+CSS
transform"이기 때문 — 노드도 cytoscape 캔버스 대신 DOM 엘리먼트로
그리면 이 문제 자체가 성립하지 않게 됨. 다만 보드 렌더링 아키텍처를
통째로 바꾸는 큰 작업이라 이 세션 범위 밖 — 별도 퀘스트로 분리해 등록함.

## 최종 코드 변경 (이 퀘스트 범위)
makeSvgUrl() 사전 디코드만 유지. 나머지 실험은 전부 원복.

check(0 errors)/test(334 passed) 통과.

## 테스트 방법
1. 두 손가락 pan/zoom 시 노드 배경 이미지 로드가 이전보다 빠르게
   느껴지는지(사전 디코드 효과) — 지연 자체는 WebKit 플랫폼(macOS/Linux)
   에서 남아있는 게 정상(알려진 한계).
2. 회귀 없는지(클릭/드래그/줌 등 기존 상호작용).
