﻿1.5GB 압축파일을 데스크탑에서 첨부하니 실패한다(admin 보고):

```
internal error: error returned from database: (code: 18) string or blob too big
```

## 원인
BUG-168 은 **전송 한도**만 고쳤다(서버 2 MiB → 64 MB, 데스크탑은 base64 IPC → 경로 전달). 저장 계층은 그대로였다: `ops::attachments::save_attachment` 이 파일을 디스크에 쓴 뒤 **같은 바이트를 `attachment_blobs` 테이블에 통째로 INSERT** 한다(DEV-069: "git 은 선택사항 — 첨부도 snapshot 만으로 복원 가능해야 한다"). SQLite 의 blob 상한은 기본 약 1GB 라 1.5GB 에서 코드 18 로 실패한다.

## 파급 (이게 더 나쁘다)
파일 write 가 **먼저** 성공하고 blob INSERT 에서 실패하므로, 참조되지 않는 대용량 파일이 `.guild/attachments/` 에 남는다. 그 상태로는
- `reindex` 의 `sync_attachment_blobs` 가 그 파일을 다시 blob 에 넣으려다 같은 에러로 실패
- 스냅샷도 `attachments/` 를 소스에 포함하므로 같은 상한에 걸려 백업이 실패

즉 첨부 한 번 실패가 재색인·백업을 계속 깨뜨리는 상태가 된다.

## 결정 (admin)
**첨부파일은 백업 대상에서 제외한다.** 임계값을 두는 대신 아예 빼는 쪽. 그리고 이 정책을 **어드민 페이지의 백업 섹션에서 설명**한다.

## 작업
- `save_attachment` 에서 blob UPSERT 제거. 경로 기반 저장은 `std::fs::copy` 로 스트리밍(1.5GB 를 메모리에 올리지 않는다).
- `sync_attachment_blobs`(reindex self-heal) 제거 + `attachment_blobs` 테이블 DROP 마이그레이션. index.db 는 파생 캐시라 삭제가 안전하다.
- 스냅샷 소스에서 `attachments/` 제외.
- 어드민 > 백업 섹션에 "백업에 첨부파일은 포함되지 않음" 안내(ko/en).
- 규칙/문서(restore-behavior, storage-design) 갱신.

## 검증
- 대용량(≥1GB) 파일 첨부가 성공하는지 + 메모리 사용이 파일 크기에 비례해 치솟지 않는지.
- 첨부가 있는 길드에서 reindex / 백업 / 복원이 모두 정상인지.
- 복원 후 첨부 파일이 지워지지 않고 그대로 남는지(백업 대상이 아니므로 건드리지 않는다).
