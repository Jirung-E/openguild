## 증상

없는 API 경로가 **200 에 HTML** 을 돌려준다.

```
$ curl -s -o /dev/null -w "%{http_code} %{content_type}\n" http://127.0.0.1:3100/api/nope
200 text/html
```

본문은 SPA 의 `index.html` 이다. API 클라이언트 입장에서는 "성공했는데 JSON 파싱이
깨졌다" 로 보인다 — 진짜 원인(그런 엔드포인트가 없다)이 응답 어디에도 없다.

## 왜 이렇게 됐나

DEV-195 의 SPA fallback 은 매칭 안 되는 경로를 전부 `index.html` 로 떨어뜨린다.
딥링크(`/quests/DEV-001` 새로고침)를 위해 필요한 동작이다. 코드 주석은
"`/api/*`, `/health` 는 이미 위에서 라우트가 매칭되므로 이 fallback 까지 오지
않는다" 고 적어 뒀는데, **등록된** 경로만 그렇다. 오타·삭제된 경로·아직 안 만든
경로는 그대로 fallback 으로 샌다.

실제로 [[DEV-380]] 작업 중 `/api/plugins` 를 만들기 **전에** 호출해 보고 200 이
와서 "이미 있나?" 하고 잠깐 헷갈렸다.

## 왜 지금 문제인가

- 클라이언트가 오타를 내거나, 서버 버전이 낮아 그 경로가 없을 때 **404 가 아니라
  200** 을 받는다. 프런트의 오류 처리는 상태코드를 먼저 보므로 엉뚱한 길로 간다.
- 반대로 `/api/quests/xyz` 처럼 파싱에 실패하는 경로는 400 을 준다 — 같은 계열의
  실수인데 응답이 제각각이다.

## 고칠 방향 (정하고 시작할 것)

`/api/` 로 시작하는 경로는 fallback 대상에서 빼고 404 + JSON 오류를 준다.
`/health` 도 같이 볼 것. 정적 fallback 은 그대로 둔다.

## 테스트 방법

- `GET /api/nope` → 404, `application/json`, 오류 메시지에 경로가 들어간다.
- `GET /quests/DEV-001` (딥링크) → 여전히 200 + index.html.
- 기존 API 경로들은 그대로 동작한다.
