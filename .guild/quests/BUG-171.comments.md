## 다음 릴리스까지 기다릴 필요 없게 만들었다

"태그를 밀어야 검증된다"는 상태가 이 버그의 원인 그 자체였다 — 릴리스 본문은
태그 push 때만 만들어지니, 0.4.1 이 중복 본문으로 나가고 나서야 알았다.
릴리스 없이 검증되는 경로를 두 개 추가:

1. **`check` 워크플로에 `release notes extraction` 잡** (매 push).
   CHANGELOG 의 최신 출시 버전(`## X.Y.Z` 첫 매치)으로 추출을 돌리고
   compare 링크 존재 + U+FFFD(인코딩 손상) 여부까지 검사한다. 빌드가 없어
   몇 초면 끝나고, 결과 본문은 `release-notes-preview` artifact 로 확인.
   → 스크립트가 깨지면 **다음 릴리스가 아니라 다음 push 에서** 잡힌다.
2. **`release` 워크플로의 추출 스텝을 dry-run 에서도 실행.**
   `workflow_dispatch` 로 수동 실행하면 릴리스는 만들지 않고(생성 스텝은 태그
   gate 유지) 추출만 돌아 `release-notes-windows` / `release-notes-Linux`
   artifact 가 나온다 — 실제 러너(pwsh 7)에서 두 OS 모두 본문을 미리 볼 수 있다.
   dispatch 시 `github.ref_name` 은 브랜치명이라 CHANGELOG 최신 버전으로 대체.

## 시험용 태그는 쓰면 안 된다 (규칙에 추가)

updater 엔드포인트가 `releases/latest/download/latest.json` 이고 워크플로가
`prerelease: false` 하드코딩이다. 즉 검증용으로 `v0.0.0-test` 같은 태그를 밀면
그게 곧 "latest" 가 되어 **사용자 앱이 시험 빌드를 업데이트로 제안**한다.
이 함정을 `release-process` 규칙에 명시했다.

## 그래도 남는 미검증 부분

액션의 `body_path` + `append_body:false` 조합이 두 번째 잡에서 **덮어쓰는지**
는 문서(*"Append to existing body instead of overwriting it"*, 기본 false)에
근거한 것이고, 실제 두 잡 동시 실행은 태그 push 때만 일어난다. 다음 릴리스
직후 릴리스 페이지를 한 번 보면 확정된다 — 어긋나도 본문은 페이지에서 직접
고칠 수 있어 되돌릴 수 없는 종류의 위험은 아니다.

## 릴리스 노트에 요약 추가 (사용자 요청)

카테고리 목록만으로는 릴리스 페이지가 20~30개 항목의 평평한 목록이 되어
"이번 버전이 뭘 바꿨는지"가 읽히지 않는다. 요약은 자동 생성할 수 없으므로
(항목을 기계적으로 줄여도 중요도 판단이 빠진다) 사람이 쓰고, 스크립트는
**빠졌는지만** 검사한다:

- `extract-release-notes.ps1`: 절이 곧바로 `### ` 로 시작하면 에러로 막는다.
  메시지에 형식(2~4줄 문단 + `**주요 변경점**` 3~5불릿)을 함께 안내.
- `release-process` 규칙: 형식 + 작성 판단 기준(주제로 묶기, 영향 큰 것부터,
  숫자 쓰기, 퀘스트 ID 는 괄호로만, 3~5개 상한) 명시.
- CHANGELOG `Unreleased`(0.5.0)에 실제 요약 작성 — 22개 항목을 5개 주제로 묶음.

검증: 0.4.1 절(요약 있음)은 정상 추출, 요약 없는 임시 절은 가드가 차단.
