admin 질문 2건에서 출발한 측정 결과. **문서 자체는 크지 않다** — 큰 건 매번
다시 받는 목록과, 캐시 정보가 없어 재사용되지 않는 응답들이다.

## 1. 상세 문서 한 건의 실제 비용 (실측)

브라우저에서 상세 페이지 1건 진입 시 새로 받는 것:

| 요청 | 해제 크기 |
|---|---|
| `/api/quests/by/BUG-006` | 6 KB |
| `/api/campaigns` | 6 KB |
| statuses / types / tag-defs / comments / memo / history | 각 0~1 KB |
| **합계** | **약 13 KB** |

즉 "글자밖에 없는 문서" 는 실제로 13KB 다. 메가바이트가 아니다.

## 2. 그런데 목록으로 **돌아갈 때마다** 275KB 를 다시 받는다

| 요청 | 전송 | 해제 |
|---|---|---|
| `/api/quests?slim=true` | 36 KB (gzip) | **275 KB** |
| quest-dependencies / statuses / types | 5 KB | 5 KB |

상세 → 목록 왕복 한 번에 약 280KB 를 다시 받고, 그걸 매번 **500여 개 객체로
파싱**한다. GUI 실측에서 "문서당 약 2MB" 로 보였던 것의 정체가 이것이다 —
문서 본문이 아니라 왕복마다 재적재되는 목록과 그 파싱 결과다.

BUG-210 이 고친 것은 "cross-link 인덱스" 의 강제 재적재였고, **목록 페이지가
자기 데이터를 다시 받는 것**은 그대로 남아 있다.

## 3. 첨부는 캐시를 아끼는 게 아니라 **매번 다시 받는다** (admin 질문 2)

`/api/guild-files/*` 응답 헤더 실측:

```
HTTP/1.1 200 OK
content-type: application/octet-stream
content-length: 6088
(cache-control 없음, etag 없음, last-modified 없음)
```

`If-Modified-Since` 를 붙여 재요청해도 **304 가 아니라 200 + 전체 본문**이
돌아온다. 검증자(validator)가 없으니 브라우저는 재사용도 조건부 요청도 못 한다.

즉 "캐시하지 않아 메모리를 아끼는" 상태가 아니라 **볼 때마다 전부 다시 받는**
상태다. 절약이 아니라 낭비다. 게다가 화면에 그려지는 순간 디코딩된 비트맵은
어차피 메모리에 올라간다(캐시 여부와 무관).

첨부 파일명은 업로드마다 고유 접미사가 붙어(BUG-219 로 결정론 문제도 수정됨)
**사실상 불변**이다 — 같은 URL 이 다른 내용을 가리킬 일이 없으므로 장기 캐시가
안전하다.

## 4. 정적 자산도 immutable 표시가 없다

`_app/immutable/*` 는 내용 해시가 파일명에 들어간 불변 자산인데
`cache-control` 이 없다. `last-modified` 만 있어 304 는 되지만, **파일마다
왕복 한 번씩** 낭비한다.

## 할 일

1. **캐시 헤더** (저위험)
   - `_app/immutable/*`: `Cache-Control: public, max-age=31536000, immutable`
   - `/api/guild-files/*`: 같은 immutable 정책 + `ETag`/`Last-Modified` 추가
   - API(JSON) 응답은 지금처럼 캐시 금지 유지 — 내용이 바뀐다.
2. **목록 응답 클라이언트 캐시** (중위험)
   - 왕복마다 275KB 재적재를 없앤다. reindex·변경 시점에 무효화해야 하므로
     BUG-210 의 memo 패턴(`loadQuestIndex`)을 참고할 것. 무효화를 놓치면
     "고쳤는데 목록에 안 보인다" 가 되므로 신중히.
