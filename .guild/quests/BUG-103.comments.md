[계획] 수정 계획 (2026-07-03, 코드 확인 완료)

## 메커니즘 확정 (core/src/incremental.rs)

sync 는 `file mtime > quests.cached_mtime` 만으로 "외부 편집"을 판정 → BUG-080 write-back(`writeback_updated_at`)이 frontmatter `updated_at` 을 mtime 으로 교체. git checkout/pull/restore 는 **내용이 같아도 mtime 을 바꾸므로** 전량 오탐 — 2026-07-03 실사고(200+ 파일 일괄 변조)의 원인.

## 수정 계획

1. **내용 비교 게이트 추가**: mtime 이 앞서도 write-back 전에 파싱 결과(또는 본문 해시)를 DB 캐시와 비교 — **동일하면 updated_at 을 건드리지 않고 cached_mtime 만 갱신**(다음 sync 재감지 방지). 비교 대상: title/description/urgency/status/parent/prereq/tags/deleted + 본문. 이미 parse 를 하고 있으므로 추가 비용은 필드 비교뿐.
2. **대량 보정 안전장치**: 한 번의 sync 에서 write-back 대상이 전체의 N%(예 50%) 이상이면 의심 신호 — stderr 경고 + (정책 결정: 진행 vs 스킵). 1번이 있으면 발동할 일이 거의 없지만 방어선.
3. 캠페인/rules 등 다른 cached 엔티티(DEV-178)도 같은 게이트 적용 여부 점검.
4. 회귀 테스트: "파일 touch(내용 동일) 후 sync → updated_at 불변 + cached_mtime 갱신" / "실제 내용 변경 후 sync → updated_at = mtime" 두 케이스.

**변경 파일**: core/src/incremental.rs (판정/write-back 경로), 테스트 동파일. 예상 규모: 중형.
