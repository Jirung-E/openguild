[계획] 구현 계획 (2026-07-03 작성)

**변경 파일**: `core/src/replay.rs` (replay_to 진입부) — CLI/HTTP 양쪽이 공유하는 core 에서 처리해야 두 경로 다 보호됨.

1. `replay_to` 시작 시: `journal::count > 0` 이면 **restore 진행 전에 `snapshot::create_snapshot(store)` 호출** — 현재 상태를 정식 백업 목록에 남김. (create_snapshot 자체가 journal truncate 하므로, 이후 replay 는 "방금 만든 최신 스냅샷 + 빈 journal" 위에서 동작 — 시맨틱 확인 필요 ⚠️: replay 대상 journal 이 truncate 되면 안 됨!)

   ⚠️ **핵심 설계 이슈**: 자동 백업(create_snapshot)이 journal 을 비워버리면 정작 replay 할 op 가 사라진다. 해결 — 순서 재구성:
   (a) journal ops 를 **메모리에 먼저 적재** (replay_to 는 이미 1단계에서 이걸 함 — 그 직후로 스냅샷 삽입), 그 다음
   (b) 현재 상태 스냅샷 생성(journal truncate 무해 — ops 는 이미 메모리에),
   (c) 그 스냅샷이 아니라 **직전 최신 스냅샷** 기준으로 restore + 메모리 ops 재적용... ⚠️ 그런데 (b)의 스냅샷이 이제 "최신"이 되어 restore 대상 선택이 꼬임 — replay_to 시그니처가 이미 snapshot 인자를 받으므로 호출자가 (b) 이전에 최신 스냅샷을 캡처해 넘기면 해결. CLI/HTTP 핸들러의 list_snapshots 시점만 (b) 앞으로 이동.
2. 자동 백업 시 stderr/응답에 안내: "복원 전 상태를 스냅샷 <ts> 로 백업함 — 되돌리려면 restore --to <ts>".
3. journal 비어있으면 스킵(멱등, 잃을 것 없음).
4. 테스트: replay 테스트에 "restore 후 backup list 에 사전 스냅샷 존재 + 그 스냅샷으로 --to 복귀 시 원상태" 케이스 추가.

핵심 난점이 1번 순서 문제라 구현 시 여기부터 검증할 것.
