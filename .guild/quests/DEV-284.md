DB 투영 불변식(BOOK-001) 구현 — 역류 경로 A3.

reindex 의 attachment blob 복원(`sync_attachment_blobs`, DEV-069)이 참조된
첨부 파일이 없으면 blob 에서 파일을 되살린다. "실수 삭제 복구" 라는 정당한
의도지만, 브랜치 전환으로 그 첨부가 없는 브랜치에 있을 때 자동 부활이
발산을 만들 수 있음.

## 수정 방향
자동 복원이 브랜치 전환과 충돌하는지 검증하고, 필요하면 현재 브랜치 실존
참조로 게이트하거나 명시적(사용자 호출) 복원으로 전환. A1/A2 보다 우선순위 낮음.

## 조사 결과 (2026-07-27)

먼저 실제 위험도를 확인했다:

- `sync_attachment_blobs` 의 **호출자는 reindex 하나뿐**이고, reindex 는
  테이블을 현재 브랜치 파일에서 재구축한 **뒤에** 호출한다.
- `.guild/attachments/*` 는 **git-tracked** 다(`git ls-files` 확인).

그래서 지금 당장 유령 부활이 나지는 않는다 — 브랜치 전환 시 파일도 함께
사라지고, 재구축된 테이블에 참조가 없으니 blob 은 복원 대신 GC 된다.

**문제는 그 정합성이 "호출 순서"에 의존한다는 것.** 판정 함수
`attachment_referenced` 는 (a) 사이드카 파일 스캔(파일 기반, 안전) + (b)
`quests`/`campaigns`/`library_docs` **테이블 본문 LIKE 쿼리**(index.db → branch-blind)
로 되어 있었다. reindex 밖에서 부르는 경로가 하나라도 생기면(수리 명령, GUI
시동 sync 등) 다른 브랜치의 캐시 본문이 "참조 중"으로 잡혀 현재 브랜치에 없는
첨부를 되살린다. BOOK-001 이 경고하는 잠재 사고 그대로다.

## 수정

판정을 **파일만** 보도록 바꿨다 — `referenced_attachments()` 가 본문 `.md` 와
첨부 사이드카를 한 번 훑어 참조된 `attachments/...` 경로 집합을 만든다.
정합성이 호출 순서에 의존하지 않는다.

부수 효과로 비용도 줄었다: orphan blob 개수 × (디렉토리 스캔 + 3개 LIKE 쿼리)
→ 디스크 1회 패스 + HashSet 조회.

기존 `attachment_referenced` 는 `#[allow(dead_code)]` 로 남겨 참고용으로만 뒀다
(자동 복원 자체는 BUG-087 의 "참조 중인 것만 복원" 정책 그대로 유지 —
스냅샷 복원 후 파일 소실 회복이라는 정당한 용도가 있다).

## Test plan

1. 첨부가 있는 퀘스트를 만든 뒤 `.guild/attachments/` 의 파일을 지우고
   reindex → 복원되는지(정당한 self-heal 유지).
2. 사이드카/본문에서 참조를 제거한 뒤 파일도 지우고 reindex → **복원되지 않고**
   blob 이 GC 되는지.
3. 브랜치 전환(첨부가 없는 브랜치)에서 reindex → `.guild/attachments/` 에
   untracked 파일이 생기지 않는지(`git status` 확인).
4. 본문 인라인 참조(`![](attachments/xxx.png)`)만 있고 사이드카가 없는 경우도
   복원 대상으로 잡히는지 — 이번에 판정 소스가 테이블에서 파일로 바뀐 지점.
