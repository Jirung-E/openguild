## 증상

`cargo test -p openguild-core` 가 간헐적으로 실패한다. 실패하는 테스트는
그때그때 다르고(`guild_file::resolve_guild_ref_resolves_by_name_from_recents`,
`snapshot::restore_snapshot_restores_index_db` 등) 재현이 어렵다.
머신이 바쁠수록(다른 앱 실행 중) 잦아진다.

빈도는 대략 수십 회에 1회.

## 원인 (코드로 확인)

env 를 건드리는 테스트가 **네 파일**에 흩어져 있는데, 잠금이 제각각이다.

| 파일 | 건드리는 env | 잠금 |
|------|--------------|------|
| `recents.rs` | `OPENGUILD_RECENTS_DIR` | 자체 `OnceLock<Mutex>` |
| `user_dirs.rs` | `OPENGUILD_HOME` | **다른** `static Mutex` |
| `locale.rs` | `OPENGUILD_HOME` / `OPENGUILD_LOCALE` | **또 다른** `static Mutex` |
| `snapshot.rs` | `OPENGUILD_AUTO_BACKUP_*` | **없음** |

파일 **안**에서는 직렬화되지만 파일 **사이**에서는 자유롭게 겹친다. 즉
`locale` 이 `OPENGUILD_HOME` 을 세우는 동안 `recents` 테스트가 env 를 읽는
창이 실제로 존재한다.

`std::env::set_var` / `remove_var` 는 프로세스 전역에 즉시 반영되고,
다른 스레드가 `getenv` 하는 중이면 **정의되지 않은 동작**이다 — 그래서 최신
Rust 에서 `unsafe` 다. `cargo test` 는 기본이 병렬이라 정확히 그 조건이다.

`snapshot.rs` 의 주석은 "테스트 단일 스레드" 라고 적혀 있었는데 사실이 아니다.

## 수정

`core/src/test_env.rs` 신설 — env 를 건드리는 **모든** 테스트가 공유하는 잠금
하나. 네 파일이 전부 이걸 쓴다.

server 는 별도 테스트 프로세스이고 자체 GUARD 가 있어 대상이 아니다(env 는
프로세스별이라 크레이트 간 간섭이 없다).

## 검증의 한계 — 정직하게

**재현에 실패했다.** 수정 후 20회, 수정 전 상태로 되돌려서도 20회 — 둘 다
전부 통과했다. 빈도가 낮아 이 횟수로는 차이를 가릴 수 없다.

따라서 **"이 수정이 그 실패를 없앴다" 고 말할 수 없다.** 말할 수 있는 것은:

- 파일 간 env 레이스가 **코드상 실재한다**(위 표).
- 잠금 없는 `set_var` 를 병렬 테스트에서 부르는 것은 정의되지 않은 동작이라,
  관측된 실패와 무관하더라도 고쳐야 할 상태다.
- 관측된 실패들이 전부 **전역 자원(env / 임시 경로)** 을 쓰는 테스트였다는
  점은 이 가설과 일관된다.

다른 원인이 남아 있을 수 있다. 재발하면 이 퀘스트에 이어 기록한다.
