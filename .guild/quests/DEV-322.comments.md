## 1) 대기 목록

`AttachProgress`(현재 파일 하나) → `AttachQueueItem[]`(고른 파일 전체).
파일을 고르는 즉시 전체 목록이 `대기` 상태로 뜨고, 각 줄이 자기 상태를
들고 있다: 대기 / 진행(진행률 바) / 완료(✓) / 실패(✕ + 사유).

- 실패가 하나라도 있으면 **목록을 걷지 않는다**. 배너 한 줄로는 여러 개 중
  무엇이 실패했는지 알 수 없기 때문. 전부 성공하면 기존처럼 사라진다.
- 목록은 `max-height: 11rem` + 자체 스크롤 — 많이 골라도 섹션이 늘어나지 않게.
- 파일명/진행 바 2단 유지(BUG-190).

## 2) 병렬 업로드 — 실측 후 도입

실측(로컬, scratch 길드 전용 서버 8812. 실제 길드는 건드리지 않음):

**HTTP bytes 경로** (브라우저)

| 케이스 | 순차 | 병렬 | 차이 |
|---|---|---|---|
| 8개 x 2MB | 171 ms | 153 ms | 병렬 10.3% 빠름 |
| 4개 x 8MB | 210 ms | 191 ms | 병렬 9.0% 빠름 |
| 2개 x 32MB | 486 ms | 369 ms | 병렬 24.0% 빠름 |

**디스크 복사 경로** (데스크톱 `save_attachment_from_path` 성격)

| 케이스 | 순차 | 병렬 | 차이 |
|---|---|---|---|
| 8개 x 2MB | 12 ms | 6 ms | 병렬 51.6% 빠름 |
| 4개 x 8MB | 17 ms | 9 ms | 병렬 44.0% 빠름 |
| 2개 x 32MB | 20 ms | 14 ms | 병렬 27.7% 빠름 |

느려지는 케이스는 없었다. 그래서 도입하되 **환경별로 동시성을 다르게** 뒀다:

- **데스크톱 3개**: Rust 가 4MiB 버퍼로 스트리밍 복사해 파일 크기와 무관하게
  메모리가 상수다.
- **브라우저 1개(순차 유지)**: bytes 경로는 파일을 통째로 읽어 base64(약 1.33배)
  로 만든다. 동시에 돌리면 그만큼 메모리가 배로 늘어난다 — BUG-168 이 1.5GB
  첨부였던 걸 생각하면 여기서 동시성을 올리는 건 위험을 사는 것이다.

또 하나: 업로드는 병렬이어도 **등록(onOne)은 직렬화**했다. 첨부 목록 sidecar
를 read-modify-write 하므로 동시에 부르면 lost update 가 난다.
