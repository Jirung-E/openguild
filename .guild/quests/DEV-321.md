﻿DEV-298 은 "돌고 있는지"만 알려주는 불확정 바로 마무리했다. 근거는 "세 전송 경로 모두 진행률을 관측할 수 없다" 였는데, BUG-188 이후 전제가 달라졌다 — 실제 %를 낼 수 있다.

## 왜 이제 가능한가
- **데스크탑(경로 기반)**: BUG-188 에서 저장이 Rust 의 `std::fs::copy` 로 바뀌었다. 이걸 버퍼 단위 복사 루프로 만들면 매 청크마다 (복사 바이트 / 전체 바이트) 를 알 수 있다. Tauri 이벤트로 흘리면 진짜 %.
- **브라우저(서버) 모드 + 원격 연결 데스크탑**: `fetch` 는 업로드 진행률을 주지 않는다(다운로드만). 첨부 POST 하나만 `XMLHttpRequest` 로 보내면 `upload.onprogress` 로 전송 바이트를 관측할 수 있다. 서버/프로토콜 변경 없음.

즉 DEV-298 이 후속으로 미뤄둔 "청크 업로드 API(init/append/finish)" 없이 해결된다.

## 작업
- core: `save_attachment_from_file` 에 진행 콜백 — 청크 복사 루프. core 는 Tauri 를 모르게 유지(콜백만 받는다).
- gui(Rust): 커맨드가 콜백에서 진행 이벤트 emit. 폭주 방지로 throttle.
- 프론트: 경로 업로드는 이벤트 구독 → %, bytes 업로드는 XHR → %. 진행 바를 결정형으로 전환.
- bytes 경로는 전송 **전에** base64 변환 구간이 있어 그때는 %가 없다 — '준비 중' 으로 따로 표시해 0% 정지처럼 보이지 않게.

## 검증
- 대용량(수백 MB) 파일에서 %가 실제로 올라가는지, 완료 시 100%로 끝나는지.
- 여러 개 선택 시 파일별로 0→100 이 반복되는지(순번 표시와 함께).
- 브라우저 모드에서도 %가 나오는지.
- 데스크탑 청크 복사가 `fs::copy` 대비 눈에 띄게 느리지 않은지(느리면 작은 파일은 기존 경로 유지).
