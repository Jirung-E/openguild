## 배경

[[DEV-367]] 에서 catch-panic 계층을 얹은 뒤, "덮이지 않는 곳" 두 군데를
실제로 패닉시켜 확인했다. 둘 다 **조용한 실패**로 이어진다.

## 1. spawn 된 태스크의 패닉 — HTTP 200 에 잘린 본문

첨부 zip 스트리밍(`stream_attachments_zip`)은 `tokio::spawn` 된 태스크에서
zip 을 쓰고, 응답 본문은 duplex reader 를 흘려보낸다. 그 태스크가 패닉하면
**catch-panic 계층을 아예 거치지 않는다** — 별도 태스크이기 때문이다.

첫 항목을 쓴 뒤 패닉시켜 실측:

| | 정상 | 패닉 |
|---|------|------|
| HTTP | 200 | **200** |
| 크기 | 9,601 | 6,180 |
| curl 종료 코드 | 0 | **0** (성공으로 봄) |
| `handler panicked` 로그 | — | **0건** |
| unzip | 2 files | `cannot find zipfile directory` |

즉 **클라이언트는 성공했다고 믿고 깨진 zip 을 저장한다.** 사용자는 압축을
풀 때서야 알게 되고, 그때는 원인을 되짚을 단서가 없다.

원인은 writer 가 drop 되면 duplex 가 그냥 EOF 로 끝나, 응답 본문이 **정상
종료**로 보인다는 것이다. chunked 종료자가 정상적으로 나가므로 HTTP 수준에서
오류가 없다.

### 고칠 방향

`tokio::spawn` 의 `JoinHandle` 을 본문 스트림 쪽에서 지켜보다가, 태스크가
비정상 종료(`is_panic()`)면 스트림을 **에러로** 끝낸다. 그러면 hyper 가
chunked 를 비정상 종료해 클라이언트가 전송 실패를 감지한다.

`ReaderStream` 을 감싸는 얇은 스트림으로 충분해 보이지만, 순서(본문을 다 흘린
뒤 join 상태 확인)와 취소 처리를 같이 봐야 한다.

## 2. Tauri 커맨드의 패닉 — invoke 가 영영 안 끝난다

임시 커맨드를 패닉시키고 프런트에서 `invoke` 한 결과를 파일로 기록해 실측:

```
--- probe 시작 ---
rejected after 5042ms: Error: TIMEOUT 5s     ← 내가 건 5초 타임아웃
패닉 후 list_rules 성공 — 앱 살아있음
--- probe 끝 ---
```

**거부되지 않는다. 응답 자체가 오지 않는다.** 앱과 다른 커맨드는 멀쩡하다.

이게 서버보다 나쁘다. 서버는 이제 500 이라도 주지만, 데스크톱은 promise 가
pending 으로 남아 **UI 가 로딩 상태로 굳는다.** 예컨대 강화 검색에서
`search_docs` 가 패닉하면 `wideLoading` 이 영영 true — 토글은 계속 깜빡이고
결과는 오지 않으며, 에러 배너도 뜨지 않는다.

GUI 쪽엔 패닉 훅도 `catch_unwind` 도 없다.

### 고칠 방향

- 커맨드 실행부를 감싸 패닉을 `Err(String)` 으로 바꾼다. 커맨드 수가 많으므로
  매크로나 공통 래퍼가 필요하다.
- 또는 프런트의 `TauriTransport.call` 에 타임아웃을 둔다 — 근본 대책은
  아니지만 UI 가 굳는 것은 막는다.
- 최소한 `std::panic::set_hook` 으로 로그를 남긴다. 지금은 stderr 뿐이라
  패키징된 앱에서는 사실상 사라진다.

## 참고

DEV-367 커밋의 주석에 "헤더 전송 후 패닉은 연결 끊김" 이라고 적었는데
**틀렸다** — 실측 결과 연결은 정상 종료되고 200 으로 나간다. 그 주석은
이 퀘스트를 등록하며 정정했다.
