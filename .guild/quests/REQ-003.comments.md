## 전제 정정 — `lock.rs` 는 이 문제를 못 막는다

퀘스트는 "근본 원인 — lock.rs 가 아무도 안 쓴다" 로 잡았는데, **채택해도 여기
든 사례들은 해결되지 않는다.**

`LockGuard` 는 `.guild/.lock` 에 PID 를 적는 **프로세스 간** 락이다. 그런데
퀘스트가 든 재현 사례는 전부 **한 프로세스 안**의 동시 요청이다(서버가 요청
두 개를 처리, GUI 가 커맨드 두 개를 처리). 같은 PID 로 두 번 획득하려 하면
`is_pid_alive(자기 자신)` 이 참이라 **스스로를 거부한다**.

그래서 in-process 뮤텍스를 도입했다. `lock.rs` 는 손대지 않았고 여전히
사용처가 0이다 — CLI ↔ 앱 동시 실행 같은 프로세스 **간** 보호는 별개 문제로
남는다(그걸 채택하면 앱을 켜둔 채 CLI 를 쓰는 지금 워크플로가 막히므로 별도
판단이 필요하다).

## 수정

### 1. `change_status` 가 삭제된 퀘스트를 건드리던 문제 (단독 버그)

`UPDATE ... WHERE id = ?` 에 `AND deleted_at IS NULL` 을 넣었다. 예전엔 행을
실제로 고친 뒤 `fetch_by_id`(필터 있음)가 NotFound 를 내, **데이터는 바뀌었는데
호출자에겐 "없음"** 이라고 답했다.

테스트 2건. 수정 전 코드로 되돌려 `assertion failed: status 가 바뀌었다` 로
실패하는 것을 확인했다.

### 2. 프로세스 내 직렬화 — `Store::write_lock`

read-modify-write 경로 **19곳**에 걸었다.

| 대상 | 곳 |
|------|-----|
| 퀘스트 댓글 (add/update/delete/reaction/discussion/resolved/pinned) | 7 |
| 캠페인 댓글 (add/update/delete/reaction/pinned) | 5 |
| 캠페인 체크리스트 (add/set/remove) | 3 |
| 첨부 (공용 add/remove) | 2 |
| 도서관 번호 할당 → 본체 쓰기 | 1 |
| 타입 카운터 파일 | 1 |

재진입 데드락이 없는지 스크립트로 전수 확인했다(잠금 함수 17개 × 상호 호출).
걸린 3건은 동명이인 `svc::add_entry`(동기 서비스) 오탐이었다.

`add_attachment` 은 **메타 JSON 갱신만** 감싼다 — 대용량 파일 복사
(`save_attachment_from_file`)는 잠금 밖이라 1.5GB 업로드가 댓글 토글을 막지
않는다.

### 3. rules self-heal 이 동시 저장을 덮어쓰던 문제

`parse_backfilled` 는 **읽기 경로**에서 불리는데 넘겨받은 `raw` 스냅샷을
그대로 되썼다. 그 사이 사용자가 저장했으면 그 내용이 사라진다.

쓰기 직전에 파일을 **다시 읽어** 최신 본문에 frontmatter 만 얹도록 바꿨다.
`parse_backfilled` 가 sync 라 async 잠금을 못 써서 이 방식을 택했다 — 완전한
원자성은 아니지만 "오래된 본문을 되쓰는" 주 경로가 사라진다.

## 검증 — lost update 가 실재함을 확인

동시 12건 댓글 추가 테스트(`multi_thread`, 4 worker).

| | 결과 |
|---|------|
| 잠금 있음 | **12/12** 보존, id 중복 0 |
| 잠금 제거 (3회) | **4 / 5 / 4** 만 생존 |

즉 지적된 lost update 는 이론이 아니라 재현되는 결함이었고, 잠금이 막는다.
