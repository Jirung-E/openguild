길드에 연결된 프로젝트용 knowledge base(프로젝트 참고문서/노트/결정 — 태스크가 아닌 지식) 추가 검토. 현재 .guild 는 quests(태스크) + rules(가이드라인)만. KB 는 .guild/kb/{slug}.md 경량 위키(파일 진리원, git tracked, GUI 에서 열람/편집, cross-link 자동완성 재사용)로 quests/rules 와 구분. 고려: rules 메커니즘 일반화 vs 별도, 위키 scope creep 경계, 프로젝트 repo 의 docs/ 와 중복 여부. 우선순위 낮음(post-1.0 백로그). 설계 논의 필요.

## 결정 — "도서관(Library)" 으로 명명, 별도 메커니즘 (2026-06-28)

[DEV-097](DEV-097.md)(글로벌 첨부파일) 토론에서 admin 이 거의 동일한 요구를
다른 각도로 제기 — 두 퀘스트가 사실상 같은 기능임이 드러남:

> '글로벌 첨부파일'의 주 목적은 기획문서나 앱/도구 등 여러곳에서 반복적으로
> 참조될 수 있는 파일을 중복저장 하지 않기 위한것이였다. 이건 '라이브러리'
> 개념과 비슷한것이고, '도서관'은 이 프로젝트의 컨셉과도 잘 어울린다.
>
> '도서관'은 '길드 규칙'과 비슷하게 별도 페이지에서 관리되도록 해야하고,
> 사용자는 어떤 편집창에서라도 도서관에 있는 문서를 링크할 수 있다(퀘스트/
> 캠페인 링크와 동일한 방식). 이를 위해 도서관의 문서에도 별도 관리번호가
> 부여되어야 한다.

이로써 (a) rules 일반화 vs 별도 — **별도**로 결정. rules 는 slug 만으로
식별되는 가이드라인 문서(번호 없음)인 반면, 도서관 문서는 **quest/campaign
과 동일하게 자체 관리번호가 부여**되고 본문 어디서든(quest/campaign 본문
편집기 포함) `@`/링크 자동완성으로 참조 가능해야 한다는 점에서 rules 와
근본적으로 다른 식별/참조 모델 — 일반화보다 별도 메커니즘이 맞음.
(b) docs/ 중복 — 프로젝트 repo 의 docs/ 는 개발자용 기술 문서, 도서관은
길드 데이터(.guild/) 의 일부로 비개발자도 GUI 에서 바로 쓰는 참고자료 —
경계는 유지.

**범위(초안, 후속 설계 필요)**:
- 저장: `.guild/library/{ID}.md` (quests 와 같은 파일 진리원 패턴).
- ID: 독립 prefix(예: `LIB-001`) 또는 quest_types 와 별개의 자체 카운터.
- 관리 페이지: rules 와 유사한 GUI 목록/편집 페이지(별도 route).
- 참조: quest/campaign 본문 편집기의 cross-link 자동완성에 도서관 문서도
  포함(기존 quest/campaign 링크 메커니즘 확장).
- [DEV-097](DEV-097.md) 의 "글로벌 첨부파일"은 **폐기** — 도서관 문서 링크로
  대체. "로컬 첨부파일"(quest 전용)은 DEV-097 범위로 현행 유지.

**아직 구현 안 됨** — 위 결정을 토대로 별도 설계/구현 세션 필요(core 스키마
+ ID 카운터, server/cli CRUD, GUI 관리 페이지, 링크 자동완성 확장 — 여러
크레이트에 걸친 신규 기능이라 이 퀘스트 하나로는 부족, sub-quest 분리 권장).
