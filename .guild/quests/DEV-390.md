## 질문

admin: *"길드에서 '플러그인의 접근권한'을 설정할 수 있어야 하지 않을지? 현재는
이벤트 구독이 전부이므로 read권한만 있으면 될거같긴 한데, 혹시 몰라서. 물론
그래봤자 외부 프로그램으로 직접 조작하는건 막지 못하기 때문에 cli/gui에서는
의미가 없고, server에서만 의미가 있어보임."*

## admin 의 진단은 맞다 — cli/gui 에서는 의미가 없다

`run` 은 **사용자 권한으로** 프로그램을 띄운다. 그 프로그램은 이미
`openguild quest delete` 를 부를 수도 있고 `.guild/*.md` 를 직접 고칠 수도
있다. 이벤트 페이로드에 무엇을 담을지 조이는 것은 그 프로그램을 **한 톨도**
제약하지 못한다.

cli/gui 의 실제 경계는 권한이 아니라 **동의**다 — "돌린다 / 안 돌린다" 뿐이고,
그건 이미 있다([[DEV-375]]).

## 그런데 server 에서도 read/write 는 축이 틀렸다

server 가 다른 점은 셋이다.

1. 플러그인이 **서버 프로세스 권한**으로 돈다. 변경을 일으킨 사람이 아니라.
2. `scope: server` 는 **그 서버를 쓰는 모두**에게 적용된다.
3. 정의는 **git 으로 온다** — 푸시할 수 있는 사람이 서버에서 도는 코드를 정한다.

그런데 서버에서도 `run` 은 여전히 임의 코드 실행이다. 그러니 "read 권한만
준다" 는 `run` 이 존재하는 한 아무것도 못 막는다. **read/write 는 지금 없는
문을 지키는 자물쇠다** — 플러그인이 길드로 되돌아 쓰는 경로 자체가 없다.

의미가 있는 축은 read/write 가 아니라 **무엇이 밖으로 나가는가**다.

| 축 | 강제 가능한가 | 왜 |
|---|---|---|
| **채널** — 이 서버에서 `run` 을 허용할 것인가 | 예 | 적재에서 거른다 |
| **행선지** — `post` 가 어디로 보낼 수 있나 | 예 | url 을 코어가 안다 |
| **내용** — 어떤 이벤트/필드를 볼 수 있나 | 예 | 페이로드를 코어가 만든다 |
| read / write | 무의미 | 되돌아 쓰는 경로가 없다 |

## 제일 큰 구멍은 `run` 이 아니라 `post` 일 수 있다

`run` 은 무섭게 생겼고 동의 화면에서 눈에 띈다. `post` 는 안 그런데,
**공유 서버에 걸린 `post` 플러그인 하나면 모든 퀘스트·댓글 본문이 임의의
주소로 조용히 나간다.** 소리도 안 나고 흔적도 서버 로그뿐이다.

그래서 하나만 만든다면 우선순위는 **server scope `post` 의 행선지 허용목록**
이지 read/write 권한이 아니다.

## 정책은 길드 안에 두면 안 된다

가장 중요한 함정이다. 정책을 `.guild/` 에 두면 **git 으로 따라온다** —
푸시할 수 있는 사람이 정책도 고칠 수 있으니 정책이 아니다. 동의가 길드 밖에
사는 것과 정확히 같은 이유다.

두려면 서버 기계에 둔다 — `~/.openguild/server-policy.json` 같은 자리.

```json
{ "allow_run": false,
  "post_hosts": ["hooks.slack.com", "api.telegram.org"] }
```

## 지금 이미 있는 통제

서버에서도 동의는 **그 기계**에 남는다. 서버를 띄우는 사람이 그 기계에서
`openguild plugin allow` 를 해야 한다([[DEV-373]] 의 "서버 동의는 HTTP 로 안
받는다"). 거칠지만(플러그인 단위 all-or-nothing) 실재하는 문이다.

그러니 질문은 "통제가 없다" 가 아니라 **"거친 문 하나로 충분한가"** 다.

## 권고

**지금은 권한 체계를 안 만든다.** 지킬 문이 아직 없고, 만들면 "권한이 있으니
안전하다" 는 잘못된 안심을 준다.

대신 순서를 이렇게 본다.

1. 실제로 공유 서버를 쓰기 시작하면 → `server-policy.json` 의 `allow_run` 과
   `post_hosts` 둘만. 작고, 강제 가능하고, 실제 위협에 정확히 대응한다.
2. **플러그인이 길드로 되돌아 쓰는 경로가 생기는 순간** — 예컨대 "이벤트를
   받고 댓글을 단다" — 그때 write 권한이 처음으로 의미를 갖는다. 그 기능을
   설계할 때 **함께** 설계한다. 나중에 얹으면 기본값이 전부 열린 채로 굳는다.

이 결정을 뒤집을 신호: 공유 서버에서 여러 사람이 플러그인을 올리기 시작하거나,
`run` 을 서버에서 실제로 쓰기 시작하는 것.
