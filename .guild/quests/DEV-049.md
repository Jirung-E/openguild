DEV-042 와 동일 부류의 **더 근본적인** 버그. `quests.id` 가 파일 정렬 순으로
부여돼서 quest 추가 / 삭제 / 이름 변경 시 모든 id 가 시프트됨. `.md` 에
저장 안 되는 캐시 테이블 (`quest_history`, `quest_positions`) 의 FK 가
깨짐. reindex 는 .md frontmatter 로 `quest_dependencies` 를 재구축하지만
이 두 테이블은 보존 안 됨.

이미 DEV-042 작업 중 직접 겪었던 그 문제:
> "quest_history 행 39 건은 backup → restore 시도했으나 reindex 가
>  quest_id 를 재할당하여 매핑 깨짐 → 결국 일괄 삭제."

## 구현 (2026-05-22)

### Schema (migration 0007)
- `quest_history.quest_slug TEXT` + `idx_quest_history_slug_ts`.
- `quest_positions.quest_slug TEXT` + `idx_quest_positions_slug`.
- 기존 행: `JOIN quests` 로 현재 id → slug 도출하여 백필 (이 시점엔 id 매핑 OK).
- 기존 `quest_id` 컬럼은 유지 (호환 + reindex 시 새 id 로 갱신).

### Reindex 동작
- 0 단계 position_backup 그대로 (JOIN 기반 slug 도출).
- 5b 단계 position 복원 시 `quest_slug` 컬럼도 함께 INSERT.
- **5c 단계 신설**: reindex 끝에 `quest_history` 의 `quest_id` 컬럼을
  `quest_slug` 기준으로 새 id 로 일괄 갱신. 슬러그가 reindex 후 살아남은
  quest 만 매핑. slug 가 없어진 quest 의 history 는 quest_id 가 null/stale
  로 남되, 호출 측이 join 으로 자연스럽게 필터됨.

### INSERT 사이트
- `core::ops::quests::change_status` — `INSERT INTO quest_history (quest_id,
  quest_slug, ts, op, old_value, new_value) VALUES (...)`. `quest.quest_id`
  (slug) 를 함께 bind.
- `core::services::quests::update_position` — SELECT 으로 slug 조회 후
  `INSERT ... (quest_id, quest_slug, x, y)` + `ON CONFLICT` 시 quest_slug 도
  갱신.

### SELECT 사이트
- `list_history`: `SELECT id, quest_id, quest_slug, ts, op, old_value, new_value, actor`.
- `list_positions`: `SELECT p.quest_id, p.quest_slug, p.x, p.y`.
- `fetch_relations`: `SELECT quest_id, quest_slug, x, y` for position.

### Model / Frontend
- `core::models::QuestHistoryEntry.quest_slug: Option<String>` (`#[serde(default,
  skip_serializing_if = "Option::is_none")]` — 호환).
- `core::models::QuestPosition.quest_slug: Option<String>` 동일.
- frontend `QuestHistoryEntry` / `QuestPosition` 타입에도 `quest_slug?: string | null`.

## 자동 테스트 +3

- `reindex::tests::reindex_preserves_history_and_position_across_id_shift`
  (core): DEV-001 만 있는 상태에서 history / position INSERT → BUG-001 추가
  reindex → DEV-001 의 id 가 실제로 시프트되고 (assert_ne!), 그래도 history /
  position 의 `quest_id` 가 새 id 로 갱신 + `quest_slug` 는 유지.
- `test_history_row_has_quest_slug` (server): 새 history 응답에 quest_slug
  필드 존재.
- `test_position_row_has_quest_slug` (server): 새 position 응답에 quest_slug
  필드 존재.

## 회귀

- 기존 `quest_id` 컬럼은 유지 → 기존 API consumer 호환.
- reindex 가 `quest_id` 를 자동 갱신하므로 id-based join 도 정상.
- frontend / GUI 화면 변경 없음 — 타입만 확장.
