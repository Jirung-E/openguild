## 왜 먼저인가

**되돌리기가 가장 어렵다.** 플러그인이 이름을 구독하기 시작하면 그것이 계약이
된다. 나머지 서브퀘스트는 나중에 바꿔도 되지만 이건 아니다.

## 이벤트를 우리가 정의한다

`ops` 가 `emit` 으로 직접 낸다([[DEV-373]] 참고 — journal 훔쳐보기를 접은
이유). 내부 함수명을 그대로 노출하지 않는다. 지금 journal 의 `op` 51종은
공개 계약으로 못 쓴다:

```
add_attachment      vs  campaign_checklist_add    ← 동사 위치가 반대
add_comment_entry   vs  add_campaign_comment      ← 한쪽만 "entry"
save_attachment     vs  add_attachment            ← 다른 일인데 구분 안 됨
set_comments / set_rules                          ← 파일 일괄 쓰기(내부 사정)
toggle_comment_resolved                           ← 해결/해제를 못 가름
```

특히 `toggle_*` 6종. "댓글이 해결됨"을 구독하고 싶은데 **해제까지 잡힌다.**

## 할 것

**1. 이벤트 카탈로그 — `리소스.동사`**

```
quest.created · quest.updated · quest.deleted · quest.restored
quest.status_changed · quest.tags_changed · quest.due_changed
comment.added · comment.updated · comment.deleted
comment.resolved · comment.unresolved · comment.pinned · comment.unpinned
campaign.* · book.* · rule.* · attachment.*
```

`toggle_*` 은 **양쪽으로 갈라서** 낸다. 내부 함수와 1:1 일 필요가 없다 —
그게 우리가 정의하는 이유다.

**2. 단계 — `pre` / `post`**

```
{ "on": ["quest.created"],        // 기본 post
  "on": ["pre:quest.created"] }   // 관찰 pre
```

**pre 는 관찰만 한다.** 거부(veto)는 하지 않는다 — 훅이 죽으면 길드가 멈춘다.
pre 는 mutation 직전 상태를, post 는 결과를 본다.

**3. 실패는 결과 필드로**

이벤트를 늘리지 않고 인자만 는다:

```json
{ "event": "quest.created", "phase": "post",
  "ok": false, "error": "타입 DEV 가 없습니다" }
```

성공만 원하는 스크립트는 `event.ok` 를 보면 되고, 실패만 구독하는 것도 같은
이름으로 된다. 실패 경로에도 emit 이 필요하므로 **호출 지점이 늘어난다** —
1단계에서 어디까지 덮을지는 구현하며 정한다.

**4. 페이로드 래핑 — 이름만 계약이 아니다**

내부 구조체를 그대로 흘리면 필드를 바꿀 때 플러그인이 깨진다. 한 겹 감싼다:

```json
{ "event": "comment.resolved", "phase": "post", "ok": true,
  "ts": "2026-09-07T…+09:00", "guild": "openguild",
  "quest":   { "id": "DEV-007", "title": "…", "status": "in_progress" },
  "comment": { "id": 3, "author": "…", "discussion": true } }
```

**5. 와일드카드** — `quest.*`, `*.created`, `pre:quest.*`. 51종(앞으로 더 늘)을
일일이 쓰게 하면 플러그인 작성이 고통스럽고, 새 이벤트가 생겨도 기존 구독자가
못 받는다.

**6. 누락 검사** — 새 mutation 에 emit 을 빠뜨리면 **조용히 구독 불가**가 된다.
`journal::append` 는 있는데 emit 이 없는 함수를 대조해 실패시킨다. journal 이
이미 54곳에 강제돼 있어 좋은 기준점이다.

의도적으로 안 내는 것(`set_comments` 같은 내부 일괄 쓰기)은 **이유와 함께**
명시적으로 제외한다 — 빠뜨린 것과 뺀 것을 구분한다.

## emit 지점 — 함수마다 고른다

`create_quest` 만 해도 6단계다:

```
journal → SQL insert → 파일 쓰기 → type counter → 부모 auto블록 → after_mutation
```

3번 뒤에 내면 4번이 실패해도 이미 나갔다. 맨 끝에 두면 조기 return(예:
`change_status` 의 no-op)과 부분 실패 허용(`sync_type_counter_file` 은 `?` 가
없다)을 각각 판단해야 한다. **이건 비용이지 결함이 아니다** — journal 방식은
이 선택지를 아예 안 준다.

**1단계에는 51종을 다 달지 않는다.** 실제로 노출할 이벤트부터 단다. 나중에
늘려도 플러그인 쪽에서는 "이벤트가 추가됐다" 로만 보인다.

## 구독자가 없으면 no-op

플러그인 설정이 없으면 이벤트를 **만들지도 않는다**. 그래야 기존 ops 테스트
429건이 부수효과를 안 갖고, 성능 부담도 없다.

## 테스트 방법

- 카탈로그의 모든 이벤트가 실제 emit 지점을 갖는다(양방향).
- 새 mutation 에 emit 을 안 넣으면 검사가 **실패**한다(되돌리기 시험).
- `toggle_comment_resolved` 가 `comment.resolved` / `comment.unresolved` 로
  갈린다.
- 와일드카드 — `quest.*` 가 `quest.created` 를 잡고 `comment.added` 는 안 잡는다.
  `pre:` 접두가 단계를 가른다.
- 실패한 mutation 이 `ok: false` + `error` 를 실은 이벤트를 낸다.
- 페이로드가 내부 구조체 변경에 안 흔들린다.
- **플러그인 설정이 없으면 emit 이 아무 일도 안 한다.**
