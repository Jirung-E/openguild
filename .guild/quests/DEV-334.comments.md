수정 — `minZoom: 0.25` 고정 → `computeMinZoom()` 으로 화면·내용에 맞춰 계산.

```
minZoom = clamp(  min(뷰포트W / 보드W, 뷰포트H / 보드H) * 0.7,  0.02,  0.25  )
```

- **전체가 들어오는 zoom 보다 30% 더** 축소할 수 있게 잡는다 — "전체 보기 +
  여유" 는 어떤 화면에서도 가능해야 한다.
- 상한을 기존 값(0.25)으로 둬서 넓은 화면에서 쓸데없이 깊게 축소되지 않게 하고,
  하한 0.02 는 안전장치.
- `syncLanes()` 에서 매번 다시 계산한다 — 상태(레인) 추가/삭제, 창 크기 변경,
  폰 회전이 전부 이 경로를 지난다.

## 가로만 보면 안 됐다

처음엔 레인 수 × 레인 폭으로 가로만 계산했는데, 실측해보니 **375px 화면의
제약은 세로**였다 — 보드가 6,504 x 17,364 (퀘스트 539건). 그래서 cy 가 있으면
실제 `boundingBox()` 로 계산하고, 최초 생성 시점처럼 아직 없으면 레인 폭으로
어림잡는 2단 구성으로 바꿨다.

## 측정 (rAF shim 적용, 실제 길드 539 노드)

| 화면 | 수정 전 minZoom | 수정 후 minZoom | fit 이 전체를 덮는가 |
|---|---|---|---|
| 375 x 812 | 0.25 | **0.0306** | ✅ |
| 750 x 1572 | 0.25 | **0.0634** | ✅ (fit 0.0882, 하한에 안 걸림) |

- 375px 에서 최대 축소 시 화면이 보드의 **가로 1.88배 / 세로 1.43배** 를 덮는다.
- 수정 전에는 375px 에서 `fit()` 조차 0.25 에서 잘려 레인 1.5개 분량만 보였다.

## 참고

화면을 키우면 minZoom 도 같이 올라가므로, 작은 화면에서 깊게 축소해둔 상태로
창을 키우면 현재 zoom 이 새 하한보다 낮은 채로 남는다. 다음 zoom 조작에서
자연히 보정되고 표시에는 문제가 없어 그대로 뒀다.
