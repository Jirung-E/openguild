구현 완료 — sibling(댓글/메모)과 캠페인 본문까지 증분 반영한다. 남은 부류는 DEV-311 로 분리했다(제목도 실제 범위로 좁혔다).

## 변경 (core/src/incremental.rs)
- `sync_changed_sibling_files` 신설: `{slug}.comments.md` / `.memo.md` (quest + campaign) 를 `file_mtime_cache` 기준으로 비교해 **그 파일만** 다시 파싱 → 소유자의 행 교체(DELETE + INSERT). 컬럼·의미는 reindex 의 5b'/6b 와 동일하게 유지.
- 파일이 사라진 sibling: 해당 행 삭제 + 캐시 row 제거. 캐시 row 를 지우지 않으면 매 열기마다 '사라진 파일' 로 다시 잡힌다.
- 소유 quest/campaign 이 index 에 없으면(고아 sibling) `needs_full_reindex` — 안전망.
- `sync_changed_campaign_files` 신설: 캠페인 본문의 외부 편집을 `refresh_campaign_if_stale` 의 재적재 로직으로 반영. **단 write-back 없이** — 자세한 이유는 아래.
- `sync_on_open` 순서: quest 본문 → 캠페인 본문 → sibling. 소유자 행이 먼저 최신이어야 그 소유자의 댓글도 같은 열기에서 반영된다.
- 모듈 doc 의 Scope 를 실제 범위로 갱신(정의 `*.toml` 은 의도적으로 full reindex 유지 — 상태 slug/타입 prefix 가 바뀌면 기존 행 해석 자체가 달라진다).

## 열기 경로에서 파일을 쓰지 않는다 (중요)
`refresh_campaign_if_stale` 은 외부 편집을 감지하면 frontmatter `updated_at` 을 파일 mtime 으로 write-back 한다. 이걸 그대로 열기 경로에 쓰면 **`git pull`/브랜치 전환처럼 mtime 만 바뀐 경우 캠페인 파일이 일괄 변조**된다 — 퀘스트 본문에서 실제로 터졌던 BUG-103(200+ 파일 updated_at 변조)의 캠페인판. 퀘스트 쪽은 내용 비교 가드로 막았지만 캠페인엔 그 가드가 없다.
그래서 내부 공통 함수에 `writeback` 플래그를 넣고, 열기 경로는 write-back 없이 행만 갱신한다(상세 진입은 사용자가 그 문서를 보는 시점이라 기존 동작 유지). 회귀 테스트로 고정: `open_path_does_not_rewrite_campaign_file` — 내용 그대로 재기록(mtime 만 변경) 후 열기, 파일 바이트가 동일한지 확인.

## 측정 (릴리스 빌드, 퀘스트 651개 / 캠페인 5개 실제 길드)
| 시나리오 | 이전 | 이후 |
|---|---|---|
| 댓글 파일 1건 외부 편집 | 전체 재색인 (약 4.1초) | **70ms** (`siblings=1 needs_full=false`) |
| 캠페인 본문 1건 외부 편집 | 전체 재색인 | **538ms** (`campaigns=1`) |
| 변화 없음 | 18ms | 27ms |

변화 없을 때 18→27ms 는 sibling/캠페인 목록 walk + 캐시 조회가 추가된 값이다.
캠페인 1건에 538ms 나 드는 이유는 링크 퀘스트 46건을 링크당 개별 문장(문장당 fsync)으로 재작성하기 때문 — 한 트랜잭션으로 묶는 건 DEV-311 에 적었다.
