## 코어가 소유하는 동작은 둘뿐

```
post   HTTP 로 이벤트를 보낸다        ← 1단계
run    프로세스를 띄우고 stdin 으로   ← 2단계
```

"밖으로 내보낸다"의 최소 완전집합이다. slack/discord/email 같은 통합을 코어에
쌓기 시작하면 끝없이 따라다녀야 한다 — 그건 사용자 프로그램의 몫이다.

## post (1단계)

- URL, 메서드, 헤더. 본문은 rhai 의 `payload` 또는 기본 이벤트 JSON.
- **비밀값** — API 키를 `.guild/plugins/*.json` 에 적으면 **git 에 커밋된다.**
  환경변수 참조(`${OPENAI_API_KEY}`)만 허용하고 리터럴 키는 거부하는 쪽을
  검토한다. 거부까지 갈지, 경고만 할지는 정해야 한다.
- 타임아웃 필수. 비동기라 길드는 안 멈추지만 무한정 붙들면 안 된다.
- `core` 에 HTTP 클라이언트가 **없다**(cli 에만 reqwest 가 있다). 어디에 둘지
  정해야 한다 — core 에 넣을지, 각 컴포넌트가 주입할지.

## run (2단계)

- 프로세스를 띄우고 이벤트 JSON 을 **stdin** 으로. 인자로 넘기면 길이 제한과
  이스케이프 문제가 생긴다.
- **임의 실행**이라 동의(DEV-375)가 반드시 선행돼야 한다.
- 작업 디렉터리·환경변수·타임아웃·좀비 프로세스 정리.

admin 판단: `run` 이 되는지가 **동작의 한계를 정한다**. 다만 안 되면 빼면
그만이므로 2단계로 미룰 수 있다.

## 테스트 방법

**post**
- 구독한 이벤트에서 실제로 요청이 나간다(대역 서버로 수신 확인).
- 받는 쪽이 죽어 있어도 길드 동작이 멀쩡하다.
- 타임아웃이 걸린다.
- 리터럴 API 키가 든 정의가 거부되거나 경고된다.

**run**
- stdin 으로 이벤트 JSON 이 들어간다.
- 프로세스가 죽거나 오래 걸려도 길드가 안 멈춘다.
- 동의 없이 실행되지 않는다.
