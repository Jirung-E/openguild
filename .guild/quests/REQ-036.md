**잠금 단위와 문서 버전** — 길드 전체를 한 번에 잠그는 지금 구조를 다시 정한다(admin: "잘못된 설계다").
2026-09-29~30 admin 과의 논의로 **방향이 정해졌다** — 아래 "정한 것".

## 지금

- 잠금은 **길드 전체** 하나(`.guild/.lock` + 프로세스 안 Mutex). 서로 상관없는 퀘스트끼리도 줄을 선다.
- 짧다는 전제로 넓게 잡았는데, 그 안에서 플러그인을 최대 60초 기다리고([[BUG-339]]), CLI 는 자동 스냅샷을
  잠금을 쥔 채 뜬다.
- 서버로 팀이 쓰거나 에이전트 여럿이 동시에 일하면 전부 한 줄로 선다.

## 배경 — 덮어쓰기에는 두 종류가 있다

| | 시간 | 막는 것 |
|---|---|---|
| 짧은 틈 | 변경 하나 안의 읽기 → 고치기 → 쓰기 (밀리초) | 잠금 — [[REQ-003]] · [[BUG-287]] |
| 긴 틈 | 편집기를 연 뒤 저장까지 (분) | 잠금으로는 못 막는다 — 출발 원문 비교 → [[REQ-024]] |

## 정한 것

### 1. "바뀌었나" 는 변경의 종류로 정확하게 가린다 — 해시를 쓰지 않는다

해시는 겹칠 확률이 있어 확률적 해결이다(admin). 종류별로 나누면 해시를 쓸 자리가 없다.

| 변경 | 방법 | |
|---|---|---|
| 더하기·빼기 (태그 추가, 댓글 달기) | BUG-287 이 이미 **의도**("X 를 더한다")로 바꿨다 — 잠금 안에서 최신 파일에 의도만 적용 | 비교 불필요, 충돌 없음 |
| 본문 통째로 고치기 (편집기 저장) | 편집기가 처음 읽은 **원문**을 들고 와 지금 파일과 **글자 그대로** 비교 → 다르면 3방향 병합(REQ-024) | 정확 |
| 값 하나 (제목 · 상태 · 긴급도) | 나중 값이 이긴다(REQ-024 에서 정함) | 규칙대로 |

원리는 git 의 3방향 병합과 같다. 다른 것은 **시점과 주체** — 저장하는 순간 앱이 하고, 파일에 충돌 표시를
박지 않으며, git 없이도 된다.

### 2. 문서 버전은 번호 — 순서 판단용

- 문서 파일(frontmatter)에 `version = N`. openguild 가 고칠 때마다 1 올린다.
- **쓰임은 순서뿐**이다 — 이벤트에 실어 훅이 "v8 을 이미 봤으니 늦게 온 v7 은 버린다" 를 판단한다.
- "바뀌었나" 판단에는 쓰지 않는다(위 1). 밖에서 파일을 직접 고치거나 git 병합으로 번호가 안 맞을 수 있다.

### 3. 잠금은 두 겹 — 길드 RW + 문서

| 층 | 잠금 | 누가 |
|---|---|---|
| 길드 | RW (`.guild/.lock`) | 보통 변경은 **공유**로 → 서로 안 막는다. 길드 전체가 필요한 일(백업, 타입·상태 이름 바꾸기 등)은 **독점** |
| 문서 | 독점 (`.guild/.locks/…`) | 실제로 고치는 문서만 |

- 서로 다른 문서를 고치는 변경은 동시에 된다. 같은 문서일 때만 하나가 기다린다.
- 프로세스 사이 공유·독점 파일 잠금은 Rust 표준(`File::lock_shared` / `File::lock`)에 있다.
- 문서 잠금 파일은 비어 있고 gitignored, **만들고 지우지 않는다** — 지우면 다른 프로세스가 새로 만든 파일을
  잠가 둘 다 통과한다(지금 `.lock` 과 같은 이유).

### 4. 잠금 순서는 사람이 못 고르게 한다

여러 문서를 고치는 변경(삭제는 하위 · 선행 퀘스트의 자동 블록까지 고친다)이 서로 다른 순서로 잠그면 서로
기다리다 멈춘다.

- 잠금 함수는 **잠글 문서 목록을 한꺼번에 받는 것 하나만** 둔다. 정렬(이름 순)은 그 안에서 한다.
- **잠금을 쥔 채 또 잠그면 오류.** 잠근 뒤 더 필요한 문서가 생기면 다 풀고 늘어난 목록으로 처음부터.
- `ops::lock_coverage` 처럼 시험으로 강제한다 — 새 기능이 규칙을 어기면 시험이 깨진다.

### 5. 백업은 두 단계 — 모두가 멈추는 시간은 읽는 동안만

1. 길드 **독점** → 백업할 파일 내용을 메모리로 읽기 + journal 정리 → 해제
2. 잠금 **없이** 읽어 둔 것을 백업 파일로 쓰기(느린 쪽)

2026-09-29 실측(이 길드 복사본, 파일 1,862개 · 13MB): 백업 전체 0.10초, 그중 **읽기 0.02초**. 문서마다 하나씩
잠그며 읽으면 멈춤은 없지만 백업이 "한 순간" 이 아니게 된다(퀘스트와 그 댓글 파일이 어긋날 수 있다) —
택하지 않는다.

### 6. 훅은 어떤 잠금 안에서도 돌지 않는다

[[BUG-339]] 가 먼저 한다. 이벤트는 변경 순간의 사본(`with` 포함)과 **버전**(위 2)을 싣는다.

## 검토하고 버린 것

| | 왜 |
|---|---|
| 잠금을 뺀다 | BUG-287 재발 — 동시 쓰기에서 태그·댓글이 조용히 사라진다 |
| 훅의 자식에게 잠금을 물려준다 | 부모와 자식이 같은 파일을 동시에 고친다 — 잠금의 뜻이 없어진다 |
| 훅을 잠금 안에서 돌려 일관성 · 순서를 얻는다 | 길드 전체가 멈추고 길드에 쓰는 훅은 교착한다. 일관성은 사본으로, 순서는 번호로 된다 |
| 내용 해시로 버전 비교 | 확률적이다(admin). 종류별 처리로 정확하게 된다 |
| RW 락 하나로 지금 잠금을 대체 | 쓰기끼리는 여전히 하나씩이고, 읽기는 원래 잠금을 안 잡으며(파일을 통째로 바꿔 끼운다), 훅 교착도 그대로다 — 길드 층에만 쓴다 |

## 할 일 (DEV 로 옮길 때)

- 문서 잠금 + 길드 RW 로 `lock.rs` · `Store::mutation_guard` 를 바꾼다
- `ops` 의 변경 함수마다 "잠글 문서 목록" 을 밝힌다 — 삭제처럼 여럿인 것은 잠근 뒤 목록을 다시 확인
- 문서 frontmatter 에 `version`, 이벤트에 싣기
- 백업 두 단계
- 시험: 다른 문서끼리 동시 변경이 안 막힌다 / 같은 문서는 줄 선다 / 잠금 순서 규칙이 강제된다 / 백업이 한
  순간을 찍는다
- **잰다**: 바꾸기 전후로 변경 한 번의 시간과, 동시 변경이 기다리는 시간
