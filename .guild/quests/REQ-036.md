**잠금 단위와 문서 버전** — 길드 전체를 한 번에 잠그는 지금 구조를 다시 정한다(admin: "잘못된 설계다").

## 지금

- 잠금은 **길드 전체** 하나(`.guild/.lock` + 프로세스 안 Mutex). 서로 상관없는 퀘스트끼리도 줄을 선다.
- 짧다는 전제로 넓게 잡았는데, 그 안에서 플러그인을 최대 60초 기다리고([[BUG-339]]), CLI 는 자동 스냅샷
  (약 2초, `lock.rs` 주석)을 잠금을 쥔 채 뜬다.
- 서버로 팀이 쓰거나 에이전트 여럿이 동시에 일하면 전부 한 줄로 선다.

## 배경 — 덮어쓰기에는 두 종류가 있다

| | 시간 | 막는 것 |
|---|---|---|
| 짧은 틈 | 변경 하나 안의 읽기 → 고치기 → 쓰기 (밀리초) | 잠금 — [[REQ-003]] · [[BUG-287]] 이 넣었다. 태그·댓글 **추가** 는 "통째로 쓰기" 대신 **의도**로 바꿔 충돌을 없앴다 |
| 긴 틈 | 편집기를 연 뒤 저장까지 (분) | 잠금으로는 못 막는다 — **출발 버전 비교** 가 필요하다 → [[REQ-024]] |

REQ-024 를 하려면 문서마다 **지금 버전**이 있어야 한다. 그게 생기면 잠금도 문서 단위로 좁힐 수 있다 —
따로 하면 잠금을 두 번 뜯어고친다. 그래서 함께 정한다.

## 정한 방향 (admin, 2026-09-23)

- **모든 쓰기는 "내가 본 버전 + 하려는 일" 을 들고 온다.** 쓰는 순간 **그 문서만** 짧게 잠그고 버전을 비교한다.
  - 같으면 → 그대로 쓴다
  - 다르면 → 추가형(태그·댓글)은 의도를 다시 적용 / 본문은 3방향 병합(REQ-024) / 단일값(제목·상태)은 나중 값
- **훅은 어떤 잠금 안에서도 돌지 않는다**([[BUG-339]] 가 먼저 한다).
- **이벤트에 버전을 싣는다.** 프로세스가 다르면 훅이 불리는 순서를 보장할 수 없다(지금도 그렇다). 대신 훅이
  순서를 **알 수 있게** 한다 — "v8 을 이미 봤으니 늦게 온 v7 은 버린다".
- **이벤트는 변경 순간의 사본을 싣는다**(`with` 포함 — BUG-339).

검토하고 버린 것:

| | 왜 |
|---|---|
| 잠금을 뺀다 | BUG-287 재발 — 동시 쓰기에서 태그·댓글이 조용히 사라진다 |
| 훅의 자식에게 잠금을 물려준다 | 부모와 자식이 같은 파일을 동시에 고치게 된다 — 잠금을 둔 뜻이 없어진다 |
| 훅을 잠금 안에서 돌려 일관성·순서를 얻는다 | 그 보장이 `wait` 훅에만 가고, 길드 전체가 멈추고, 길드에 쓰는 훅은 교착한다. 일관성은 사본으로, 순서는 버전으로 된다 |
| 잠금 없이 "쓰기 직전 확인 후 다시 시도" 만 | 파일시스템에 원자적 비교-교체가 없어 결국 짧은 잠금이 필요하다. 문서 단위 짧은 잠금 + 버전 비교가 같은 것을 준다 |

## 정할 것

- **버전을 무엇으로** — 내용 해시 / 단조 증가 번호(파일 frontmatter) / mtime. git 으로 오가는 파일이라
  mtime 은 믿기 어렵다.
- **여러 문서를 고치는 변경**(삭제는 하위·선행 퀘스트의 자동 블록까지 고친다) — 건드릴 문서를 먼저 정하고
  **늘 같은 순서**(경로 순)로 잠근다. 잠근 뒤 "관련 목록이 그새 바뀌지 않았나" 를 다시 확인한다.
- **`index.db` · journal** — SQLite 가 줄을 세우므로 문서 잠금과 별개로 둘 수 있는지.
- **자동 스냅샷** — 잠금 밖으로. 길드 전체를 읽으므로 "그 순간의 일관된 모습" 을 어떻게 얻을지.
- **길드 단위로 남아야 하는 것** — 카운터(새 번호 붙이기), 타입·상태 정의 변경처럼 길드 전체에 걸린 것.
