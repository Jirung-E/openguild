## 제안 옵션

### urgency 범위 / 다중
- `--urgency 1,2` — 복수 단일 값. CSV 또는 반복.
- `--urgency 1-3` — 범위. 1 이상 3 이하.
- 현재 `--urgency N` 단일만 지원.

### 시간 범위
- `--created-after <ISO date>` / `--created-before <ISO date>`.
- `--updated-after <ISO date>` / `--updated-before <ISO date>`.
- ISO 8601 (`2026-05-15` 또는 `2026-05-15T10:00:00Z`) 입력.
- SQL `datetime()` 비교.

### 조합 예시
```bash
openguild quest list --urgency 1,2 --status open
openguild quest list --urgency 1-2
openguild quest list --updated-after 2026-05-15 --sort updated
openguild quest list --created-after 2026-05-15 --created-before 2026-05-17
```

## 후속 버그 수정 (2026-05-22)

테스트 중 발견: `--created-after 2026-05-22T00:00:00` 입력 시 KST 사용자가
방금 만든 quest (DEV-041, `created_at = 2026-05-21T15:26:39Z` = KST 0시 26분)
가 매치 안 됨.

### 원인 (둘 다 작용)

1. DEV-041 이후 stored ts 는 **mixed format**:
   - legacy 행 (migration 0005 변환): `2026-05-21T15:26:39Z` (20자).
   - 새 행: `2026-05-22T00:43:40+09:00` (25자).
   - 19번째 문자 `Z` (0x5A) vs `+` (0x2B) — `'+' < 'Z'` ASCII 이라
     같은 날짜에서 lex 비교 결과가 절대 시각과 어긋남.

2. user 입력 `2026-05-22T00:00:00` (TZ 마커 없음) 을 SQLite 가 UTC 로 해석.
   KST 사용자 의도 (현지 자정) 과 9시간 어긋남.

### 수정

- `core::time::normalize_filter_ts(input)`:
  - TZ 마커 있으면 그대로.
  - date-only (`YYYY-MM-DD`) → `T00:00:00<local_offset>` 부착.
  - datetime w/o TZ (`...T00:00:00`) → `<local_offset>` 부착.
- `services::quests::list` 의 시간 비교 SQL:
  - `q.created_at >= ?` (lex) → `datetime(q.created_at) >= datetime(?)`.
  - SQLite 의 `datetime()` 은 입력의 `Z` / `±HH:MM` 를 모두 인식하여 UTC
    space-form (`YYYY-MM-DD HH:MM:SS`) 으로 통일 변환 → 안전한 lex 비교.
- bind 단계에서 `normalize_filter_ts` 통과.

### 자동 테스트 +9
- core::time +7: `normalize_filter_ts` (Z / +offset / +HHMM / date-only /
  naked datetime / 빈 / has_tz_marker 패턴 검증).
- server +2: TZ-aware after-검색 (방금 만든 quest 가 매치) / naked datetime
  입력의 로컬 TZ 해석.
