## 배경

DEV-121 (startup incremental sync) 가 GUI 에 적용되고 CLI 는 변경 없음으로 결정됨 (사용자 책임). server 는 long-running 이라 **startup + mid-runtime** 두 axis 가 모두 있어 별도 검토 필요.

## 시나리오

- 서버 host 중 admin 이 CLI 로 quest 수정 → server 의 DB 캐시 stale.
- 서버 host 중 운영자가 `.guild/` 디렉토리에 `git pull` → 다수 파일 갱신.
- 멀티사용자 환경에서 서로 다른 client (브라우저 / 다른 서버 인스턴스) 가 파일 시스템 공유.

server 는 long-running 이라 startup 1회 sync 만으로는 부족.

## 옵션 (각각 단독 또는 조합)

### (S1) Startup sync — DEV-121 의 `open_with_sync` 를 server 시작 시 호출

`server/src/main.rs:176` (host 진입점) 에 `Store::open_with_sync` 1 line 변경. 비용: 시작 시 ~20ms. 누락 부분 회수.

### (M1) per-request lazy stat

각 API request 핸들러가 다루는 resource (예: `GET /api/quests/:id`) 에서 그 quest 파일의 mtime 만 확인 → cached_mtime > 면 그 한 row 만 incremental sync 후 응답.
- 장점: 거의 실시간. cost = request 당 stat 1-N 회.
- 단점: 모든 핸들러에 sync wrap 추가 — 코드 침범.
- 완화: middleware 로 추출.

### (M2) 주기적 sync (background tick)

`tokio::spawn` 으로 60s (또는 설정값) 마다 `incremental::sync_changed_files`.
- 장점: 코드 단순. 모든 핸들러 무관.
- 단점: 60s 지연. 자주 sync 하면 N * 20ms 비용.
- 적합: 외부 편집이 드문 환경.

### (M3) Filesystem watcher (`notify` crate)

`.guild/quests/` 등 파일 시스템 변경 event 받아 그 파일만 즉시 incremental sync.
- 장점: 실시간, 효율적 (변경된 파일만 처리).
- 단점: 의존성 추가. inotify / kqueue / ReadDirectoryChangesW 각 OS 별 quirks. event coalescing / debounce 필요.
- 적합: server 의 정석 — long-running 에 적합.

### (M4) 현 상태 유지 (manual reindex)

`/api/admin/reindex` + `openguild-server reindex` CLI 만 제공. 사용자 / agent 가 외부 편집 후 명시 호출.
- 장점: 0 cost. 단순.
- 단점: 사용자가 잊으면 stale. (현 상태.)

## 권장

- **(S1) startup sync 는 거의 무조건 채택** — DEV-121 인프라 그대로 활용, cost 무시 가능.
- mid-runtime 은 **(M3) filesystem watcher 권장** — 정확 + 효율. 단 구현 부담 (debounce / 멀티 OS 테스트) 크면 1차로 **(M2) 60s tick** 으로 임시 운영하고 나중에 M3 로 교체.
- (M1) 은 핸들러 침범이 커서 비권장.
- (M4) 는 멀티사용자 / 협업 server 용도엔 부족.

## 결정 보류

- mid-runtime 전략 — M2 vs M3 vs M2→M3.
- watcher debounce 간격 (예: 500ms 코얼레스).
- 서버 reload event 를 WebSocket / SSE 로 클라이언트 (브라우저) 에 push 할지 — 별개 quest 후보 (DEV-088 원격 모드 연결).
