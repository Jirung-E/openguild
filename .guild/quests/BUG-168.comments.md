## 원인 조사 결과 (실측)

### 확정: 서버(브라우저) 모드 — axum 기본 body limit 2 MiB

`/api/attachments` 는 파일 bytes 를 base64 로 감싼 JSON 을 받는데
(`editor-attach.ts` → `saveAttachmentBytes`), 라우터 어디에도
`DefaultBodyLimit` 설정이 없어 **axum 0.8 기본값 2 MiB** 가 그대로 걸린다.

임시 길드 + `openguild-server.exe host` 로 실측 (원본 크기 → HTTP 코드):

| 원본 | JSON body | 결과 |
|---|---|---|
| 512 KB | 699,082 B | 200 |
| 1024 KB | 1,398,134 B | 200 |
| 1400 KB | 1,911,498 B | 200 |
| **1500 KB** | **2,048,030 B** | **200** (한도 직전) |
| **1600 KB** | **2,184,566 B** | **413** |
| 2 MB | 2,796,234 B | 413 |
| 5 MB | 6,990,538 B | 413 |

경계가 2,097,152 B(2 MiB) 와 정확히 일치. base64 가 4/3 로 부풀기 때문에
**원본 약 1.5 MB 를 넘으면 실패**한다 — 사진 한 장에도 걸리는 수준.

에러 메시지도 그대로 노출된다: `Failed to buffer the request body: length
limit exceeded` (axum 원문). 사용자는 왜 실패했는지 알 수 없다 — [[DEV-298]]
(진행 표시)과 같은 뿌리의 UX 문제.

### 데스크탑(Tauri IPC) 모드 — 한도는 미확인, 설계 자체가 취약

여기서는 GUI 를 띄울 수 없어 IPC 한도를 실측하지 못했다. 다만 현재 경로는
크기와 무관하게 낭비가 크다: 파일 → ArrayBuffer → binary string → base64
문자열 → JSON → Rust `String` → decode `Vec<u8>` 로, **파일 크기의 5~6배
메모리**가 JS/Rust 양쪽에 동시에 잡힌다. 대용량에서 실패하거나 멈춘 것처럼
보이는 게 자연스럽다.

### 수정 방향

1. **서버**: `/api/attachments` 에 `DefaultBodyLimit` 을 명시적으로 넉넉히
   (다른 라우트는 2 MiB 기본 유지 — bytes 를 받는 라우트만 완화).
2. **데스크탑**: 파일 선택 경로는 bytes 를 IPC 로 보내지 말고 **경로만**
   넘겨 Rust 쪽에서 복사한다(`save_attachment_from_path`). 크기와 무관하게
   IPC payload 가 상수 — 한도 문제가 원천 소멸하고 속도도 빨라진다.
   붙여넣기/드래그&드랍은 File 객체(bytes)뿐이라 기존 경로 유지.
3. **프론트**: bytes 경로에 한해 업로드 전 `file.size` 로 한도를 확인하고
   한도를 명시한 안내를 띄운다(axum 원문 노출 금지).

### core 에는 상한을 두지 않는다

`ops::attachments::save_attachment` 에 상한을 넣으면 CLI 직접 첨부(base64
경유가 없어 지금은 크기 제약이 없다)까지 후퇴한다. 상한은 그 제약이 실재하는
전송 경계(HTTP body)에만 둔다.

참고: 첨부는 `attachment_blobs` 로 index.db 에도 복사되므로([[DEV-284]])
한도를 크게 잡으면 스냅샷 용량도 같이 커진다 — 무제한은 피한다.
