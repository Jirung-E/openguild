전체 코드베이스 리뷰(server/cli)에서 발견. 코드 확인으로 검증 완료.

## 1. journal count 무제한 — `?count=-1` 로 전체 덤프

`server/src/routes/admin.rs:139` `JournalQuery.count: i64` 는 serde 기본값 50 만
있고 **상한/하한 검증이 없다.** 값이 그대로
`core/src/maintenance.rs:118` 의 `LIMIT ?` 에 바인딩된다.

SQLite 는 **음수 LIMIT 을 "제한 없음" 으로 해석**한다. 따라서
`GET /api/admin/journal?count=-1` 은 의도된 50 캡을 우회해 journal 테이블
전체를 한 응답에 쏟아낸다. 장수명 호스트에서 무제한.

수정: `count` 를 clamp (예: 1..=1000).

## 2. 배너 파일 누락에 500 (404 여야 함)

`server/src/routes/campaigns.rs:214` 가 `std::fs::read` 실패를 **종류 불문**
`AppError::Internal` 로 매핑 → HTTP 500.

같은 파일-없음 상황을 `admin.rs:222/249` 는 올바르게 `NotFound` → 404 로
매핑한다. DB 엔 image_path 가 있는데 디스크 파일이 drift 로 사라진 경우
(브랜치 전환 등 [[BOOK-001]] 맥락에서 충분히 발생 가능) 클라이언트는 원인을
알 수 없는 500 을 받는다.

## 3. 대용량 첨부 전체 버퍼링 — BUG-188 취지와 충돌

`server/src/routes/admin.rs:249` `get_guild_file` 이 async 핸들러 안에서
동기 `std::fs::read` 로 **파일 전체를 메모리에 올린다.** Range 미지원,
blocking pool 오프로딩 없음.

`routes/mod.rs:29-34` 의 압축 레이어는 BUG-188 의 1.5GB 첨부를 의식해
octet-stream/zip/video/audio 를 정성껏 제외하고 있는데, 정작 그 첨부를
실제로 서빙하는 핸들러가 통째로 버퍼링한다. 동시 다운로드 몇 건이면 메모리
고갈 + tokio 워커 블로킹. Range/206 이 없어 영상 탐색도 불가.

## 4. 댓글 생성이 200 (다른 create 는 전부 201)

`server/src/routes/comments.rs:117` `add_comment`, `:204` `camp_add_comment` 가
`Json(entry)` 로 암묵적 200 을 반환한다.

같은 트리의 다른 create 는 전부 201 — `quests.rs:85`, `campaigns.rs:51`,
`campaigns.rs:120`, `library.rs:94`, `rules.rs:111`.

## 5. `--table --json` 처리 불일치 (CLI)

`cli/src/main.rs:7627` `quest list` 만 두 플래그 동시 지정을 **에러로 거부**
한다. `--table` 을 제공하는 다른 모든 명령(statuses/rules/campaign/tag/library
list, 예: :6897)은 `if json { } else if table { }` 구조라 `--table` 을 조용히
무시하고 JSON 을 낸다. 같은 플래그 조합에 서브커맨드마다 다른(문서화되지 않은)
동작 — 스크립트 작성자가 당할 수 있다.

## 6. 사소 — 상태 slug 하드코딩 (정정 포함)

`cli/src/main.rs:8111` 의 `quest start/done/reopen` 이 `resolve_status_slug` 에
표시명 문자열 `"In Progress"` / `"Done"` / `"Open"` 을 넘긴다.

**주의 — 리뷰 1차 보고는 틀렸다.** "`statuses update --name-en` 으로 표시명을
바꾸면 깨진다" 는 주장은 재현되지 않는다. `resolve_status_slug`(:3685) 의
1단계가 **입력**을 정규화해(`"In Progress"` → `in_progress`) `s.slug` 와
비교하므로 name_en 을 바꿔도 slug 가 그대로면 계속 매칭된다.

실제로 남는 위험은 좁다: **slug 자체를 rename** 하고 **동시에 name_en 도
"In Progress" 가 아니게** 되어야(3단계 fallback 까지 실패) 깨진다.
버그라기보다 의도를 정직하게 표현하는 정리 건 — 표시명 대신 정규 slug
(`open`/`in_progress`/`done`)를 직접 넘기는 편이 낫다. 우선순위 낮음.
