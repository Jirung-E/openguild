백업 스냅샷이 `.guild/` 소스 트리를 **파일 단위로 복사**해, 파일 수에 비례한
비용과 디스크 낭비가 발생한다. 설계 의도(백업은 DB)와도 어긋난다.

## 배경 — 왜 트리 복사가 됐나

원래는 스냅샷 = `index.db` 사본이었는데, [[BUG-076]](urgency 1)에서 데이터
소실이 발견됐다: 복원해도 `.guild` 파일이 되살아나지 않고, 규칙(rules)은 DB 에
없어 백업 범위에서 아예 빠졌다. 그 수정으로 "진리원인 **파일**을 담는다"로
바꾼 것은 옳았지만, 담는 **방식**이 파일 트리 복사였다.

## 측정 (실제 길드, 퀘스트 475개)

- `.guild` 소스 = 파일 약 1,100개, 실데이터 1.5MB
- **D: 볼륨이 exFAT + 128KB 클러스터** → 평균 2.1KB 파일이 각각 128KB 점유
  (60배 증폭). 스냅샷 하나가 137MB, 보관 7개가 **957MB**
- `backup new` = **2,054ms** (파일 1,100개 create+write)
- 자동 스냅샷이 걸린 상태 변경 = **3,976ms** (사용자 보고 "버벅임")

## 구현 — 스냅샷 1개 = SQLite 파일 1개

`snapshots/{ts}.db` 에 `files(rel_path PK, content BLOB)` + `meta(key,value)`.
`rel_path` 는 길드 루트 기준 상대 경로(`/` 정규화)라 복원이 그대로 되붙인다.
담는 대상(진리원 파일)은 **이전과 동일** — rules/사이드카/첨부 모두 포함.

**journal.db 와 합치지 않고 스냅샷별 파일로 분리한 이유**(사용자 결정: 분리):
journal 은 스냅샷마다 truncate 되는 파일이라 보관 정책이 섞이면 얽힌다.
분리하면 (a) 목록·보관정리가 파일 이름/삭제로 끝나 **매 mutation 마다 도는
`latest_snapshot_timestamp` 가 DB 를 열지 않아도 되고**(BUG-167 취지 유지),
(b) 스냅샷 하나가 손상돼도 나머지가 안전하다.

레거시 디렉토리 스냅샷(`{ts}/`)은 계속 **목록·복원·삭제 대상**으로 남긴다 —
이미 만들어진 것을 버리지 않는다. 보관 개수(7)는 둘을 합쳐 센다.

## 결과

| | 이전 | 이후 |
|---|---|---|
| 스냅샷당 파일 수 | 1,100개 | **1개** |
| `backup new` | 2,054ms | **460ms** (4.5배) |
| 스냅샷 크기 | 137MB(할당) | 1.6MB(실데이터) |
| 상태 변경(스냅샷 시) | 3,976ms | **350ms** |
| 상태 변경(평상시) | 230ms | 220ms |

디스크: 957MB → 레거시 5개가 보관 정책으로 밀려나가면 약 10MB 로 수렴.
(첫 `backup new` 가 9.2초였던 것은 137MB 디렉토리 하나를 prune 하며 지운
비용 — 일회성이다.)

DEV-299(백그라운드화)와 합쳐지면 GUI 에서 스냅샷은 체감되지 않는다.

## 검증

- core 364건 / 워크스페이스 678건 통과, clippy `-D warnings` 통과.
- 기존 스냅샷 테스트(history 사이드카·도서관·첨부 bytes 포함, 복원, retention 7,
  replay 기준 상태)가 새 구조에서 그대로 통과 — 경로 존재 검사만 DB 조회로 교체.
- 실제 길드에서 생성·목록 확인. **복원은 실제 길드에서 시험하지 않았다**
  (라이브 데이터를 덮어쓰므로) — 단위 테스트가 커버.

## 부수 수정

DEV-299 테스트가 `OPENGUILD_AUTO_BACKUP_OPS`(프로세스 전역)를 세워 병렬 실행 중
무관한 replay 테스트를 실패시켰다. `Store.auto_snapshot_ops_override` 로
Store 별 지정으로 바꿔 오염을 제거(서버/GUI 도 코드로 정책 지정 가능).

## Test plan

1. `backup new` → `backup list` 에 새 항목이 보이고 크기가 수 MB 인지.
2. **복원**: 임시 길드에서 퀘스트/규칙/댓글/첨부를 만들고 스냅샷 → 파일 일부
   삭제 → `backup restore <ts>` → 전부 되돌아오는지(특히 rules 와 첨부 bytes).
3. 레거시 디렉토리 스냅샷이 남아 있는 길드에서 목록·복원·삭제가 되는지.
4. 보관 7개 초과 시 오래된 것(디렉토리든 .db 든)부터 지워지는지.
5. GUI 백업/복원 화면에서 동일하게 동작하는지.
6. 원격(`--remote`) 모드의 backup 명령도 정상인지.
