`just test` 병렬 실행에서 `attachment_name_keeps_original_and_stays_safe` 가
가끔(이 머신에선 자주) 실패 — `assert_ne!` 인데 두 값이 같음.

## 원인

`core/src/ops/attachments.rs` 의 `new_attachment_rel`:

```rust
let nanos = SystemTime::now().duration_since(UNIX_EPOCH).map(|d| d.as_nanos())...;
let rand: u32 = (nanos as u32) ^ 0x5bd1_e995;
let uniq = format!("{:08x}{rand:08x}", (nanos as u64) & 0xffff_ffff);
```

`rand` 라는 이름과 달리 실제로는 난수가 아니라 **같은 nanos 값에서 XOR 상수로
파생**된 값이다. uniq 문자열의 두 hex 파트가 전부 같은 `nanos` 하위 32비트에서
나오므로, 두 호출의 `nanos` 하위 32비트가 우연히 같으면(짧은 시간 안의 연속
호출에서 시스템 클럭 해상도가 코드 실행 속도보다 성길 때 실제로 발생) uniq
전체가 완전히 동일해진다 — "같은 밀리초 안의 충돌도 사실상 없다"는 주석의
전제가 틀렸다.

## 수정

프로세스 전역 `AtomicU32` 카운터를 추가해 매 호출마다 무조건 다른 값이
나오게 한다(클럭 해상도와 무관하게 in-process 유일성 보장). nanos 기반 값은
그대로 두되(같은 프로세스 재시작 후에도 어느 정도 시간 다양성 유지), 카운터를
섞어 넣는다.

## 테스트 방법

`cargo test -p openguild-core --lib attachment_name_keeps_original_and_stays_safe`
반복 실행(또는 `just test` 병렬 실행)해서 더 이상 실패하지 않는지.
