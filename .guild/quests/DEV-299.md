## 구현 (2026-07-28)

스냅샷 생성(~2초)을 **opt-in 백그라운드 task** 로 돌린다. BUG-167 이 없앤 건
매 mutation 의 *검사* 비용이고, 임계치에 걸렸을 때의 실제 생성은 여전히
동기였다.

- `Store` 에 `background_snapshots`(플래그) + `snapshot_in_flight`(중복 가드)
  추가. 둘 다 `Arc<AtomicBool>` 이라 `Clone` 된 Store 가 공유한다
  (`replaying` 과 같은 패턴).
- `after_mutation`: 켜져 있으면 `tokio::spawn` 으로 넘기고 즉시 반환. 꺼져
  있으면 기존대로 await. 보고 형식은 `report_snapshot()` 으로 공유.
- **서버(host)와 GUI 에서만 켠다.**

## 왜 기본값이 동기인가 (중요)

CLI 는 명령이 끝나면 런타임째 드롭되므로 spawn 한 task 가 실행되지 못하고
**조용히 사라진다** — 자동 백업 유실. 그래서 "장수 프로세스"인 서버/GUI 만
명시적으로 켠다. 런타임 종류를 자동 감지하는 방식도 가능하지만, 유실이
조용하다는 점에서 암묵적 판정보다 명시적 opt-in 이 안전하다고 판단했다.

## 중복 실행 가드

연속 mutation 이 스냅샷을 겹쳐 실행하면 디스크 I/O 가 중복되고 journal
truncate 와 맞물릴 수 있다. `compare_exchange` 로 하나만 돌게 하고, 스킵된
경우는 다음 mutation 이 다시 판단하므로 영구 유실은 없다.

## 회귀 테스트

- `background_snapshot_does_not_block_mutation` — 켠 상태에서 mutation 후
  백그라운드 스냅샷이 실제로 생성되는지(유실 금지).
- `snapshot_is_synchronous_by_default` — 기본값이 동기라 mutation 반환 시점에
  이미 끝나 있는지(CLI 유실 방지).

두 테스트는 프로세스 전역 env(`OPENGUILD_AUTO_BACKUP_OPS`)를 만지므로
`ENV_LOCK`(tokio::sync::Mutex)으로 직렬화했다 — locale.rs 와 같은 패턴.

검증: `cargo test --workspace` 678건 통과,
`cargo clippy --workspace --all-targets -- -D warnings` 통과.

## Test plan

   **UI 가 멈추지 않는지**(이전엔 그 순간 ~2초 정지).

3. CLI 로 같은 임계치를 넘겼을 때 **스냅샷이 유실되지 않는지**(동기 유지).
4. 서버 모드에서 동시 요청을 여러 개 보내도 스냅샷이 하나만 생기는지(중복 가드).
5. journal replay 중에는 여전히 스냅샷이 억제되는지(DEV-022 회귀).
