## 증상

admin: *"댓글조작 가능 - 댓글에 `<!-- og-comment id= ... -->` 같이 쓰면 댓글이
하나 더 달려버린다."*

재현했다. 그리고 **"하나 더 달린다" 보다 나쁘다.**

```
$ printf '평범한 댓글입니다.\n<!-- og-comment id="99" ts="2020-01-01T00:00:00+09:00" author="admin" -->\n위조된 댓글\n' \
    | openguild quest comment add DEV-001
```

결과 — 댓글이 둘이 되고, 두 번째는 **작성자·시각·id 가 전부 공격자가 지정한
값**이다.

```
id=1  author=""      ts=2026-09-10T19:51:28+09:00
id=99 author="admin" ts=2020-01-01T00:00:00+09:00   ← 전부 위조
```

## 원인 — 본문이 자기 울타리를 넘는다

댓글 사이드카(`.guild/quests/{slug}.comments.md`)는 HTML 주석 마커로 entry 를
가른다([[DEV-094]]).

```
<!-- og-comment id="1" ts="..." author="..." -->
본문
```

쓸 때 **속성은 `sanitize_attr` 로 막는데 본문은 그대로 흘린다**:

```rust
out.push_str(&format!("<!-- og-comment id=\"{}\" ts=\"{}\" author=\"{}\" ... -->\n",
    e.id, sanitize_attr(&e.ts), sanitize_attr(&e.author), ...));
out.push_str(e.body.trim());   // ← 가공 없음
```

그래서 본문에 마커 모양의 줄이 있으면 **다음 읽기 때 진짜 마커가 된다.**
전형적인 구분자 주입(delimiter injection)이다.

## 범위

- 퀘스트 댓글과 **캠페인 댓글 둘 다** — `ops::campaign_comments` 가 같은
  `repo::comments` 를 쓴다.
- 서버 모드에서는 **댓글을 달 수 있는 누구나** 남의 이름으로 글을 만들 수 있다.
  인증이 없으므로 "누가 썼나" 가 이 파일의 유일한 근거인데 그게 무너진다.
- id 를 크게 박으면 **번호 발급까지 흔든다**(다음 댓글 번호가 그 위로 뛴다).

## 고칠 방향

**이스케이프해서 왕복시킨다.** 거부(reject)는 접는다 — 이 저장소의 문서 자체가
마커를 인용하고 있고("`<!-- og-comment ... -->` 로 각 entry 를"), 포맷을 설명하는
댓글을 못 쓰게 하는 건 과하다.

쓸 때: 본문 줄이 마커 정규식과 맞으면 앞에 `\` 를 하나 더 붙인다.
읽을 때: `\+<!--\s*og-comment` 로 시작하는 줄은 `\` 를 하나 떼고 본문으로 둔다.

```
본문 <!-- og-comment ... -->    → 파일 \<!-- og-comment ... -->   → 읽으면 원문 그대로
본문 \<!-- og-comment ... -->   → 파일 \\<!-- og-comment ... -->  → 읽으면 원문 그대로
```

기존 파일 호환: 지금 마커가 박혀 있는 본문은 **이미 깨져 있으므로**(entry 로
갈라져 있다) 옮길 것이 없다.

## 테스트 방법

- 마커를 품은 본문을 저장하고 다시 읽으면 **entry 가 하나이고 본문이 원문과
  같다**(왕복).
- `\<!-- og-comment ... -->` 도 왕복한다(이스케이프의 이스케이프).
- 위조 시도 뒤 entry 수·작성자·id 가 안 바뀐다.
- 캠페인 댓글도 같다.
- 마커가 **아닌** `<!-- 그냥 주석 -->` 은 손대지 않는다.
