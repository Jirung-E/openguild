길드 파일 구조가 버전 간 달라질 때 (`.guild/quests/*.md` frontmatter
필드 추가/제거, `.guild/types/*.toml` 형식 변경 등) 안전하게 처리.

## 문제 정의

현재 `<name>.guild` 마커 파일:
```toml
name = "openguild"
version = "1.0"
created_at = "2026-05-15"
```
`version` 필드는 있지만 실제로 사용되는 곳 없음 — schema 호환 검사가 없어
다음과 같은 시나리오에서 깨짐:

1. **앞으로 schema 가 바뀐 길드 (v2) 를 옛 실행파일 (v1) 로 열기**
   → 모르는 필드 또는 형식 → 파싱 실패 / 데이터 손상.
2. **옛 길드 (v1) 를 새 실행파일 (v2) 로 열기**
   → 누락 필드 default 처리 + 필요 시 자동 마이그레이션.

## 구현 스케치

### 마커 파일
- `schema_version` 필드 추가 (integer; 1 부터).
- 기존 길드 (필드 없음) → 1 로 가정.

### 실행파일 측
- core/src/repo/seed.rs::seed_guild_dir — 새 길드는 항상 현재 `CURRENT_SCHEMA_VERSION` 으로 기록.
- core/src/store.rs::Store::open — 시작 시 마커 읽고 비교:
  - `marker.schema_version > CURRENT` → `AppError::IncompatibleGuild`
    ("이 길드는 더 새 버전의 OpenGuild 로 만들어졌습니다. 앱을 업데이트하세요.")
  - `marker.schema_version < CURRENT` → migration 함수 chain 실행:
    `migrate_1_to_2(store)`, `migrate_2_to_3(store)` …
    완료 후 marker 갱신.
  - `== CURRENT` → 정상.

### GUI 진입 처리
- IncompatibleGuild 시 Welcome 페이지 또는 별도 안내 페이지로 redirect +
  "업데이트 확인" 버튼 (DEV-063 연결).
- migration 필요 시 진행 모달 + "백업 권장" 안내.

### Migration 정책
- snapshot 자동 생성 (migration 전).
- migration 함수는 idempotent + 트랜잭션.
- 실패 시 snapshot 복원 + 사용자 안내.

## 검증
- v1 길드 → v2 실행파일로 열기 → 자동 마이그레이션 + 정상 동작.
- v2 길드 → v1 실행파일로 열기 → 명확한 에러 안내 + 데이터 unchanged.
- migration 중 실패 → snapshot 복원 + 원래 상태 유지.

## 후속 (이 quest 범위 외)
- "downgrade" — 새 길드를 옛 실행파일로 강제 열기 (위험, 별도 quest).
- multi-step migration 의 자동 테스트 프레임워크.
