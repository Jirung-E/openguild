## 배경

BUG-049 (자동 reindex) + BUG-059 (drift detection — `last_indexed_at`) 으로 GUI 시동 시 외부 편집이나 첫 부트스트랩에서 `drift::auto_resync` → `reindex()` 가 돌아간다. 작은 길드 (< 50 quest) 면 < 100ms 라 무감지지만:

- **첫 0.2.0 업데이트 사용자**: migration 0014 적용 직후 마커가 빈 값 → 모든 파일 fresh 판정 → 전량 reindex 한 번. 수백 quest + 댓글 / 메모 sibling 까지 적재되면 수 초 걸릴 수 있음.
- **큰 길드 + git pull 직후**: 많은 파일이 갱신되어도 같은 시나리오.

이 동안 GUI 는 시동 sequence 가 `tauri::async_runtime::block_on` 안에서 멈춰있어 **윈도우가 안 뜨거나 빈 화면 / 로딩 표시 없이 멈춤** — 사용자 시각엔 "앱이 hang 했다".

## 해결 방향 (옵션)

### (A) Splash 윈도우

Tauri 의 별도 작은 윈도우를 시동 즉시 띄우고 reindex 완료 시 닫음 + 메인 윈도우 표시.
- 장점: 사용자가 "뭔가 돌고 있다" 즉시 인지.
- 단점: 윈도우 2개 관리. 짧은 reindex 일 땐 깜빡임.

### (B) 메인 윈도우 빈 상태 표시 + 백그라운드 reindex

`block_on(auto_resync)` 제거. 메인 윈도우는 즉시 표시하고 `tauri::async_runtime::spawn` 으로 reindex. Frontend 가 reindex 진행 상태를 event 로 받음 (`emit('reindex-progress', {phase, done, total})`).
- 장점: 윈도우 1개, 자연스러움.
- 단점: reindex 중에 frontend 가 stale 데이터로 mount → reindex 끝나면 다시 fetch / invalidate 필요. UX 처리 복잡.

### (C) 동기 reindex + 단순 "잠시만요" 텍스트

기존 흐름 유지하되 윈도우는 즉시 띄우고 `<main>` 안에 "데이터 sync 중…" 표시. reindex 끝나면 normal mount.
- 장점: 가장 단순. spawn / IPC 안 필요.
- 단점: 여전히 main thread 점유 (block_on) — 진행 회전 애니메이션도 멈춤. WebView 가 painted 되는 시점은 보장.

## 권장

(C) 1차 → 사용자 반응 보고 부족하면 (B) 로 진화.

(C) 구현 부담:
- `+layout.svelte` 의 onMount 에서 `current_guild_path` 받기 전 잠시 "Sync 중…" placeholder.
- Tauri 측에서 `block_on(auto_resync)` 를 main 윈도우 show 이후로 이동 (window 가 먼저 뜨도록).

## 측정 / 수치

진행 전 실측:
- 100 quest / 50 댓글 길드의 reindex 시간.
- 1000 quest / 500 댓글 (큰 길드) — 가능하면 dogfood `.guild/` 자체로 측정.

수치가 < 500ms 면 작업 우선순위 ↓ (사용자 거의 못 느낌).
