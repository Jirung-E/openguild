## 배경 / 동기

BUG-049 (자동 reindex) + BUG-059 (drift detection) 후 startup 마다 `drift::auto_resync` 가 변경 감지 시 **풀 reindex** 실행 — DELETE all + INSERT all. 사용자 토론 (2026-06-09) 에서 두 가지 깨달음:

1. **"파일이 진리"** 라는 원칙과 코드 실태 (DB-first read) 가 모순. read 자체는 DB 가 빠르니 유지하되, **파일 → DB 동기화는 mtime 기반 incremental** 로 바꾸면 모순이 거의 해소.
2. **`stat()` 만으로 mtime 읽기 = microsecond 수준 (공짜)**. 변경된 파일만 re-parse 하면 매 startup 비용 < 50ms (수천 파일 길드도).

→ 풀 reindex 의 역할을 "명시적 corruption recovery / admin 수동" 으로 격하. startup 은 incremental 로.

## 설계

### Phase 1 — Startup incremental sync (필수)

`Store::open` 직후의 `drift::auto_resync` 호출을 새 `incremental::sync_changed_files(store)` 로 교체.

```
for each file in .guild/quests/*.md (sibling 제외):
    file_mtime = stat(file).mtime
    db = SELECT id, cached_mtime FROM quests WHERE slug = ?
    if db is None:                          # 신규 파일
        parse + INSERT (cached_mtime = file_mtime)
    elif file_mtime > db.cached_mtime:      # 외부 편집
        parse + UPDATE (description / frontmatter 전 필드 + cached_mtime)
    # else: skip — DB 가 정확

for each db_row (alive):
    if 해당 파일 사라짐:
        soft delete (또는 hard, 정책 선택)
```

`.guild/statuses/*.toml`, `.guild/types/*.toml`, `.guild/tags/*.toml`,
`.guild/campaigns/*.md`, `{slug}.comments.md`, `{slug}.memo.md` 도 동일 패턴.

### Phase 2 — Lazy detail refresh (선택, 안전망)

Detail 페이지 read 시:
- file mtime > db.cached_mtime → 그 한 파일만 re-parse + UPDATE.
- 세션 중 외부 편집 추가 보호 (Phase 1 은 startup 한 번).

비용 매우 작음 (페이지당 한 파일 stat + 비교).

### Phase 3 (선택) — 풀 reindex 보존 + 의미 명시

`reindex()` 는 유지하되 용도 한정:
- Admin "Reindex" 버튼 (DEV-120 로 자동 새로고침까지).
- DB 손상 의심 시 manual recovery.
- 마이그레이션 (예: 새 컬럼 추가 후 재계산).

startup 경로에선 호출 X.

## 시간 비교의 timezone 안전성 ⚠️ (중요)

비교 양쪽이 **timezone-independent absolute time** 이어야 함. 한쪽이 local time / 다른 쪽이 UTC 면 길드를 다른 PC 로 옮기거나 사용자가 TZ 변경 시 오작동.

### Storage 결정

`cached_mtime` 컬럼 타입 두 후보:

| 후보 | 형식 | TZ 안전 | 비교 |
|---|---|---|---|
| **(권장) INTEGER (Unix nanoseconds)** | 절대 시각 (epoch 기준) | ✅ TZ 무관 | `file_mtime_nanos > db.cached_mtime_nanos` |
| RFC 3339 string with offset | 예 `2026-06-09T02:00:00+09:00` | ✅ (parse 가 절대 시각 변환) | parse → DateTime → 비교 |
| naive ISO string (no offset) | 예 `2026-06-09T02:00:00` | ❌ ambiguous | 사용 금지 |

INTEGER nanos 가 가장 빠르고 안전 — parse 부담 0. 다른 컬럼들 (`created_at` / `updated_at`) 은 RFC 3339 string 으로 일관 유지하더라도 `cached_mtime` 만 INTEGER 가 적절 (사람이 직접 SQL 로 inspect 할 일 거의 없음).

### File mtime 획득

Rust `std::fs::metadata(path)?.modified()?` → `SystemTime`. `duration_since(UNIX_EPOCH)?.as_nanos() as i64`. 모든 OS 에서 epoch 기준 절대 시각. local time / TZ 영향 없음.

### 엣지 케이스

1. **clock skew (사용자 시계 변경)**:
   - 시계 뒤로 → 파일 mtime > db.cached_mtime 잘못 판정 → 불필요 re-parse 한 번 (harmless).
   - 시계 앞으로 → 모든 row 가 stale 처럼 보임 → 한 번 풀 re-parse (느리지만 정확).
2. **FAT32 등 2초 정밀도**: 같은 초 안 편집은 못 잡음 — admin "Reindex" 로 우회. NTFS / APFS / ext4 는 sub-second 라 무관.
3. **mtime 보존 복사 (git checkout, rsync -t, file copy)**: 파일 변경됐는데 mtime 이 옛것일 수 있음. 가장 위험. 완화:
   - 첫 차원: admin Reindex 버튼.
   - (선택) `cached_size` 컬럼 추가 → size 도 다르면 변경 판정. 거의 모든 의미 있는 변경은 size 변함.
   - (선택) content hash — 가장 정확이지만 read 비용 = 결국 parse 비용에 가까움.
4. **타임존 변경 (여행 / DST)**: SystemTime epoch 기준이라 무관. RFC 3339 string 도 offset 가지면 무관. naive string 만 위험.

## 마이그레이션 0015 안

```sql
ALTER TABLE quests              ADD COLUMN cached_mtime INTEGER NOT NULL DEFAULT 0;
ALTER TABLE quest_statuses      ADD COLUMN cached_mtime INTEGER NOT NULL DEFAULT 0;
ALTER TABLE quest_types         ADD COLUMN cached_mtime INTEGER NOT NULL DEFAULT 0;
ALTER TABLE quest_tag_defs      ADD COLUMN cached_mtime INTEGER NOT NULL DEFAULT 0;
ALTER TABLE campaigns           ADD COLUMN cached_mtime INTEGER NOT NULL DEFAULT 0;
ALTER TABLE quest_comments      ADD COLUMN cached_mtime INTEGER NOT NULL DEFAULT 0;
ALTER TABLE quest_memos         ADD COLUMN cached_mtime INTEGER NOT NULL DEFAULT 0;
```

DEFAULT 0 → 첫 startup 에 모든 row 가 "0 < file_mtime" → 전체 re-parse 한 번. 그 뒤로는 mtime 비교가 효력. (대안: 마이그레이션 안에서 현재 파일들 mtime 으로 backfill — 더 빠르지만 마이그레이션 코드가 fs 의존, 복잡도 ↑.)

또는 별도 정규화 테이블 `cache_meta(table_name, row_id, cached_mtime_nanos)` — 정규화 좋지만 join 비용. 컬럼 추가가 더 단순.

- **BUG-049 / BUG-059 의 부담 해소**: startup < 50ms 보장.

  - `incremental::sync_changed_files` 가 그 역할 흡수.
  - `app_meta` 테이블은 다른 용도로 확장 가능 (계속 유지).
- **풀 `reindex()` 동작 변경 없음** — admin / 손상 복구 용도로 유지.
