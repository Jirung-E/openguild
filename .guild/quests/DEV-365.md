## 요청

`openguild quest new` 에 **선행 퀘스트 지정 옵션**(`--prereq`)을 추가한다.

## 배경 — [[DEV-361]] 과 **완전히 같은 구조의 문제**

지금 `quest new` 는 `--parent` 는 받지만 `--prereq` 는 없다. 선행 관계를 걸려면
생성 후 `quest prereq add` 를 따로 실행해야 한다.

DEV-361 에서 토론 댓글이 정확히 이랬다 — `comment add` 에 `--discussion` 이 없어
2단계를 밟아야 했고, 그래서 작성자가 1단계만 하고 본문에 `[[토론]]` 말머리를
붙이는 오용이 반복됐다. **한 번에 만드는 경로가 없으면 사람은 그 단계를
건너뛴다.**

같은 일이 실제로 일어났다: 강화 검색 후속 3건([[REQ-010]] / [[REQ-011]] /
[[REQ-012]])을 만들면서 본문에 `[[REQ-009]]` 만 적고 **선행 관계를 안 걸었다.**
본문 링크는 읽는 사람을 위한 것일 뿐, 보드의 의존성 그래프 / 트리 /
`--has-prereq` 필터 어디에도 안 잡힌다 — 보드에서는 셋이 아무 관계 없이 떠 있는
것처럼 보였다.

## 제안

```bash
openguild quest new --type REQ --title "..." --prereq REQ-009
openguild quest new --type REQ --title "..." --prereq REQ-009,REQ-002   # 다중
```

- 값은 쉼표 구분 다중 허용(`--parent` 는 단일이라 그대로).
- 존재하지 않는 slug 는 **에러** — 조용히 무시하면 "왜 안 걸렸지" 로 이어진다.
- 자기 자신 / 순환 참조 방어가 `quest prereq add` 에 이미 있는지 확인하고,
  없으면 같이 처리한다.
- HTTP `POST /api/quests` 에도 같은 필드를 받아 파리티를 맞출지 판단
  (DEV-361 은 CLI 만 했다 — 사용자 결정).

## 함께 할 것 — 문서

[[DEV-361]] 때 배운 대로, **플래그만 추가하고 문서를 안 고치면 같은 오용이
반복된다.** 이미 스킬 2곳에 "연관은 생성 그 자리에서 건다" 를 넣어 뒀으니,
`--prereq` 가 생기면 그 예시를 새 문법으로 갱신할 것:

- `.agents/skills/openguild-workflow/SKILL.md`
- `skills/openguild-plugin/skills/openguild/SKILL.md`

## 테스트 방법

1. `quest new --prereq <기존ID>` 로 만들고 `quest show` 에 선행이 잡히는지.
2. 쉼표로 여러 개 지정했을 때 전부 걸리는지.
3. 없는 slug 를 주면 에러로 막히는지.
4. 보드에서 의존성 엣지가 그려지는지 / `quest list --has-prereq` 에 잡히는지.

## 수정 내용 (2026-08-21)

`quest new --prereq <slug>[,<slug>...]` 추가.

- **생성 전에 slug 를 전부 해석한다.** 만든 뒤 없는 slug 를 발견하면 관계 없는
  퀘스트만 남아 사용자가 뒤처리를 해야 한다. 하나라도 없으면 **생성 자체가
  막힌다.**
- 연결 실패는 **에러로 알린다** — 조용히 넘어가면 "걸었다고 생각했는데 안 걸린"
  상태가 되어 원래 문제로 되돌아간다.
- 사람이 보는 출력에 `선행 + DEV-001, DEV-002` 한 줄 추가. **JSON 은 스키마를
  바꾸지 않았다** — 생성 응답은 `QuestRow` 이고 거기엔 `prerequisites` 필드가
  애초에 없다(그 정보는 `quest show` = `QuestDetail` 에 있다). 키를 새로 넣으면
  파싱하는 쪽이 깨질 수 있어 사람이 읽는 쪽만 보완했다.

문서를 두면 같은 오용이 반복된다.

### 검증 중 내가 낸 오해

처음엔 생성 응답 JSON 에 선행이 안 보여 "연결이 안 됐다" 고 판단하고 재조회
코드를 넣었다. 그런데 `QuestRow` 에는 `prerequisites` 필드가 **원래 없었고**,
빈 배열처럼 보인 것은 내 검증 스크립트의 `or []` 탓이었다. 실제로는 처음부터
정상 연결돼 있었다 — 재조회는 되돌리고 출력 문구만 남겼다.
