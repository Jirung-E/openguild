문서가 분명히 존재하는데 이미 본문에 적혀 있는 cross-link 가 **빨간색(미존재)**
으로 표시된다.

## 재현 조건 (사용자 보고)

- 자동완성이 아니라 **이미 적혀 있는 cross-link 를 볼 때** 발생.
  (자동완성 쪽은 미확인)
- 해당 문서로 **들어갔다 나오면 해소**됨.
- **새로고침으로는 해소될 때도 있고 아닐 때도 있음** — 레이스 성격.
- 퀘스트/도서관 문서 **종류 무관**하게 발생.

## 기존 수정과의 관계

DEV-256 에서 "인덱스 적재 전에 렌더되면 missing 으로 영구 고착" 레이스를
고쳤다 — anchor 에 `data-xtoken` 을 남기고 `$questIndex` 변경 시 재-resolve.
그 경로는 살아 있으므로, 이번 건은 **인덱스 자체가 비어 있거나 그 문서가
인덱스에 없는** 경우로 보인다.

## 유력 원인 (조사 중)

`stores/questIndex.ts` 의 `loadQuestIndex()`:

```ts
const [quests, campaigns, rules, books] = await Promise.all([
  questsApi.list(),
  campaignsApi.list(),
  rulesApi.list().catch(() => null),   // 개별 catch 있음
  libraryApi.list().catch(() => null), // 개별 catch 있음
]);
```

- **quests / campaigns 에는 개별 catch 가 없다.** 둘 중 하나라도 실패하면
  `Promise.all` 이 reject → 바깥 catch 가 삼키고 **인덱스가 통째로 빈 채**로
  남는다(`loaded` 도 true 가 안 됨).
- 실패가 **조용하다**(catch 주석: "보조 기능 — 실패 시 빈 인덱스 유지").
  콘솔 경고조차 없어 진단이 안 된다.
- 이후 다른 MarkdownView 가 마운트되면 `loadQuestIndex()` 를 다시 호출해
  재시도하므로 **"문서에 들어갔다 나오면 해소"** 와 정확히 일치한다.
- 앱 시동 직후엔 백엔드 준비/시동 sync 와 겹쳐 일시 실패 가능성이 있어
  **"새로고침 시 될 때도 안 될 때도"** 도 설명된다.

## 확인 필요

1. 실제로 인덱스가 비어 있는지(특정 ID 만 빠진 게 아니라).
2. 어느 fetch 가 실패하는지(네트워크 탭/콘솔).
3. limit/페이지네이션은 원인이 아님 — `/api/quests` 는 기본 limit 이 없고
   실제로 472건 전부 반환하는 것을 CLI 로 확인했다.

## 원인 (조사 완료)

인덱스가 **세션당 1회만 적재(memo)** 되고, 실패·부분실패·노후화가 전부 그
상태로 굳는 구조였다. 세 갈래인데 뿌리는 하나다.

1. **부분 실패가 전체 실패로** — `quests`/`campaigns` 에는 개별 catch 가 없어
   하나만 실패해도 `Promise.all` 이 reject → 바깥 catch 가 삼키고 인덱스가
   통째로 빈 채 남았다.
2. **부분 실패인데 memo** — `rules`/`library` 는 개별 catch 로 `null` 이 되지만
   그래도 `loaded = true` 였다. 그 종류의 링크는 **세션 내내 빨강 고착**
   (도서관 문서에서 발생한다는 보고와 일치).
3. **노후화** — 이 프로젝트는 GUI 를 켜둔 채 CLI/에이전트가 문서를 계속
   만든다. 나중에 생긴 문서를 가리키는 링크는 인덱스에 없으니 빨강인데,
   재적재 트리거가 reindex 버튼 / 규칙·도서관 페이지의 일부 동작 뿐이었다.
   → "문서에 들어갔다 나오면 해소"(그 페이지가 강제 재적재를 호출) 와
   "새로고침은 될 때도 안 될 때도"(전체 새로고침은 모듈 상태가 초기화돼
   재적재되지만, 그 시점 이후 만들어진 문서는 다시 빨강) 이 정확히 설명된다.

게다가 실패가 **완전히 조용**해서(주석: "보조 기능 — 실패 시 빈 인덱스 유지")
진단 자체가 불가능했다.

`/api/quests` 의 페이지네이션은 원인이 아니다 — 기본 limit 이 없고 실제로
472건 전부 반환하는 것을 확인했다.

## 수정

`stores/questIndex.ts`:
- 네 소스 **모두 개별 catch** — 부분 실패가 전체를 날리지 않는다.
- **전부 성공했을 때만 `loaded = true`** — 하나라도 실패하면 다음 호출이 재시도.
- 실패한 종류는 **이전 인덱스 값을 보존** — 일시적 실패가 이미 잘 보이던
  링크를 빨갛게 만들지 않는다.
- 실패 시 `console.warn` — 조용한 실패 금지.
- `refreshIndexForMissing()` 신설: 쿨다운(15초) 안에서 1회 강제 재적재.

`components/MarkdownView.svelte`:
- 렌더 결과에 `a.xlink.missing` 이 하나라도 있으면 `refreshIndexForMissing()`
  호출 → 성공 시 `$questIndex` 갱신 → DEV-256 의 재-resolve 경로로 자동 파랑.
  진짜 없는 링크는 그대로 빨강이고, 쿨다운 때문에 매 렌더마다 네트워크를
  때리지 않는다.

## 검증

- 신규 단위 테스트 7건(`questIndexLoad.test.ts`) — 부분 실패 내성, 재시도,
  이전 값 보존, 경고 출력, 쿨다운 1회.
- 프론트 테스트 308건 통과, `svelte-check` 0 errors / 0 warnings.
- 브라우저 실기: 서버로 앱을 띄워 링크가 파랑으로 정상 표시되고 href/title 이
  맞는 것 확인.

**미검증**: "인덱스가 노후한 상태에서 missing → 자가 치유" 전 과정은 SPA
상태를 런타임에 만들기 어려워 단위 테스트로만 고정했다. 실기 확인 필요.

   열어도 네트워크 요청이 쿨다운대로 억제되는지(개발자도구 네트워크 탭).
3. 도서관 문서(BOOK-NNN) 링크에서도 동일한지.
4. 서버를 잠시 내렸다가 올린 뒤 문서를 열면, 인덱스가 재시도로 복구되는지
   (예전엔 세션 내내 빨강).
5. 콘솔에 적재 실패 경고가 남는지.
