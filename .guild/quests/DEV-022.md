현재 restore 는 snapshot 만 복원. journal.db 의 ops 를 시간순 적용해 snapshot 이후 시점도 복원 가능하게

## 구현 (완료)

`core/src/replay.rs` — `replay_to(store, snapshot, target_ts)`:
1. restore 전 현재 index.db 에서 `id → slug` 맵 확보 + journal ops 메모리 로드.
2. 최신 snapshot restore (파일 → snapshot 상태, reindex).
3. `replaying` 플래그 on (auto-snapshot 억제 — replay 중 journal truncate 방지).
4. `ts <= target` ops 를 dispatcher 로 재적용. id 는 `id→slug→현재 id` 로 재매핑
   (reindex 가 id 를 새로 부여하므로 필수). campaign_id 도 동일.
5. journal truncate (복원된 시점 = 새 baseline).

노출: CLI `backup restore --at <ISO8601-UTC>`, HTTP `/api/admin/restore` `at`.

### 범위 / 한계 (의도적 fail-loud)
journal 은 **감사 로그**라 일부 op 은 내용(body)을 저장하지 않음 → replay 불가:
- **내용 미기록**: 댓글/메모 본문(`add/update_comment`, `set_memo`, `set_comments`,
  `create/set_rule`, `set_rules`) — `len` 만 기록.
- **type 변경**(`change_quest_type`) — slug 가 바뀌어 안전 매핑 불가.
- **첨부**(`save/add/remove_attachment`) — 바이너리/외부 파일 의존.

이 op 들이 낀 시점 범위는 조용히 부분복원하지 않고 **명확히 거부**(full snapshot
restore 안내). replay 가능: quest op 전체, 댓글 토글/반응/삭제, 캠페인 구조 op
(링크/체크리스트/생성·수정·삭제).

후속(범위 밖): 완전 replay 를 위한 journal 풀-페이로드 기록(별 quest), GUI(Tauri)
시점 복원 명령.
