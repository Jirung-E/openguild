## 왜 스크립트가 필요한가

JSON 만으로는 **"어떤 이벤트를 보낼지"** 와 **"어떤 모양으로 보낼지"** 를
표현할 수 없다. "미해결 토론 댓글만 AI 에 보낸다" 같은 것이 실제 요구다.
여기서 조건 문법을 발명하기 시작하면 결국 DSL 을 만들게 된다.

## 왜 rhai 인가 (JS 를 접었다)

이 저장소에 JS 런타임이 없다(확인함). CLI 에서도 돌리려면 3개 바이너리에
새로 넣어야 하고, **AI 를 부르려면 스크립트에 네트워크를 줘야 하니 샌드박스가
무의미해진다** — 셸과 위험이 같아지면서 엔진 값만 치른다.

rhai 는 순수 Rust 인터프리터라 core 에 넣어도 이질적이지 않다. 결정적으로
**I/O 를 안 줘도 된다.**

## 핵심 제약 — rhai 에 I/O 를 주지 않는다

```
rhai        판단·가공만. 파일도 네트워크도 없다. 순수 함수.
코어        내보내기(post/run)를 담당.
```

이 분리가 이 설계의 전부다. 스크립트가 폭주해도 밖으로 못 나간다. 네트워크가
필요한 순간 코어의 액션으로 넘긴다.

```rhai
// transform.rhai
fn should_send(event) {
    event.name == "comment.added" && event.comment.discussion
}
fn payload(event) {
    #{ text: `[${event.quest.id}] ${event.comment.author}: ${event.comment.body}` }
}
```

## 정해야 할 것

- **폭주 방지** — 무한 루프를 막을 연산 상한 / 시간 제한. rhai 가 지원하는
  범위를 확인해 반드시 건다. 안 걸면 스크립트 하나가 CLI 를 멈춘다.
- **오류 처리** — 스크립트가 던지면 그 이벤트만 건너뛴다. 길드 동작에 영향
  없어야 한다.
- **바이너리 크기** — 3개 바이너리에 들어간다. 현재 CLI 16MB / 서버 13MB.
  **넣기 전과 후를 실측**하고, 감당 못 할 수준이면 이 서브퀘스트를 재검토한다
  (계약과 배선은 rhai 없이도 성립하므로 되돌릴 수 있다).

## 테스트 방법

- `should_send` 가 false 면 액션이 호출되지 않는다.
- `payload` 가 만든 모양이 그대로 전달된다.
- 스크립트가 던져도 다른 플러그인과 길드 동작이 멀쩡하다.
- **무한 루프가 상한에 걸려 멈춘다** — 이게 안 되면 넣으면 안 된다.
- 스크립트에서 파일/네트워크 접근이 **불가능**하다(샌드박스 확인).
- 바이너리 크기 증가분 기록.
