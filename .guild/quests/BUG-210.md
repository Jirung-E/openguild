admin 보고: WebView2 가 메모리를 300MB 넘게 쓴다. 측정 결과 Chromium 기본
오버헤드가 아니라 **우리 프런트엔드가 라우트 이동마다 대용량 데이터를
재적재**하는 문제였다.

## 측정 (실측, 로컬 서버 + 실제 길드 531 퀘스트)

- 프로세스: renderer 354MB / browser 139MB / gpu 125MB / utility 59MB,
  Rust 본체는 58MB. (같은 PC 의 Windows SearchHost 도 자체 WebView2 366MB —
  WebView2 는 OS 공용 런타임)
- SPA 라우트 이동 115회에 JS 힙 12MB → 260MB, GC 후 바닥값도 계속 상승.
  이동 1회당 약 2.5MB.
- fetch 계측: 이동 16회에 18.4MB 수신 = **이동당 1.15MB**.
  URL 별로는 `/api/quests` 가 압도적 — 1회 응답 **1,127KB**.
  힙 증가(2.5MB/이동) ≈ JSON 파싱 결과(보통 원본의 2~3배)와 일치.

## 원인 1 — 목록 적재 경로에서 인덱스를 강제 재적재

`routes/library/+page.svelte:261` 과 `routes/rules/+page.svelte:77`
이 **일반 목록 로드 함수 안에서** `loadQuestIndex(true)` 를 부른다.
주석은 "목록 변동(생성/삭제/제목변경) 시 재적재"라고 돼 있지만 실제로는
**페이지에 들어갈 때마다** 실행된다. `force=true` 라 memo 를 무시하고
quests/campaigns/rules/library 4종을 통째로 다시 받는다.

실측 확인: /rules ↔ /library 왕복 시 `/api/quests` 호출이
rules 진입 0회, **library 진입마다 1회** — memo 자체는 정상 동작 중이고
강제 재적재만 문제.

## 원인 2 — cross-link 인덱스가 필요 없는 본문까지 받는다

인덱스는 `quest_id` + `title` 만 쓰는데 `/api/quests` 는 description 을
전부 싣는다. 531건 평균 1,095자 → 응답 827KB 중 약 580KB 가 본문이다.
정상적인 1회 적재조차 필요량의 20배 이상.

## 수정 방향

1. (프런트) 강제 재적재를 **변경 발생 시점**으로 옮기고, 마운트 시엔
   memo 되는 `loadQuestIndex()` 를 쓴다.
2. (서버+프런트) 인덱스 전용 경량 응답 — 본문 없이 id/title 만.
3. 1·2 적용 후 잔여 보존(GC 후 바닥값 상승)을 재측정한다.
