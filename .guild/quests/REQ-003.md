전체 코드베이스 리뷰에서 두 리뷰어가 독립적으로 같은 근본 원인에 도달. 검증 완료.

## 근본 원인 — lock.rs 가 아무도 안 쓴다

`core/src/lock.rs` 는 `LockGuard` 를 구현하고 `core/src/lib.rs:20` 에서
`pub mod lock;` 으로 노출되어 있지만, **workspace 전체(core/cli/server/gui)에서
호출부가 0건이다.** 모듈 doc 은 "동시 mutation 방지" 를 표방하는데 실제로는
어디에도 적용되지 않았다.

검증: `grep -rn "LockGuard" core cli server gui` → lock.rs 자기 자신 외 0건.

그 결과 read-modify-write 경로 전부가 무방비다.

## 파생 결함

### 1. change_status 가 soft-deleted 퀘스트를 건드리고 실패를 보고 (독립 버그)

`core/src/services/quests.rs:906`:
```sql
UPDATE quests SET status_id = ?, updated_at = ? WHERE id = ?
```
`deleted_at IS NULL` 필터가 없다. soft-deleted 행도 실존하므로
`rows_affected == 1` → 조기 return 안 함 → 이후 `fetch_by_id`(:1251, 이쪽은
`deleted_at IS NULL` 필터 있음)가 NotFound 반환.

**순효과: 삭제된 퀘스트의 status/updated_at 이 실제로 바뀐 뒤 호출자에겐
"없음" 이라고 응답한다.** 형제 메서드(`update`/`set_due_dates`/`change_parent`)
는 전부 먼저 `fetch_by_id` 하므로 이 함수만 예외다. 이건 락과 무관한 단독
수정 가능 건 — 먼저 고쳐도 된다.

### 2. library allocate_number TOCTOU — 문서 소실

`core/src/repo/library.rs:249`. read counter → 파일 max 스캔 → +1 → write.
`create_book`(core/src/ops/library.rs:257)에서 직렬화 없이 호출.
동시 2건이면 둘 다 N+1 을 계산하고 두 번째 `BookFile::write` 가 첫 문서를
덮어쓴다 → **문서 영구 소실.**

주의: 이 함수의 `max(카운터, 실존최대)+1` 공식 자체는 [[BOOK-001]] 의 A2
처방(파일-로컬 heal)을 정확히 구현한 것이라 설계 위반이 아니다. **빠진 건
동시성 보호뿐.**

### 3. rules self-heal 이 동시 편집을 덮어씀

`core/src/repo/rules.rs:203` `parse_backfilled` 는 읽기 경로
(`list_rules`:194, `read_rule_entry`:240)에서 호출되는데, frontmatter 만
패치하지 않고 **stale `raw` 스냅샷의 body 까지 통째로** `write_rule_file` 한다.

레거시(DEV-182 이전) 규칙 파일에서 GUI 목록 새로고침이 사용자 저장과 경합하면,
`write_rule` 이 Ok 를 반환한 뒤 옛 본문이 되써진다 → **저장 내용 소실.**
파일당 최초 1회 창이지만 실재한다.

### 4. sync_type_counter_file TOCTOU

`core/src/ops/quests.rs:120`. SQLite 카운터 트랜잭션 **바깥**에서 read/compare/
write 하므로 디스크 카운터가 역행할 수 있다(자기 주석이 보장한다는 단조증가
위반).

### 5. 사이드카 lost-update 다수

`ops/comments.rs`(반응/토론/resolved/pinned 토글), `services/comments.rs`,
`ops/campaigns.rs`(체크리스트), `ops/attachments.rs` 전부 전체 읽기 → 메모리
수정 → 통째 덮어쓰기. 같은 퀘스트에 동시 2건이면 한쪽이 조용히 사라진다.
(GUI 탭 2개, 또는 GUI + CLI 동시)

## 접근 제안

1 번은 단독으로 즉시 수정. 2~5 는 `LockGuard` 를 실제로 채택할지, 아니면
경로별로 원자적 쓰기/CAS 를 쓸지 먼저 결정 필요 — 결정 후 개별 서브퀘스트로
쪼개는 편이 좋아 보인다.
