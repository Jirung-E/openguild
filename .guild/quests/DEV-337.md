admin 질문: 서버 첨부 업로드 최대 크기가 왜 64MB 인가.

## 조사 결과: **근거가 이미 사라진 상한이다**

`server/src/routes/attachments.rs:27` 의 주석이 이유를 밝히고 있다:

> 무제한으로 두지 않는 이유: 첨부는 `attachment_blobs` 로 index.db 에도
> 복사되므로(DEV-284) 스냅샷 용량이 같이 커진다.

그런데 **BUG-188 에서 첨부 blob 백업을 통째로 없앴다** — 마이그레이션 0029 가
`attachment_blobs` 테이블을 drop 했고, 스냅샷도 attachments 를 제외한다.
즉 이 상한의 명시된 근거는 더 이상 존재하지 않는다.

## 지금 남아 있는 진짜 제약

크기 자체가 아니라 **bytes 경로가 메모리를 쓰는 방식**이다:

- 브라우저: 파일을 통째로 읽어 base64(약 1.33배) 문자열로 만들고 JSON 에 담는다.
  64MB 파일이면 JS 힙에 원본 + base64 + JSON 문자열이 겹쳐 올라간다.
- 서버: `Json<SaveAttachmentRequest>` 로 body 를 통째로 버퍼링한 뒤 디코드 —
  피크에 파일 크기의 2배 이상.

데스크톱(로컬 Tauri)은 경로 기반이라 **이 상한과 무관**하다(4MiB 버퍼 스트리밍,
BUG-168). 즉 64MB 는 "원격/브라우저에서 올릴 때만" 걸린다.

## 선택지

1. **숫자만 올린다** (예: 256MB) — 한 줄이지만 메모리 문제는 그대로 커진다.
   서버가 폰과 같은 기기에서 돌면 위험.
2. **스트리밍 업로드로 바꾼다** — `POST /api/attachments` 를 base64 JSON 대신
   `application/octet-stream` 원문 body(또는 multipart)로 받아 파일로 흘려쓴다.
   메모리가 상수가 되고 상한을 사실상 없앨 수 있다. 프런트는 XHR 로 Blob 을
   그대로 보내면 되고 진행률(upload.onprogress)도 그대로 동작한다.
   base64 왕복이 사라져 전송량도 25% 준다.
3. 그대로 둔다 — 데스크톱은 무제한이고 원격에서 64MB 넘는 첨부가 드물다면.

**2번을 권한다.** BUG-168(1.5GB 첨부)에서 이미 "통째로 메모리에 올리지 않는다"
는 방향으로 데스크톱 경로를 고쳤는데, 원격 경로만 옛 방식으로 남아 있다.

## 주의

- 기존 base64 라우트를 바로 없애면 구버전 클라이언트가 깨진다 — 새 라우트를
  추가하고 프런트를 옮긴 뒤, 한 릴리스 뒤에 정리하는 순서가 안전하다.
- DEV-332(gzip)의 압축 제외 대상에 새 업로드 라우트도 포함시킬 것.
