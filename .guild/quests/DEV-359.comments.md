## 펼침 애니메이션 추가 (사용자 요청)

먼저 CSS `transition: height` 를 걸어봤는데 **전혀 동작하지 않았다** — 접힌
상태·펼친 상태 모두 `height: auto` 라 계산값이 바뀌지 않아 전환이 시작조차 하지
않는다(브라우저에서 `getAnimations()` 가 비어 있는 것으로 확인). `interpolate-size:
allow-keywords` 도 한쪽이 길이여야 의미가 있고, 접힌 높이를 상수로 박으면 글꼴·
확대 배율에 따라 어긋난다.

그래서 **변화 전후 높이를 재서 Web Animations 로 잇는** 방식으로 갔다
(`animateHeightChange`, 120ms ease-out). 상수가 없고 엔진도 안 가린다 —
WebKit(macOS/Linux)에서도 그대로 동작한다.

호출 지점은 `$effect.pre` 다. DOM 갱신 **전에** 도는 덕분에 바뀌기 전 높이를 잴
수 있고, 키보드·호버 어느 쪽으로 선택이 옮겨가도 한 자리에서 처리된다. 펼치는
항목과 접히는 항목 **양쪽**에 건다. `prefers-reduced-motion: reduce` 면 건너뛴다.

`keepRowAnchored` 는 이제 위치가 멎을 때까지(최대 300ms) 매 프레임 따라간다 —
전환이 여러 프레임에 걸쳐 움직이므로 한 프레임만 보정하면 애니메이션 내내 행이
흘러간다.

## "반응이 느리다" — 원인 두 가지

**1. 보정 루프가 겹쳐서 서로 싸우고 있었다.** 목록을 훑으면 호버가 30ms 간격
으로 들어오는데, `keepRowAnchored` 는 호출마다 최대 300ms 짜리 프레임 루프를
새로 시작했다. 즉 한 번에 **기준점이 다른 루프가 열 개까지 동시에** 돌며 매
프레임 `scrollTop` 을 각자 다른 값으로 밀었다. 프레임마다 강제 레이아웃이
그만큼 반복되고, 스크롤이 서로 되돌려져 굼뜨고 떨리게 보인다.
→ 세대(generation) 토큰을 둬서 새 호출이 들어오면 이전 루프는 다음 프레임에
스스로 물러난다. 상한도 300ms → **160ms**(전환 90ms + 여유)로 줄였다.

**2. 같은 행에 애니메이션이 쌓였다.** 빠르게 오가면 이전 높이 애니메이션이
남은 채 새 애니메이션이 얹혀, 높이가 옛 값에 붙들려 다음 측정이 어긋났다.
→ 새로 걸기 전에 그 행의 이전 애니메이션을 취소한다. 뒷정리(`collapsing`/
overflow 복구)는 **이어받은 쪽만** 하도록 WeakMap 으로 구분 — 안 그러면 옛
정리가 새 애니메이션의 상태를 걷어간다.

전환 길이도 120ms → **90ms** 로 줄였다.

## 흔들림(두 항목이 접혔다 펼쳐졌다) — 원인과 수정

브라우저에서 재현했다. 커서를 행 **경계 근처**에 두면, 항목이 펼쳐지며 아래 줄이
밀리고 → 브라우저가 새 레이아웃으로 hit-test 를 다시 해 **커서가 가만히 있어도**
이웃 항목에 `mouseenter` 를 쏜다 → 그 항목이 펼쳐지고 다시 밀리고… 가 반복된다.
실측: 커서 고정 상태에서 `elementFromPoint` 가 35 → 34 → 35 … 로 계속 바뀌었다.

스크롤 보정(`keepRowAnchored`)은 **다음 프레임**에야 돌기 때문에 이 연쇄를 막지
못한다 — 그 한 프레임 사이에 이미 hover 가 발사된다.

**수정**: 사람이 움직여 들어온 hover 는 좌표가 반드시 달라진다. 좌표가 완전히
같은 `mouseenter` 는 레이아웃이 만들어낸 것으로 보고 무시한다
(`isPointerDrivenHover`). 같은 재현 절차에서 35 로 수렴하고 더는 오가지 않는다.

**함께 고침**: `contain-intrinsic-size` 를 `auto 36px` → `36px` 로. `auto` 는
마지막 렌더 크기(펼친 58px)를 기억해서, 한 번 펼쳤던 행이 화면 밖으로 나가면
예상 높이가 달라지고 그만큼 스크롤이 흔들린다.

## 접근을 바꿨다 — 펼침이 흐름을 밀지 않는다

휠 걸림, 넘어갈 때 덜컥임, 경계에서의 떨림은 전부 **레이아웃이 움직인다**는 한
가지 원인에서 나왔다. 흐름 안에서 항목을 키우면 아래 줄이 밀리고, 그래서:

- 밀린 만큼 스크롤을 되돌려야 하고(매 프레임 목록 전체 레이아웃),
- 그 보정은 한 프레임 늦어서 그 사이 이웃 항목에 hover 가 들어가고,
- 휠로 굴리는 중에는 사용자의 스크롤과 보정이 서로 민다.

보정으로 덧대는 대신 **원인을 없앴다**: 항목의 흐름상 높이는 접힌 값으로 붙박아
두고(JS 가 인라인 height 고정), 펼친 내용만 아래로 **겹쳐 그린다**. 목록은 미동도
하지 않는다. 스크롤 보정(`keepRowAnchored`)은 통째로 제거했다.

겹치는 대상은 바로 아래 한두 줄뿐이고, 배경·그림자를 그 항목과 같은 스타일로
줘서 "항목이 자란 것"으로 읽힌다(DEV-297 이 없앤 별도 툴팁 팝업과 다르다).

곁들여: `content-visibility` 는 paint 억제(=클리핑)를 함께 걸어, 켜둔 채로는 겹친
내용이 항목 밖으로 나오지 못한다 — 펼친 항목에서만 해제한다.

겹쳐 그리기는 결국 툴팁이고 아래 항목을 가린다(admin 지적). 되돌리고, 흔들림의
실제 원인인 **"보정이 한 프레임 늦다"** 를 고쳤다.

`flushSync` 로 선택 변경을 즉시 DOM 에 반영하고, **같은 이벤트 핸들러 안에서**
스크롤 보정까지 끝낸다. 브라우저는 중간 상태를 그리지도, hit-test 하지도 않으므로
커서 밑 행이 바뀌지 않는다 → 핑퐁이 생기지 않는다.

### 순서가 핵심이었다

처음엔 `flushSync` → 보정 → 애니메이션 순으로 짰는데 그대로 흔들렸다. 실측해 보니
애니메이션이 높이를 **시작값으로 되돌리면서** 방금 맞춘 위치가 반대로 22px 어긋났다
(보정 직후 커서 밑이 35 → 34 로 바뀜). 최종 높이를 재고 **애니메이션을 먼저 건 뒤**,
그 상태의 위치로 보정해야 한다. 이후 프레임은 기존 추적 루프가 이어받는다.

## 실측 (8811)

| | 결과 |
|---|---|
| 경계(다음 행 상단 +4px)에서 6회 반복 | `35→35→35` — 핸들러 직후·애니메이션 후 모두 그대로 |
| 행 상단 3px 지점을 순차 호버(보이는 4행) | 어긋난 스텝 **0** |
| 전환 중 대상 행 top | 255px **고정**(스크롤 1072 → 1050 으로 흡수) |

이전 빌드에서는 같은 측정이 `35→34→35`(핸들러 직후 이미 딴 행) 였다.

## 남는 것 (정직하게)

위 행이 22px 줄면 **그 위쪽 내용은 어딘가로 움직인다**. 커서 밑을 고정했으므로
위쪽이 그만큼 내려오는 형태이고, 90ms 애니메이션과 함께 흐른다. 커서 근처는
정지, 위쪽은 부드럽게 정돈되는 움직임 — 이게 거슬리면 남은 선택지는 모든 행을
2줄 높이로 미리 잡아두는 것뿐이다(화면당 항목 수 감소).

테스트: `hoverSelect` 계약 4건(동기 보정, 미이동 시 무동작, 양쪽 애니메이션,
스크롤러 없을 때) + 좌표 가드. vitest 415 passed / 0 errors.
