**다시 색인하기(`reindex`)와 여는 순간의 따라잡기(`incremental::sync_on_open`)가 길드 잠금을 안 잡는다**
(2026-10-01, DEV-432 를 마치며 확인 — 코드로 봄, 재현은 고칠 때 시험으로).

- `reindex` 는 캐시(index.db)를 **비우고** 파일에서 다시 채운다. 그사이 다른 변경(다른 프로세스의 CLI,
  서버의 다른 요청)이 캐시에 쓰면 — 비우기 전에 쓴 것은 지워지고 파일에서 다시 읽히지만, 읽기가 이미
  지나간 파일에 쓴 것은 **캐시에서 빠진다**. 다음 `reindex` 까지 목록 · 검색에서 안 보인다.
- 불리는 곳: CLI `openguild reindex`, 앱 관리 화면, 서버 `/api/admin/reindex`, drift 고치기(`check --fix`).
  복원 안의 `reindex` 는 복원이 쥔 길드 독점 안이라 괜찮다(BUG-340).
- `sync_on_open` 은 앱이 길드를 열 때 바뀐 파일만 캐시에 반영한다 — 같은 까닭으로 겹칠 수 있다.
- 원래 잠금 없이 돌던 것이다(DEV-432 에서 생긴 것이 아니다). 다만 DEV-432 로 변경이 동시에 도는 일이
  늘었다.

## 고칠 것

- `reindex` · `sync_on_open` 은 길드 **독점**. 복원처럼 이미 쥔 쪽에서 부르는 경로는 잠금 없는 몸통을 부른다.
- 이 길드 기준 `reindex` 가 얼마나 걸리는지 재어 적는다 — 그동안 모든 변경이 기다린다.

## 시험

- 잠금을 쥔 동안 `reindex` 가 끝나지 않는다.
- 복원(잠금 안에서 `reindex`)이 스스로를 기다리지 않는다.

## 고침 (2026-10-01)

- `reindex` · `drift::auto_resync` · `incremental::sync_on_open` 이 길드 **독점**을 잡는다. 이미 쥔 쪽(복원,
  여는 순간의 따라잡기 안의 다시 채우기)은 잠금 없는 몸통(`reindex_locked`, `auto_resync_locked`)을 부른다.
- 측정: 이 길드 사본(퀘스트 파일 약 1,100개)에서 `openguild reindex` 0.44초(처음 한 번 1.4초) — 그동안 모든
  변경이 기다린다.
- BOOK-006 잠금 표에 더했다.

## 시험

- 문서를 고치는 동안 다시 색인하기가 끝나지 않고, 풀면 끝난다(고치기 전: 바로 끝나 실패).
- 복원과 여는 순간의 따라잡기가 스스로를 기다리지 않는다.

## 테스트 방법

사람이 볼 것은 거의 없다 — 앱에서 관리 → 다시 색인하기가 예전처럼 되고, 앱을 열 때 멈추지 않으면 정상.
