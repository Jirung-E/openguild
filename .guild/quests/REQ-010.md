## 요청

퀘스트 목록 화면의 검색에서도 [[REQ-009]] 의 강화된 검색(댓글 / 첨부 이름)을
쓸 수 있게 한다. **A 방식**(사용자 결정).

## A 방식이란

목록 검색은 **필터**다 — 타입·상태·태그·기한과 AND 로 엮이고 결과가 정렬
가능한 퀘스트 목록이어야 한다. 반면 `/api/search`(REQ-009)는 캠페인·규칙·도서관
까지 섞여 나오고 정렬 기준도 없어 그대로 붙일 수 없다.

그래서 **기존 목록 쿼리를 확장**한다:

- `GET /api/quests?search=…&in=comment,attachment` 처럼 영역 옵션을 받는다.
- 대상은 **퀘스트로 한정**하고 결과 형태는 지금과 동일 — 다른 필터와 자연스럽게
  AND 로 엮이고 정렬도 그대로 동작한다.
- 현재 `title_only` 플래그와의 관계를 정리해야 한다(`title_only` = 가장 좁음,
  기본 = title+description+slug, 여기에 comment/attachment 를 더하는 구조).

## UI

`QuestListFilter` 의 검색 그룹에 영역 체크박스를 둔다 — `댓글 포함` /
`첨부 이름 포함`. 메모는 [[REQ-009]] 결정대로 **여기서도 기본 제외**이며,
넣더라도 명시적 opt-in 이어야 한다.

기존 필터처럼 URL(`?in=`)과 localStorage 에 동기화해 새로고침/공유에도 유지되게
한다.

## 주의

- **기본 동작을 바꾸지 않는다.** 체크를 안 하면 지금과 완전히 같은 결과여야
  한다(회귀 확인 필수).
- 댓글까지 훑으면 쿼리가 무거워진다 — 목록은 페이지네이션/정렬이 걸려 있어
  REQ-009 처럼 "전부 메모리에 올려 필터" 하는 방식을 그대로 쓸 수 없다.
  SQL 쪽에서 EXISTS 서브쿼리로 거는 편이 자연스럽다.

## 테스트 방법

1. 댓글에만 있는 단어로 검색 → 체크 없으면 안 나오고, `댓글 포함` 을 켜면 나오는지.
2. 첨부 이름으로 검색 → `첨부 이름 포함` 켰을 때만 나오는지.
3. 타입/상태 필터와 함께 걸었을 때 AND 로 동작하는지.
4. **회귀** — 체크를 안 한 상태의 결과가 이전과 동일한지.
5. 새로고침 후에도 체크 상태가 유지되는지.

## 수정 내용 (2026-08-21)

### 서버 — 목록 쿼리 확장

`ListQuery` 에 `search_comments` / `search_attachments`(둘 다 `#[serde(default)]`)
추가. 켜지 않으면 **예전과 완전히 같은 SQL** 이 나간다.

- **댓글**: `EXISTS (SELECT 1 FROM quest_comments …)` 를 토큰별 OR 목록에 얹는다.
  목록은 페이지네이션/정렬이 걸려 있어 [[REQ-009]] 처럼 "전부 메모리에 올려
  필터" 할 수 없어 SQL 안에서 건다.
- **첨부 이름**: index.db 캐시가 없어(BUG-188 로 blob 폐기) SQL 로 못 건다.
  `ops::quests::list_quests` 가 사이드카를 먼저 훑어 **토큰별 매치 slug 목록**을
  만들고, 서비스는 그걸 `IN (…)` 으로 OR 에 얹는다. 사전 스캔을 ops 에 **한
  곳만** 둔 이유는 CLI/서버/GUI 세 호출부가 각자 하면 갈라지기 때문이다.
  (빈 목록이면 절을 만들지 않는다 — `IN ()` 은 SQLite 문법 오류다.)

토큰 AND 시맨틱은 그대로다 — 토큰마다 OR 후보만 늘어난다.

### CLI

`quest list --search-comments / --search-attachments`.
`quest search`(alias)에는 **넣지 않았다** — 그건 "간단히 찾기" 용이고, 넓게 훑는
건 최상위 `openguild search`(REQ-009)가 담당한다.

### GUI — 구조적 문제를 하나 넘어야 했다

퀘스트 목록은 전체를 한 번 받아 **클라이언트에서 필터**한다(`filterQuests`).
서버에 `search` 를 보내지 않으므로 위 서버 확장만으로는 화면에 반영되지 않는다.
그런데 댓글·첨부 이름은 클라이언트에 없다.

그래서 **옵션이 켜졌을 때만** 서버에 판정을 맡긴다:

- `questsApi.searchWide()` 로 매치 quest 목록을 받아 id 집합을 만든다.
- `filterQuests` 에 `serverMatchIds` 로 넘기고, 그 경우 **클라이언트 토큰 매칭은
  건너뛴다** — 두 번 거르면 댓글에만 있는 매치가 탈락한다.
- 나머지 필터(타입/상태/태그/기한)는 그대로 클라이언트에서 AND 로 걸린다.
- **디바운스 250ms** + **stale-async 가드**(늦게 온 응답이 최신 결과를 덮지 않게
  시퀀스 확인) — [[REQ-004]] 가 지적한 함정을 여기서 새로 만들지 않는다.
- 요청 실패 시 로컬 필터로 떨어진다(빈 목록을 보여주는 것보다 낫다).

### 도중에 잡은 것

- CLI 도움말에 `(REQ-010)` 을 넣었다가 **`help_output_has_no_quest_id_leaks`
  테스트에 걸렸다.** 퀘스트 ID 가 사용자 도움말로 새는 것을 막는 가드가 이미
  있었다 — 문구에서 제거했다.
- 서버를 재시작하지 않아 **옛 바이너리로 검증하다** "HTTP 만 0건" 이라고 오판할
  뻔했다. 이 저장소에서 Rust 를 고쳤으면 실행 중인 서버도 반드시 재시작해야 한다.
