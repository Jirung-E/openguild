[[REQ-024]] 에서 정한 **같은 본문 동시 편집 — 위키백과 방식**을 만든다(admin: "진행", 2026-10-02).

## 무엇

나중에 저장한 쪽이 먼저 저장한 쪽을 **조용히 덮지 않게** 한다.

```
저장 → 편집을 시작할 때 본 본문 == 지금 본문?
  ├─ 같음            → 그냥 저장
  └─ 다름 → 3방향 병합(시작할 때 본 것, 지금, 내 것) — 줄 단위
       ├─ 겹치는 줄 없음 → 조용히 합쳐 저장
       └─ 같은 줄 충돌   ├─ 앱 → 충돌 구간마다 "지금 저장된 것 / 내 것" 을 나란히 보여 고르게 (내 글은 편집기에 그대로)
                         └─ CLI/에이전트 → 저장 거부 + 0 아닌 종료 코드 + 지금 내용
```

- 대상: 퀘스트 본문, 도서관 문서 본문, 규칙 본문, 댓글 수정.
- 단일값(제목 · 긴급도 · 기한 · 상태)은 나중 값이 남는다(REQ-024 결정).
- 퀘스트는 편집하던 **번호(slug)** 도 보낸다 — 그사이 타입이 바뀌었으면 "BUG-005 로 바뀌었습니다", 지워졌으면
  "삭제되었습니다" 로 저장을 막는다. 입력 내용은 편집기에 남긴다.
- 파일에 충돌 표시(`<<<<<<<`)를 절대 안 박는다. 먼저 쓴 사람의 글은 어떤 경로로도 안 사라진다.
- 병합은 잠금 안에서 — 그 순간의 최신 본문이 "지금" 이다. journal 에는 병합된 결과를 적는다(재생 때 다시 병합하지 않게).

## 정한 것 (만들며)

- 앱은 **시작할 때 본 본문**(글자)을 보낸다 — 3방향 병합에 그것이 필요하다(옛 판을 따로 보관하지 않는다).
- CLI · 에이전트는 시작할 때 본 본문을 들고 있지 않다 — 대신 `--base-version N`(DEV-433 파일 번호)을 줄 수 있다.
  번호가 다르면 합치지 않고 **거부**한다(에이전트는 다시 읽고 다시 적용하는 게 낫다). 안 주면 예전처럼 덮는다.
- 줄 단위 비교는 `similar` 크레이트(Myers diff).

## 시험

- 겹치지 않는 두 편집(1번째 줄 / 10번째 줄)이 둘 다 남는다 — 화면에 아무것도 안 뜬다.
- 같은 줄을 둘 다 고치면 앱은 충돌 화면, CLI 는 0 아닌 종료 코드. 파일에 충돌 표시가 없다.
- 충돌 화면을 닫아도 내 글이 편집기에 남는다.
- 편집 중 타입이 바뀌면 저장이 막히고 새 번호가 안내되며, 입력 내용이 남는다. 삭제도 같다.
- 단일값은 나중 값이 남는다.

## 한 것 (2026-10-02)

- **코어** `merge.rs` — 줄 단위 3방향 병합(`similar` Myers). 한쪽만 고친 곳은 그쪽, 똑같이 고친 곳은 그대로, 같은 줄을
  다르게 고쳤거나 같은 자리에 다르게 끼워 넣었을 때만 충돌. 이웃한 줄은 충돌이 아니다. 충돌은 구간 목록으로 —
  글자에 표시를 박지 않는다.
- `AppError::EditConflict` — `text`(구간) · `stale`(번호로만 앎) · `renamed`(새 번호) · `deleted`, 지금 본문 포함.
- 저장 경로: `update_quest`(본문 · 번호 · 편집하던 번호), `update_book_with`, `set_rule_with`,
  `update_comment_entry_with`, `campaign_comments::update_entry_with`. 옛 함수는 확인 없이 부르는 얇은 겉(Composes).
  병합은 잠금 안에서, journal 에는 합친 결과.
- **서버** 409 + `{"error", "conflict"}`. **앱** `EDIT_CONFLICT::` 꼬리표 + JSON — 프런트가 같은 모양으로 푼다.
- **CLI** `quest update` · `library update` · `rule set` 에 `--base-version N` — 다르면 저장하지 않고 0 아닌 종료 코드와 지금
  내용. `quest show` 요약 · `--field version` · `library show` 에 번호를 보인다(`QuestDetail.version`).
- **화면** `EditConflictDialog` — 부딪힌 구간마다 "지금 저장된 것 / 내가 쓴 것" 을 나란히, [지금 것] [내 것] [둘 다].
  다 고르면 합친 글을 편집기에 넣는다(저장은 사람이 한 번 더). 닫아도 내 글은 편집기에 그대로. 번호가 바뀌었으면
  "새 번호로 열기(내 글은 클립보드에)". 퀘스트 본문 · 도서관 · 규칙 · 댓글(퀘스트 · 캠페인) 편집에 붙였다.
- 문서: USAGE("둘이 같은 본문을 고치면"), 스킬(에이전트 `--base-version` 흐름), BOOK-006.

## 시험

- 코어: 병합 10가지(다른 줄 · 이웃 줄 · 같은 편집 · 같은 줄 · 같은 자리 끼워 넣기 · 지움 대 고침 · 끝 줄 · 빈 시작 등),
  퀘스트 5가지(다른 줄 둘 다 남음 · 같은 줄 거부하고 먼저 쓴 글 남음 · 표시 없음 · 이름 바뀜/지워짐 거부 · 번호 거부/통과 ·
  확인 없으면 예전처럼), 도서관 · 규칙 · 댓글 합치기/거부.
- 프런트: 꼬리표 · 409 풀기, 고른 대로 잇기, 명령 인자, 충돌 화면(다 골라야 넣기 · 닫기는 안 바꿈 · 새 번호로 열기).
- 실제 서버(사본 길드): 첫 저장 200 → 다른 줄 저장 200(합쳐짐) → 같은 줄 409(구간) → 다른 번호 409 renamed.
- 사본 길드 CLI: 번호가 바뀐 뒤 `--base-version` 저장이 거부되고 지금 내용이 나온다(종료 1), 새 번호면 저장.

## 테스트 방법

앱 창 둘(또는 앱 + 웹)로 같은 퀘스트를 연다.

1. **다른 줄** — 창 A 에서 본문 편집을 열고 첫 줄을 고친다(아직 저장 안 함). 창 B 에서 같은 퀘스트의 마지막 줄을 고쳐
   저장한다. 창 A 에서 저장한다. → 아무 화면 없이 저장되고, 본문에 두 고침이 다 있으면 정상.
2. **같은 줄** — 다시 두 창에서 같은 줄을 서로 다르게 고친다. B 를 먼저 저장하고 A 를 저장한다. → A 에 고르는 화면이
   뜬다. "닫기" 를 누르면 A 편집기에 내 글이 그대로 있고, 다시 저장해 "내 것" 을 고르고 넣은 뒤 저장하면 내 글로 바뀌면
   정상. 파일(`.guild/quests/번호.md`)에 `<<<<<<<` 가 없어야 한다.
3. **타입 바뀜** — A 에서 편집을 연 채로 B 에서 그 퀘스트의 타입을 바꾼다. A 에서 저장한다. → "번호가 바뀌었습니다" 와
   "새 번호로 열기" 가 뜨고, A 편집기의 글은 그대로면 정상.
4. 도서관 문서 본문, 규칙 본문, 댓글 수정도 1 · 2 와 같이 해 본다.

## 후속 — 릴리스 전 문서 · 스킬 점검에서 (2026-11-06)

- **규칙 번호를 CLI 로 알 길이 없었다.** `rule set --base-version` 은 받는데 `rule show` 가 번호를 안 보여 줘, 파일을
  열거나 일부러 충돌을 내야 했다. `rule show --json` 에 `version` 을 싣는다(로컬 · `--remote` 둘 다, 서버
  `GET /api/rules/{slug}` 도). 도움말 · USAGE · 스킬이 번호가 어디 있는지 적는다.
- **합친 규칙을 저장한 응답이 보낸 글을 돌려줬다**(서버 · 앱). 화면은 그 응답을 다음 편집의 출발점으로 쓰므로, 합쳐진
  남의 고침이 화면에서 빠진 채 다음 저장의 기준이 됐다. 이제 파일에서 다시 읽은 본문을 돌려준다.
- **합칠 때마다 끝 줄바꿈이 사라졌다.** 비교하려고 끝 공백을 뗀 채 결과를 썼다. 결과의 끝은 내 글을 따른다(퀘스트 ·
  도서관 · 규칙 · 댓글 공통).
- 시험: `rule_show_json_gives_the_version_rule_set_takes`(CLI), `test_rule_response_carries_version_and_saved_merge`(서버),
  `merged_text_keeps_my_trailing_newline`(코어).

### 후속 테스트 방법

1. `openguild rule show <규칙> --json` 에 `version` 이 있다. 그 값으로 `rule set <규칙> --file x.md --base-version <값>` 이
   저장되고, 같은 값으로 한 번 더 하면 거부된다.
2. 위 4번(규칙 본문 1 · 2)에서 합쳐 저장한 뒤 편집기를 다시 열면 두 고침이 다 보이고, 파일 끝 줄바꿈이 그대로다.
## 후속 2 — CRLF 파일에서 거짓 충돌 (2026-11-08, 윈도우 시험에서)

- **문제:** 윈도우 메모장 등으로 저장해 줄바꿈이 CRLF 인 본문을 앱에서 고치면, 다른 줄만 고쳐도 충돌 창이 떴다. 구간도
  파일 대부분으로 넓었다. 편집기(CodeMirror)는 늘 LF 라, 시작할 때 본 글(CRLF)과 내 글(LF)을 견주면 `\r` 때문에
  모든 줄이 바뀐 것으로 보였다. 파일은 저장되지 않아 잃은 것은 없다.
- **고침:** `resolve_edit` 가 세 판(시작 · 지금 · 내 것)의 줄바꿈을 LF 로 맞춘 뒤 비교 · 병합한다. 퀘스트 · 도서관 · 규칙 ·
  댓글 공통. 합친 결과는 LF 로 저장된다(앱 · CLI 가 원래 LF 로 저장하던 것과 같다).
- 시험: `crlf_and_lf_texts_merge_by_line`(코어).

### 후속 2 테스트 방법

1. 규칙 파일을 CRLF 로 만든다(메모장 저장, 또는 `\r\n` 으로 직접 씀).
2. 앱에서 편집기를 연 채 한 줄을 고치고, 그사이 밖에서 다른 줄을 고친다(CRLF 그대로 / CLI 로 / 파일 통째로 CRLF 저장).
3. 앱에서 저장 → 충돌 창 없이 저장되고 두 고침이 다 남는다. 같은 줄을 고쳤으면 충돌 구간이 그 줄 하나뿐이다.
