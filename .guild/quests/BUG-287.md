## 증상 — 성공이라고 보고하고 데이터가 사라진다

admin: *"퀘스트의 내용 자체가 손실이 발생하는거면 큰 문제다. os수준의 파일 락이
필요할 수 있음."*

재현했다. **여러 프로세스가 같은 퀘스트를 동시에 고치면 변경이 조용히 사라진다.**

### 태그 — 퀘스트 파일 front matter (git 추적 진리원)

서로 다른 CLI 프로세스 12개가 같은 퀘스트에 **서로 다른 태그를 하나씩** 동시에 붙였다.

```
라운드 1: 12개 추가 → 남은 것 1
라운드 2: 12개 추가 → 남은 것 1
라운드 3: 12개 추가 → 남은 것 1
```

오류 출력을 버린 탓이 아닌지 따로 확인했다 — **12개 전부 종료 코드 0** 으로 끝나며
`✓ DEV-001 tags: …` 를 찍었는데 실제로 남은 건 2개였다.

### 댓글 — 사람이 쓴 글

```
댓글 12개 동시 작성 → 성공 보고 12 → 실제로 남은 댓글 4
```

**사람이 쓴 댓글 8개가 사라졌다.** 출력에 `✓ 댓글 추가: #2` 가 여러 번 찍혔다 —
여러 프로세스가 같은 상태를 읽어 **같은 번호를 발급**한 것이다.

가장 나쁜 실패 모양이다. 명령은 성공을 말하므로 **에이전트도 스크립트도 사람도
알아챌 방법이 없다.**

## 원인 — 읽기-수정-쓰기에 프로세스 간 보호가 없다

`.guild` 파일 쓰기는 대부분 **파일 전체를 읽고 → 고치고 → 전체를 쓴다.** 두
프로세스가 같은 상태를 읽고 각자 쓰면 먼저 쓴 쪽이 지워진다.

| 보호 | 범위 | 실제 |
|---|---|---|
| `store.write_lock` (tokio Mutex) | **한 프로세스 안** | 댓글·캠페인·첨부 등 일부 ops 만. `update_quest`·`set_quest_tags` 는 **안 잡는다** |
| `lock.rs` 의 `.guild/.lock` (PID 파일) | 프로세스 간 | **어디서도 안 쓴다**(시험에서만) |

[[REQ-003]] 이 댓글 동시 저장 손실(12건 중 4~5건 생존)을 고치며 **"프로세스 안에서
직렬화"** 까지만 했다. 이번 실측이 같은 숫자인 건 우연이 아니다 — 프로세스 경계를
넘으면 그 수정이 없던 것과 같다.

## 누가 동시에 쓰나 — 흔하다

- **데스크톱 앱 + 에이전트의 CLI** 가 같은 길드. 사람이 앱에서 퀘스트를 고치는 동안
  에이전트가 CLI 로 상태를 바꾸는 것은 이 도구의 기본 사용법이다.
- **데스크톱 앱 + `openguild-server`**(웹) 가 같은 길드.
- 에이전트가 여러 CLI 명령을 **병렬로** 던질 때.
- 서버 안에서 동시에 온 HTTP 요청 — `write_lock` 을 안 잡는 ops 는 **한 프로세스
  안에서도** 경합한다.

## 수정 방향

**OS 수준 권고 잠금(advisory lock)으로 모든 `.guild` 변경의 읽기-수정-쓰기를 감싼다.**

- Rust 표준 `File::lock` — 1.89 에서 안정화, 이 저장소 툴체인은 1.97.1. unix `flock`
  / Windows `LockFileEx` 를 표준이 감싸므로 **의존성도 플랫폼 분기도 없다.** [[BUG-276]]
  이 셸 `kill` 의 플랫폼 차이를 밟았던 종류를 피한다.
- 길드 단위 잠금 파일 하나(예: `.guild/.write.lock`, gitignored). 변경은 사람 속도라
  경합 비용이 무시할 수준이고, 파일 단위로 쪼개면 여러 파일을 함께 고치는 변경
  (타입 이름 변경 등)이 교착할 수 있다.
- `flock` 은 **열린 파일 기술자 단위**라, 같은 프로세스에서 따로 연 핸들끼리도
  서로 막는다 — 서버 안의 동시 요청도 함께 직렬화된다.
- 막는 호출(blocking)이므로 tokio 런타임 스레드를 묶지 않게 `spawn_blocking` 으로 잡는다.
- 쓰지 않는 `lock.rs` 는 이걸로 대체하거나 정리한다.

## 범위 확인이 필요한 것

이 퀘스트는 **태그·댓글로 재현**했다. 같은 모양(읽기-수정-쓰기)인 곳을 전수로
확인해야 한다 — 퀘스트 본문·상태·선후 관계, 캠페인, 도서관, 규칙, 첨부 메타,
체크리스트, 반응, 보드 위치([[BUG-286]]).

## 구현

### ① 잠금 — `Store::mutation_guard()` (`core/src/lock.rs`)

| 층 | 무엇 |
|---|---|
| 프로세스 안 | 기존 `write_lock`(tokio Mutex) — 먼저 async 로 기다려 blocking 스레드를 줄 세우지 않는다 |
| 프로세스 사이 | `.guild/.lock` 에 표준 `File::try_lock` (spawn_blocking 에서 폴링, 60초 넘으면 "멈춘 앱·CLI 가 없는지" 오류) |

- 경로는 옛 PID 잠금이 쓰던 `.guild/.lock` 을 그대로 쓴다 — 기존 길드의 `.gitignore`
  에 이미 있다. 파일은 **지우지 않는다**(지우면 다음 두 프로세스가 서로 다른 inode 를
  잠가 둘 다 통과한다). 옛 `LockGuard`(PID 파일, 시험에서만 쓰던 것)는 걷어냈다.
- 잠금을 지원하지 않는 파일시스템(일부 네트워크 공유)이면 경고만 남기고 프로세스 안
  보호로 진행한다 — 쓰기를 전부 막지 않는다.
- **공개 변경 진입점의 맨 앞**에서 잡는다. 검증용 읽기까지 잠금 안에 들어가야 남이 막
  바꾼 상태를 보고 판단한다.
- 재진입이 안 되므로 진입점끼리 서로 부르지 않는다. 그랬던 곳은 몸통을 쪼갰다:
  `update_type → rename_type_locked`, `update_status → rename_status_slug_locked`.
  진입점 안의 옛 `write_lock`(`sync_type_counter_file`, BUG-286 의 위치 키 이동 등)은
  교착이 되므로 뺐다.

### ② 분류 강제 — `ops/lock_coverage.rs`

ops 공개 함수 **전부**를 표에 적는다: `Guarded` / `Via(비공개 함수)` / `Composes` /
`Read` / `Helper` / `NewFile`. 소스를 읽어 확인한다:

- 새 공개 함수는 분류를 적기 전까지 실패.
- `Guarded` 는 잠금이 있고, 그 **앞에서 `store` 를 만지지 않는다**.
- 잠금을 쥔 함수가 다른 진입점을 부르면 실패(교착).
- `store.write_lock` 을 직접 잡으면 실패(다른 프로세스를 못 막는다).

분류 중 판단이 들어간 것:
- 첨부 **저장**(`save_attachment*`)은 `NewFile` — 고유한 새 이름만 만들고, 업로드
  내내 쥐면 그동안 모든 쓰기가 멈춘다. 첨부 **목록**(`add_*/remove_*_attachment`)은 잠근다.
- 배너 `set_banner_image` 는 `Composes` — `begin`/`commit` 이 각자 잠그고 사이의 복사는
  잠금 밖이다.
- `get_book` 은 `Read` — 자가 치유가 DB 캐시만 고친다.

### ③ 태그는 붙이기·떼기로

잠금만으로는 태그가 안 고쳐진다. CLI `tag add` 가 **목록 조회 → 합쳐서 전체 교체**
두 번의 호출이라, 잠금이 각 호출을 감싸도 그 사이에 남이 끼어든다. 데스크톱 화면도
들고 있던 목록으로 전체를 바꿨다.

`ops::TagEdit { add, remove }` — 잠금을 쥔 채 **지금** 목록에 적용한다. 퀘스트·도서관·
규칙 셋 다.

| 층 | 추가 |
|---|---|
| core | `edit_quest_tags` / `edit_book_tags` / `edit_rule_tags` |
| server | 같은 경로의 `POST .../tags` (기존 PATCH/PUT 은 전체 교체 그대로) |
| desktop | `edit_*_tags` 명령 + transport 매핑 |
| 화면 | 퀘스트 상세·`TagPills`(도서관·규칙)가 붙이기·떼기를 보낸다 |
| CLI | `tag add` / `tag rm` (퀘스트·도서관·규칙) |

저널에는 결과 전체가 기존 `set_*_tags` 로 남는다 — 복원 재생은 바뀌지 않는다.
`tag set` 과 새 퀘스트에 템플릿 태그를 넣는 경로는 원래 뜻이 전체 교체라 그대로다.

### 확인한 것

- **서로 다른 프로세스 12개** 시험 4종(`cli/tests/concurrent_writes.rs`) — 태그 추가,
  댓글 추가(번호 중복 없음), 퀘스트 생성, 태그 추가와 `quest update` 섞기. 3회 반복 통과.
- 되돌려 봄:
  - 파일 잠금만 끄면 4종 전부 실패(태그 5/12, 댓글 6/13, 생성은 `database is locked`).
  - 잠금은 두고 CLI 를 옛 "조회 → 전체 교체" 로 돌리면 태그 2종이 실패(1/12).
  - 두 조각이 **각각** 필요하다.
- 잠금을 쥔 채 **죽은 프로세스** — 시험 바이너리를 자기 자신으로 띄워 쥐게 한 뒤 kill,
  바로 다음 잠금이 풀린다. 잠금을 무시하게 바꾸면 이 시험이 실패한다.
- 분류 시험 되돌려 봄: `update_quest` 의 잠금을 빼면 / `update_type` 이 `rename_type` 을
  부르게 하면 각각 실패.

## 이 퀘스트 밖으로 남긴 것

- **reindex·스냅샷 복원·journal replay** 는 잠그지 않는다. 복원/replay 는 안에서 ops 를
  부르므로 겉에서 잡으면 교착이다 — 잠금 없는 내부 경로를 따로 세워야 한다.
- 템플릿 저장(`repo::save_template`)은 ops 를 거치지 않아 표 밖이다.
- 제목·본문 같은 **단일 값·자유 텍스트**의 "화면이 옛 값을 들고 저장" 은 잠금으로
  못 막는다 — [[REQ-024]].

## 테스트 방법

- 위 두 재현을 시험으로 — **서로 다른 프로세스** N개가 동시에 쓰고 N개가 전부 남는다.
- 같은 번호 발급이 안 일어난다(댓글 id 가 전부 다르다).
- 잠금을 잡은 채 죽은 프로세스가 다음 쓰기를 영원히 막지 않는다(`flock` 은 프로세스
  종료 시 OS 가 푼다).
