설계 결정 (사용자 확정): journal replay 를 별도 명령이 아니라 **restore 인터페이스에 흡수**.

- "최신 스냅샷 + 저널" = 사실상 "최신 백업". restore 목록이 개별 스냅샷들 + "최신
  (마지막 스냅샷 + 저널 replay)" 항목을 함께 노출하고, 사용자는 스냅샷 고르듯 "최신"을 선택.
- "최신" 선택 = 마지막 스냅샷 복원 후 journal.db op 를 재생 → 스냅샷을 안 떴어도 현재
  상태까지 복구. (op T 까지만 재생하면 point-in-time 도 동일 메커니즘.)

예시:
  10:00 스냅샷 S1 (저널 비워짐) → 10:00~12:00 op 3건(저널, 새 스냅샷 없음)
  restore 목록: [S1(10:00) → 3건 잃음] / [최신 = S1 + 저널 3건 → 12:00 현재]

→ CLI 의 `restore` (top-level 유지) + GUI admin 복원 UI 가 "최신" 항목을 스냅샷과 동일하게
제공. journal 은 `journal tail` 로 보기만 하고, replay 는 restore 경로에서 처리(별도
`journal replay` 명령 안 만듦).

사용자 의도 재확인(테스트 후): point-in-time(과거 특정 시점 되감기)이 주목적이 아님. 진짜 의도는 **손상 복구 / 오래된 백업 상태에서 "최신으로 복구"** — 최신 스냅샷 + journal 전체 replay → 현재 상태 재구성.

현 구현으로 그 시나리오는 이미 지원됨: `restore --at <먼 미래>` = 최신 스냅샷 + 전체 journal replay = 현재 복구. 다만 CLI 가 `--at <구체 시각>`(point-in-time)을 전면에 내세워 의도와 어긋나 보였음. **`--at latest` 키워드(DEV-210)** 가 이 UX 갭을 메움 → 그게 사실상 본 기능의 주 진입점.

truncate 관련 정정: restore 가 "무조건" journal 을 날리는 게 아님(코드 확인).
- `restore --at` (replay 경로): replay 후 journal truncate — "최신 복구"엔 올바름(상태 동일, 새 baseline). 과거 시점 복원 시에만 이후 op 영구 손실(파괴적).
- 그냥 `restore` / `--to <snapshot>`: journal 보존.

파괴성 경고/확인은 DEV-212 로 별도 등록. DEV-022 자체(replay 메커니즘)는 의도 부합 — 다만 주 진입점이 DEV-210(키워드)이라, DEV-022/DEV-210 우선순위·상태 조정은 사용자 판단 요청.
