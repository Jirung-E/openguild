## 수정

소문자화하면서 **소문자 char 인덱스 → 원문 char 인덱스** 대응표를 함께
만든다. `char::to_lowercase()` 가 한 글자를 여러 글자로 펼칠 수 있어 1:1 이
아니므로 매핑이 필요하다.

```rust
for (i, ch) in chars.iter().enumerate() {
    for lc in ch.to_lowercase() { lower.push(lc); origin.push(i); }
}
let byte_pos = lower.find(needle_lower).unwrap_or(0);
let lower_char_pos = lower[..byte_pos].chars().count();  // lower 안에서는 경계가 맞다
let char_pos = origin.get(lower_char_pos).copied().unwrap_or(0);
```

프런트의 `highlight.ts`([[REQ-014]])는 같은 함정을 "길이가 달라지면 표시를
포기" 로 피했는데, 여기는 발췌를 못 만들면 결과 자체가 쓸모없어지므로 정확히
대응한다.

## 테스트 3건

- `İ` 를 앞에 둔 긴 한글 문자열에서 **패닉하지 않고** 매치를 담는다
- **위치가 밀리지 않는다** — 패닉만 막는 걸로는 부족하다. 경계에 우연히 걸리면
  조용히 어긋난 발췌가 나온다. 정확한 문자열로 비교한다:
  `excerpt_around("İİİ 앞부분 표적 뒷부분", "표적", 6) == "…부분 표적 뒷부분"`
  (예전 구현은 `…분 표적 뒷부분` — 한 글자 밀림)
- 매치가 없으면 앞에서부터 (기존 동작 회귀)

수정 전 코드로 되돌려 **앞의 2건이 실패**하는 것을 확인했다. 세 번째는
원래 통과하는 회귀 방지용이다.

## 남는 것 — 서버에 catch-panic 계층이 없다

이번 건은 고쳤지만, 다른 패닉이 나면 똑같이 **빈 응답**으로 끊긴다. 500 도
아니라 클라이언트는 네트워크 오류로 보고, 프런트는 조용히 로컬 결과만
보여준다(이번에 "검색이 0건" 으로 보인 이유). `tower_http::catch_panic` 을
얹으면 최소한 500 + 로그로 드러난다. 범위가 달라 별도 퀘스트 후보로 남긴다.
