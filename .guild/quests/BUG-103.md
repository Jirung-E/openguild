재현(2026-07-03 실사고): git checkout master↔develop 후 첫 CLI 실행에서 mtime 기반 auto-resync 가 200+ quest 의 updated_at 을 일괄 rewrite — git 은 내용이 같아도 mtime 을 바꾸므로 mtime 단독 판정은 checkout/pull/restore 전부 오탐.

## 수정 (core/src/incremental.rs)

**내용 비교 게이트** `is_content_identical_to_db`: mtime 이 앞서도 write-back 전에 파싱 결과를 DB 캐시와 비교 — frontmatter 전 필드(title/status/urgency/parent/dates/deleted/due) + 본문 + (나머지 동일 시에만 2쿼리로) prereq/tags. **동일하면 updated_at 을 건드리지 않고 cached_mtime 만 갱신**(재감지 churn 방지), needs_full_reindex 도 안 올림.

적용 지점 2곳: sync_changed_quest_files(시동 sync — 실사고 경로) + refresh_quest_if_stale(상세 진입 lazy refresh, else 경로 cached_mtime 을 max(file,cached)로).

campaign 등 다른 캐시 엔티티는 범위 밖(같은 패턴 필요 시 후속) — 실사고는 quests 였음.

## 테스트 방법
- `cargo test -p openguild-core incremental` — 신규 회귀 테스트 `same_content_new_mtime_does_not_rewrite_updated_at`(checkout 시뮬레이션: 동일 내용 재작성→sync/refresh 모두 updated_at 불변+DB/파일 확인) 포함 전부 통과.
- 실기: 브랜치 전환(git checkout) 직후 아무 CLI 명령 실행 → `git status` 에 quest .md 대량 diff 가 **안 생기는지**. 실제 외부 편집(내용 변경)은 여전히 updated_at=mtime 보정되는지(기존 테스트 modified_file_detected_and_updated 커버).
