## 배경

Windows에서는 GUI의 Tauri updater가 NSIS를 실행하므로, [[BUG-151]]의 기존 방향대로 사용자가 설치해 둔 GUI·CLI·Server 구성요소를 함께 갱신할 수 있다. 하지만 CLI만 사용하는 사용자는 GUI를 열지 않고 같은 업데이트를 실행할 진입점이 없다.

반면 macOS와 Linux의 GUI 자동 업데이트는 `.app`/AppImage만 교체한다. CLI(`openguild`)와 Server(`openguild-server`)는 별도 설치물이므로 갱신되지 않는다.

- macOS는 [[DEV-349]]에서 사전 빌드된 `cli-server.tar.gz` 배포를 추가했지만, 새 릴리스마다 사용자가 직접 다시 받아 `/usr/local/bin`에 덮어써야 한다.
- Linux GUI 패키지(deb/rpm/AppImage)는 GUI만 포함하며, Cargo 없이 설치할 CLI/Server 사전 빌드 배포물도 아직 없다.
- [[DEV-187]]은 새 버전 확인과 안내만 다루며 실제 바이너리 교체는 범위 밖이다.

## 목표

Windows/macOS/Linux에서 다음 명령 하나로 설치된 CLI와 Server를 같은 릴리스 버전으로 갱신한다.

```text
openguild --update
```

OS별 교체 방식은 다르지만 사용자 명령은 동일하게 유지한다.

- Windows: 서명된 기존 NSIS installer를 내려받아 `/UPDATE` 모드로 실행한다. 실행 중인 CLI가 자기 exe를 직접 덮어쓰지 않는다.
- macOS/Linux: 서명된 CLI/Server tar.gz를 내려받아 Unix 파일 교체 방식으로 갱신한다.

## 범위

1. CLI 전역 `--update` 플래그가 현재 OS/아키텍처와 설치 버전을 확인하고 플랫폼에 맞는 updater 자산을 선택한다.
2. Windows에서는 `latest.json`의 서명된 `*-setup.exe`를 다운로드·검증한 뒤 NSIS `/UPDATE` 모드로 실행한다.
   - [[BUG-151]]의 정책대로 이전 설치에서 선택했던 GUI·CLI·Server만 갱신하고 선택하지 않았던 구성요소를 새로 설치하지 않는다.
   - GUI 선택 여부도 복원되는지 확인한다. 현재 BUG-151 구현이 CLI/Server만 기록한다면 `CompGui` 또는 파일 존재 fallback까지 보완한다.
   - NSIS가 `openguild.exe`를 덮어쓰기 전에 `--update`를 실행한 CLI 프로세스가 확실히 종료되도록 호출 PID 전달·대기 등 명시적인 동기화를 둔다. 단순한 실행 후 즉시 종료 타이밍에 의존하지 않는다.
   - 완료 후 GUI 자동 재실행은 강제하지 않는다. CLI에서 시작한 업데이트 결과와 재실행 안내를 installer가 명확히 제공한다.
3. Linux x64용 `openguild_<version>_linux_x64_cli-server.tar.gz`와 서명 파일을 Release workflow에서 빌드·게시한다.
4. macOS arm64의 기존 tar.gz에도 단순 SHA-256 외에 updater 신뢰 키로 검증 가능한 서명을 제공한다.
5. macOS/Linux에서는 다운로드한 아카이브의 서명, 내부 파일명, 대상 아키텍처와 버전을 검증한다.
6. macOS/Linux에서는 임시 디렉터리에 풀고 기존 CLI/Server를 백업한 뒤 같은 파일시스템에서 원자적으로 교체한다. 중간 실패 시 기존 파일을 복구한다.
7. `/usr/local/bin`처럼 현재 사용자에게 쓰기 권한이 없는 설치 위치에서는 부분 교체하지 않고 중단하며, 필요한 권한과 재실행 명령을 정확히 안내한다.
8. 실행 중인 Server 프로세스는 갱신 후에도 구버전 코드로 계속 동작할 수 있으므로, 성공 결과에 반드시 Server 재시작 필요를 표시한다. Windows에서는 NSIS가 실행 중 Server를 안전하게 처리할 정책도 검증한다.
9. CLI만 존재하거나 Server가 설치되지 않은 환경에서 Server를 조용히 새로 설치하지 않는다. 모든 OS에서 기존에 설치된 구성요소만 갱신하는 것을 기본 원칙으로 한다.

## 배포 manifest

Tauri GUI용 `latest.json`은 현재 Windows setup, macOS app, Linux AppImage URL을 담는다. Windows CLI updater는 같은 NSIS 항목을 재사용한다. macOS/Linux CLI·Server용 URL·서명·버전을 신뢰성 있게 찾을 수 있도록 다음 중 한 방식을 확정한다.

- `latest.json`에 CLI/Server용 확장 필드를 추가하되 Tauri updater와의 호환성을 검증한다.
- 또는 별도 `latest-cli.json`을 게시해 CLI 전용 manifest로 사용한다.

GitHub Release 파일명 추측이나 `latest` 페이지 HTML 파싱에 의존하지 않는다. SHA-256 파일만 같은 Release에서 함께 받는 방식은 공격자가 둘을 함께 바꿀 수 있으므로, 기존 updater 공개키로 검증하는 서명을 사용한다.

## 안전 조건

- 다운로드·검증이 끝나기 전에는 설치 파일을 변경하지 않는다.
- CLI와 Server 중 하나만 새 버전이 되는 부분 성공을 허용하지 않는다.
- 심볼릭 링크로 실행된 경우 링크 자체와 실제 설치 대상 중 무엇을 갱신하는지 일관되게 처리한다.
- 업데이트가 guild 파일이나 `~/.openguild` 사용자 데이터를 변경하지 않는다.
- 버전 다운그레이드는 기본 거부하고, 같은 버전 재설치도 기본적으로 no-op 처리한다.
- Windows에서는 실행 중 exe 자기 교체를 구현하지 않는다. GUI updater와 `openguild --update` 모두 [[BUG-151]]의 동일한 NSIS `/UPDATE` 경로를 사용한다.

## 테스트 방법

1. Windows에서 구버전 installer로 GUI+CLI+Server, GUI+CLI, CLI 전용 조합을 각각 설치한다.
2. 각 조합의 `openguild --update`가 서명된 NSIS를 `/UPDATE`로 실행하고, 설치돼 있던 구성요소만 신버전이 되며 미설치 구성요소는 새로 생기지 않는지 확인한다.
3. Windows에서 updater를 시작한 CLI가 종료될 때까지 NSIS가 기다리고 `openguild.exe` 교체가 파일 잠금으로 실패하지 않는지 확인한다.
4. Release workflow의 수동 실행 artifact에서 macOS arm64와 Linux x64 CLI/Server tar.gz 및 서명이 모두 생성되는지 확인한다.
5. macOS/Linux의 쓰기 가능한 임시 `bin`에 구버전 CLI/Server를 설치하고 `openguild --update` 후 두 `--version`이 모두 새 버전인지 확인한다.
6. 서명 변조, 잘못된 OS/아키텍처, 손상된 installer/tar.gz에서 기존 바이너리가 그대로 보존되는지 확인한다.
7. CLI 교체 성공 후 실행 중이던 Server의 동작과 재시작 후 버전을 OS별로 확인한다.
8. Server 미설치, CLI/Server 중 하나만 존재, 심볼릭 링크 실행, 설치 경로 쓰기 불가를 각각 확인한다.
9. macOS/Linux에서 교체 도중 실패를 주입해 두 바이너리가 모두 기존 버전으로 롤백되는지 확인한다.
