## 증상

Linux CI 의 `cargo (core + cli + server + gui)` job 이 **47분** 돌다가 러너째
죽었다.

```
The hosted runner lost communication with the server. Anything in your workflow
that terminates the runner process, starves it for CPU/Memory, or blocks its
network access can cause this error.
```

같은 커밋의 macOS job 은 **44초**에 통과했다. 로컬(macOS)에서도 `just test` 는
3회 연속 정상이라 재현이 안 됐다.

## 원인

`plugins::delivery` 의 `run` 액션 타임아웃 처리가 프로세스 그룹을 죽일 때
`kill(1)` 로 셸아웃하고 있었다.

```rust
Command::new("kill").arg("-KILL").arg(format!("-{pid}"))
```

`kill -KILL -1234` 의 인자 해석이 플랫폼마다 다르다.

- BSD(macOS) `kill` — `-1234` 를 **pgid** 로 받아서 그룹을 죽인다. 통과.
- procps(Linux) `kill` — 앞의 `-KILL` 을 이미 시그널로 먹었으므로 뒤의 `-1234`
  파싱이 달라서 **그룹이 안 죽는다**.

그래서 Linux 에서는 타임아웃된 자식의 **손자 프로세스가 살아남았다**. 테스트가
띄우는 건 `while true; do :; done` 이었고, 이게 러너 CPU 를 끝까지 먹으면서
job 이 47분 뒤 통신 두절로 죽었다. macOS 가 통과했기 때문에 로컬에서는
영영 안 보이는 종류의 버그였다.

## 수정

1. **셸아웃 제거, `libc::killpg` 직접 호출** (`core/src/plugins/delivery.rs`).
   자식을 `process_group(0)` 으로 띄우므로 pgid == 자식 pid 다. 플랫폼 파싱
   차이가 사라지고, 죽이려고 프로세스를 하나 더 만드는 일도 없어진다.
   `core/Cargo.toml` 에 `[target.'cfg(unix)'.dependencies] libc = "0.2"`.

2. **테스트의 무한 루프를 400회로 유계화**. 킬이 회귀하면 러너에 영원히 도는
   프로세스를 남기는 대신, ~20초 뒤 스스로 끝나고 **단언이 실패**한다.
   실측으로 24초에 종료하는 것을 확인했다.

3. **모든 CI job 에 `timeout-minutes`**. 이번에 47분을 먹은 이유의 절반은
   상한이 없었던 것이다. check.yml: cargo 20 / macos 20 / gui-frontend 15 /
   release-notes 10. release.yml: release-notes 10 / 빌드·배포 4개 60.

## 역전 테스트

`killpg` 를 되돌리면 `a_timeout_kills_grandchildren_too` 가
"직계만 죽이고 손자는 계속 돌고 있다" 로 실패한다. 확인함.

## 남는 교훈

`just test` 는 macOS 에서만 돌기 때문에 **플랫폼 분기가 있는 코드는 로컬 통과가
증거가 아니다**. 셸 유틸리티에 의존하는 코드가 그 분기의 대표적인 원천이다.
