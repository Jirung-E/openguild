## 왜

[[REQ-021]] 에서 admin 이 든 텔레그램 봇 예시의 다섯 항목 중 넷은 값을 받아
쓰면 끝인데, **전송 주기(즉시/5분/10분/30분/1시간)** 만 성격이 다르다.

```
- 봇 토큰            텍스트      → REQ-021
- 생성/상태/댓글 알림  체크박스 ×3  → REQ-021
- 전송 주기          선택상자    → 위젯은 REQ-021, 실제 동작은 여기
```

선택상자를 그리는 것까지는 REQ-021 이 한다. 고른 값대로 **실제로 모아 뒀다
보내는 것**은 지금 구조에 아예 없는 기계다.

## 지금 구조

이벤트 하나당 HTTP 한 번, 즉시, 붙잡지 않고 던진다(fire-and-forget). 전달
스레드 하나가 큐에서 꺼내 바로 보낸다.

## 필요한 것

- **버퍼** — 주기가 끝날 때까지 이벤트를 들고 있는다.
- **타이머** — 주기마다 깨워서 비운다.
- **묶은 payload** — 이벤트 여럿을 메시지 하나로 만드는 다른 모양. 지금
  `payload(e)` 는 이벤트 하나를 받는다. `payload_batch(events)` 같은 것이
  필요하고, 없으면 무엇을 보낼지 정할 수 없다.

## 제일 큰 문제 — 오래 사는 프로세스가 없다

**CLI 는 명령이 끝나면 죽는다.** 종료할 때 ~2초 drain 하는 게 전부다
([[DEV-378]]). 5분 버퍼는 **영원히 안 비워진다.**

그래서 `즉시` 가 아닌 주기는 오래 사는 프로세스에서만 의미가 있다.

| scope | 되나 |
|---|---|
| `server` | 된다 — 계속 떠 있다 |
| `gui` | 앱이 켜져 있는 동안만 |
| `cli` | **안 된다** |

## 정할 것

- **못 비운 버퍼를 디스크에 남길 것인가.** 남기면 재시작 뒤 보낼 수 있지만,
  어디에 둘지([[BUG-279]] 의 데이터 폴더가 자리다) · 언제 버릴지 · 오래된
  알림을 뒤늦게 보내는 게 맞는지를 정해야 한다.
- **CLI 에서 즉시가 아닌 주기를 고르면 어떻게 되나.** 조용히 즉시로
  떨어뜨리면 거짓말이다. 적재나 화면에서 "이 scope 에서는 안 된다" 고
  알려야 한다.
- **주기를 코어가 아는 개념으로 둘 것인가, 플러그인 설정값으로 둘 것인가.**
  설정값이면 코어는 문자열만 보고 아무것도 못 한다 — 모으는 일을 코어가
  하려면 코어의 개념이어야 한다(`action` 옆의 `deliver: { every: "5m" }`
  같은 자리).

## 선행

[[REQ-021]] — 값을 받는 자리가 먼저 있어야 주기를 고르게 할 수 있다.
