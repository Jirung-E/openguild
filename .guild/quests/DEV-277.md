# [gui] 연관 퀘스트 추가 팝업 정렬 기준 재검토

사용자 질문: 그 창에서 뜨는 퀘스트는 무슨 순서로 정렬된 것인가?

## 조사

`core/src/services/quests.rs::list_candidates` 가 `ORDER BY q.id DESC` —
`id` 는 내부 row id 라 사실상 **생성 역순(최신 생성 먼저)**.

**검색 팔레트도 같았다**(사용자 확인 요청 사항): 팔레트는
`questsApi.list()` 를 그대로 쓰는데, `quest list` 의 기본 sort 가
`("id", false)` = `q.id DESC` 라 동일하게 생성 역순.

"연관 퀘스트를 고르는" 맥락에서는 방금 만든 것보다 **최근에 손댄 것**이
위에 있는 편이 유용하다 — 오래된 퀘스트를 연결하려고 긴 목록을 뒤지는
일이 줄어든다. 검색어를 치면 어차피 필터되므로 이 정렬이 좌우하는 건
"검색 전 첫 화면"이다.

## 수정 (사용자 결정: 최근 갱신순으로)

- **팝업(candidates)**: `ORDER BY q.updated_at DESC, q.id DESC`
  (id 는 안정 정렬 tiebreaker).
- **검색 팔레트**: `questsApi.listRecent()` 신설 —
  `/api/quests?sort=updated` 를 명시 요청. CLI `quest list` 의 기본값은
  기존 스크립트 호환 때문에 그대로 두고(`--sort updated` 로 지정 가능),
  이 UI 만 다른 정렬을 요구하게 했다.

## 작업 중 발견한 별개 버그 (같이 수정)

Tauri transport 가 `/api/quests` 의 **query string 을 통째로 버리고**
있었다(`args: {}`). 서버 모드는 `Query<ListQuery>` 로 그대로 받는데
데스크탑만 정렬/필터가 무시되는 비대칭 — `list_quests` 커맨드는 이미
`query: Option<ListQuery>` 를 받으므로 전달만 하면 되는 문제였다.
이걸 안 고쳤으면 이번 정렬 변경이 **웹에서만 먹고 데스크탑에선 무시**될
뻔했다. `ListQuery` 는 `#[serde(default)]` 라 일부 키만 넘겨도 안전.
