restore --at 이 journal 을 truncate 하는 파괴적 동작 — 대화형 확인 대신(사용자 결정) **실행 직전 현재 상태를 정식 스냅샷으로 자동 백업**하고 진행. 확인 프롬프트 없이도 항상 되돌릴 수 있음.

## 구현 (2026-07-05, core/src/replay.rs)
- replay_to 1.5단계: ops 를 메모리에 확보한 **직후**·restore **직전**에 create_snapshot — 계획서의 순서 함정(스냅샷의 journal truncate 가 replay 대상을 지움) 해소: ops 는 이미 메모리, 복원 대상 스냅샷은 호출자가 진입 전 선택 완료라 '최신' 오염도 없음.
- journal 비어있으면 스킵(멱등, 잃을 것 없음).
- ReplayReport.pre_backup 필드 — CLI 출력('복원 전 상태는 스냅샷 <ts> 로 자동 백업... restore --to <ts>'로 안내, 폐기 경고 대체) + --json + HTTP /api/admin/restore 응답에 노출.
- restore-behavior 길드 규칙 갱신: --at 이 '비가역' → '자동 백업으로 가역'.
- 테스트 2건: 과거 시점 replay 후 pre_backup 으로 복원 → 폐기됐던 quest 부활 / 빈 journal 이면 pre_backup 없음+스냅샷 수 불변.

## 테스트 방법
- cargo test -p openguild-core replay — 신규 2건 포함 통과.
- 실기(스크래치 길드): quest 2개 → backup new → quest 1개 더 → restore --at <과거> → 출력에 '자동 백업' 안내 + backup list 에 새 스냅샷 → restore --to <그 ts> 로 3개째 quest 복귀.
