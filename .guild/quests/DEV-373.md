## 목표

길드의 동작에 사용자가 **자기 동작을 붙일 수 있게** 한다. 예: 새 퀘스트나
댓글이 생기면 그 내용을 AI 에 보낸다.

0.6.0 의 핵심 기능. 설계 논의 결과를 여기 정리하고 작업은 서브퀘스트로 나눈다.

## 세 층

```
① 배선 (JSON)      언제 / 어디서 / 무엇으로 내보낼지
                   on(이벤트) · scope(cli|gui|server) · action(post|run)

② 판단·가공 (rhai)  보낼 것인가, 어떤 모양으로 보낼 것인가
                   **I/O 없음** — 순수 함수. 입력 event, 출력 payload 또는 skip

③ 실제 동작 (외부)  사용자 프로그램 / 서비스. 무엇이든.
```

**코어가 소유하는 동작은 둘뿐**이다 — `post`(HTTP)와 `run`(프로세스).
"밖으로 내보낸다"의 최소 완전집합이고 나머지는 사용자 몫이다. 통합 카탈로그
(slack/discord/email…)를 코어에 쌓기 시작하면 끝없이 따라다녀야 한다.

## 이벤트는 `ops` 가 **직접 낸다** (명시적 emit)

journal 을 훔쳐보는 값싼 방법을 먼저 검토했다가 접었다. 세 가지가 걸린다:

1. **시점** — journal 은 `// 1. journal append (의도 기록)` 로 **하기 전에**
   쓴다. 뒤에서 실패해도 남으므로 **실패한 시도까지 나간다.**
2. **결과가 없다** — `journal::append` 54곳 중 **53곳이 `result` 를 `None`**
   으로 넘긴다. `create_quest` 의 args 에는 새로 부여된 `DEV-007` 이 없다.
3. **목적 충돌** — journal 은 AOF(복구 replay)라 스냅샷 때 truncate 되고
   replay 억제가 붙는다. 겸용하면 **복원 중 과거 이벤트가 쏟아진다.**

무엇보다 **journal 로는 pre/post 를 구분할 자리가 없다.** "시도 기록" 하나뿐
이라 pre 훅이 구조적으로 불가능하다.

명시적 emit 의 대가는 호출 지점을 함수마다 정해야 한다는 것인데, 그건 결함이
아니라 **자유도**다 — `create_quest` 만 해도 6단계(journal → SQL → 파일 →
counter → 부모 auto블록 → after_mutation)라 "어디가 성공인가"를 우리가 골라야
한다. journal 방식은 그 선택지를 아예 안 준다.

## 정한 것 (admin)

| 질문 | 결정 |
|------|------|
| 이벤트 출처 | **`ops` 의 명시적 emit** |
| pre 훅 | **관찰 pre 만.** 거부(veto)는 하지 않는다 — 훅이 죽으면 길드가 멈춘다 |
| 실패 | **같은 이벤트에 결과 필드**(`ok` / `error`). 이벤트 수를 안 늘리고 인자만 는다 |
| CLI 에서도 도나 | **돈다.** 단 `scope` 로 사용자가 고른다(gui 전용 등) |
| 실행 시점 | **인라인 + 비동기**(fire-and-forget) |
| 스크립트 | **rhai** — 1단계 포함. 동작을 결정하는 핵심 |
| `run` | 2단계로 미룰 수 있음 |
| 이벤트 이름 | **우리가 정의한다.** `리소스.동사` + 와일드카드 |
| 페이로드 | 내부 구조체를 그대로 흘리지 않고 **공개 모양으로 감싼다** |

### 내가 정한 기본값 (뒤집고 싶으면 한 줄이면 된다)

- **비대화형 CLI 에서 동의를 못 물으면 실행하지 않는다** — 스크립트/CI 에서
  조용히 남의 코드가 도는 것보다 안 도는 쪽이 낫다. 안내 메시지는 남긴다.
- **`plugin.json` 은 `.guild/plugins/{name}/` 안에** 둔다. `.rhai` 스크립트와
  같은 폴더 — 플러그인 하나가 폴더 하나다.
- **`pre` 에는 `ok`/`error` 가 없다.** 아직 결과가 없으니 그 필드 자체를 안
  싣는다(`false` 로 싣지 않는다 — 실패로 오해된다).
- **emit 은 함수 맨 끝**(파일·DB 쓰기가 다 끝난 뒤). 조기 return 이 있는
  경로(예: `change_status` 의 no-op)는 그 자리에서 판단한다.
- **실패 이벤트는 1단계에서 `?` 로 조기 반환되는 주요 실패만** 덮는다. 모든
  오류 경로에 emit 을 심지는 않는다.
- **누락 검사는 "planned" 목록을 함께 둔다.** 1단계는 퀘스트+댓글만 emit
  하므로 나머지 40여 함수가 전부 누락으로 잡힌다. 카탈로그에 "아직 안 냄"
  목록을 두고 거기 있으면 통과시킨다. **어느 목록에도 없는 새 함수만 실패**
  한다 — 그래야 검사가 처음부터 빨간불이 되지 않으면서 제 일을 한다.

## 비용을 줄이는 두 가지

- **구독자가 없으면 emit 은 no-op.** 플러그인 설정이 없으면 이벤트를 만들지도
  않는다. 그러면 기존 ops 테스트 429건이 부수효과를 안 갖고 성능 부담도 없다.
- **51종 전부를 1단계에 달지 않는다.** 실제로 노출할 이벤트부터 단다. 나중에
  늘려도 플러그인 쪽에서는 "이벤트가 추가됐다" 로만 보인다.

누락(새 mutation 에 emit 을 빠뜨림)은 조용한 실패이므로 검사로 막는다 —
**journal 호출은 있는데 emit 이 없는 함수**를 대조하면 된다. journal 이 이미
54곳에 강제돼 있어 좋은 기준점이 된다.

## 왜 rhai 인가 (JS 를 접었다)

이 저장소에 JS 런타임이 없다. CLI 에서도 돌리려면 3개 바이너리에 새로 넣어야
하고(GUI 만 WebView 덕에 갖고 있다 — 요구사항과 충돌), **AI 를 부르려면
스크립트에 네트워크를 줘야 하니 샌드박스가 무의미해진다** — 셸과 위험이 같아
지면서 엔진 값만 치른다.

rhai 는 순수 Rust 인터프리터라 core 에 이질적이지 않고, 무엇보다 **I/O 를 안
줘도 된다.** 네트워크는 코어의 `post`/`run` 이 태우고 rhai 는 그 앞에서
판단·가공만 한다. 그러면 샌드박스가 실제로 의미를 갖는다.

## 하지 않는 것

- **거부 pre(veto)** — 위 표 참고. 관찰만.
- **사용자 정의 CLI 명령**(`openguild ai hello`) — 다른 기능이다. 섞으면
  범위가 터진다.
- **통합 카탈로그**(slack/discord/email 액션) — "코어는 둘뿐" 참고.

# 대역 서버: RECEIVED: openguild {"text":"[DEV-002] 전달확인"}

## 계획에 없던 판단 셋 (뒤집고 싶으면 한 줄이면 된다)

**동의 지문에 스크립트 원문을 넣었다.** `plugin.json` 은 그대로 두고
`transform.rhai` 만 고치면 보내는 내용이 통째로 바뀐다 — 정의만 보는 동의는 그
구멍으로 빠져나간다.

**`run` 을 2단계로 안 미뤘다.** `Action::Run` 이 이미 정의 스키마에 있어서, 안
만들면 `run` 을 적은 정의가 적재는 되고 아무 일도 안 하는 상태가 된다. 그게
미루는 것보다 나쁘다.

**서버 동의는 HTTP 로 안 받는다.** 팀이 공유하는 엔드포인트로 동의를 받으면
"누구의 동의인가" 가 흐려지고 `run` 을 열어 주는 원격 구멍이 된다. 서버를
띄우는 사람이 그 기계에서 CLI 로 한다.

### cargo feature 로 가르지 않는다 (admin 확정)

한때 "줄이고 싶으면 `plugins` 를 cargo feature 로 뺄 수 있다" 고 적어 뒀는데,
**기술적 가능성만 보고 하면 안 되는 이유를 안 적었다.** admin 지적: *"애초에
나눌 이유가 없잖아. 사용자 필요에 따라 둘 다 써야할수도 있는데."*

`post` 를 쓸지 `run` 을 쓸지, 스크립트를 쓸지는 **길드마다·플러그인마다,
`plugin.json` 을 쓰는 사람이** 정한다. 런타임 결정이다. 컴파일 시점에 가르면
그 결정권이 사용자에게서 **패키징하는 사람에게로** 넘어간다 — `plugin-post`
없이 빌드된 서버를 받은 사람은 `post` 플러그인을 쓸 수 없고, 미리 알 방법도
소스에서 다시 빌드하는 것 말고 고칠 방법도 없다.

코드도 이미 그 조합을 정상으로 취급한다 — `Action` 은 둘 다 스키마에 있고
`script` 는 선택이며 한 길드에 섞여 있는 게 당연하다. 기능으로 가르면 "적재는
되는데 그 액션만 안 되는" 반쪽 상태를 곳곳에서 새로 다뤄야 한다. **없는 경계를
만들고 그 뒷감당을 하는 일이다.**

같은 이유로 rhai 자체를 더 깎는 것(`no_float` / `only_i64` / `no_closure`)도
안 한다 — 스크립트가 쓸 수 있는 것을 줄이는 일이라 규모만 작을 뿐 같은 실수다.
안전한 축은 "사용자가 어차피 못 쓰는 것" 뿐인데 그건 `no_module` 로 이미
가져갔다(그것도 크기가 아니라 샌드박스 목적이었다).

덧붙여, 지금 릴리스는 `cargo build --release -p openguild-cli -p openguild-server`
**한 번**이라 기능이 두 패키지에 합집합으로 통일된다. 가르더라도 빌드를 쪼개기
전에는 한 바이트도 안 줄어든다.
