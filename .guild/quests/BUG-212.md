BUG-210 후속. 이동당 남던 증가분을 GC 를 강제 유도해 다시 재보니, **대부분은
쓰레기가 아니라 진짜 누수**였고 발생처는 **보드 페이지 한 곳**이었다.

## 측정 (강제 GC 후 바닥값 비교)

- `/rules ↔ /library` 20회: 48.2MB → 48.3MB — **누수 없음**
- `/?view=list ↔ /rules` 20회: 48.2MB → 48.3MB — **누수 없음**
- `/?view=board ↔ /rules` 12회(체류 900ms): 90.7MB → 133.3MB
  = **보드 1회 방문당 7.1MB**
- 보드에 3초 체류해도 동일(방문당 7개 canvas) — 초기화 경합이 아니다.

## 확증

`document.createElement` 를 패치해 canvas 를 WeakRef 로 추적:

- 보드 5회 방문 → canvas 35개 생성, 강한 메모리 압박(약 300MB 할당/폐기)
  후에도 **35개 전부 alive**.
- 전부 `isConnected === false` — DOM 에선 떨어졌는데 JS 가 붙잡고 있다.
- 크기가 2560×1336 → 개당 백킹스토어 약 13.7MB. 5회 방문분 합계 약 392MB.
  **WebView2 renderer 가 300MB 를 넘던 실체가 이것이다**(canvas 픽셀은 JS
  힙 밖이라 usedJSHeapSize 로는 안 보였다).

## 원인 범위

- 전역 리스너/옵저버/타이머는 균형이 맞다. 보드 1회 방문의 순증은
  `window/'test'` 1건뿐(cytoscape 의 passive 지원 감지) — 이건 retainer 가
  아니다.
- 리스너 순증이 없다는 건 `cy.destroy()` 가 **실행은 됐다**는 뜻이다
  (destroy 가 window 바인딩을 해제하므로).
- cytoscape 3.33.3 의 `BRp.destroy` 는 옵저버 disconnect 와 바인딩 해제만
  하고 **`r.data.canvases` 는 놓아주지 않는다**. 따라서 renderer(→cy) 를
  누가 하나라도 붙잡고 있으면 canvas 백킹스토어가 통째로 남는다.

## 방향

컴포넌트 파기 시 보드가 쥔 큰 참조를 명시적으로 끊고(cy/컨테이너/캐시),
재측정해 방문당 canvas 순증이 0 이 되는지 확인한다.
