## 확인 결과 — 범위가 예상보다 작았다

퀘스트 본문의 "구현 전 확정할 것" 세 항목을 코드로 확인했다.

**1번(core 검색에 rule 포함)은 이미 되어 있었다.** REQ-009 가 처음부터 규칙을
넣어 뒀다 — `search.rs:180` 이 `list_rules` 를 훑고, `SearchHit.kind` 주석에도
`rule` 이 있다. 실측:

```
$ openguild search setext
rule      release-process        [body]
```

**규칙엔 댓글도 첨부도 없다** — `rule` 하위 명령이 list/show/history/set/new/
delete/rename/tag 뿐이다. 따라서 대상은 slug / 태그 / 본문 셋.

**서버 왕복이 필요 없다.** `/api/rules` 응답이 `content` 를 통째로 싣고 온다
(실측 9건 24,617자). 도서관의 첨부 이름 검색(REQ-011)이 서버에 판정을 맡긴
이유는 첨부 이름이 목록 응답에 없기 때문인데, 규칙 본문은 이미 손에 있다.
그래서 디바운스도 stale 가드도 없이 **즉시 필터**한다.

결과적으로 남은 일은 UI 하나였다.

## 구현

`lib/utils/rule-filter.ts` 신설 — 컴포넌트 안에 두면 테스트를 못 붙인다
(REQ-006 에서 같은 이유로 worklog 묶음을 뺐다).

- `filterRules(entries, query, tags)` — 검색어는 slug/태그/본문 중 하나라도
  맞으면 통과(OR), 태그 필터는 전부 가져야 통과(AND, **기존 동작 유지**).
  둘 사이는 AND.
- `matchedIn` 으로 **어디서 맞았는지** 돌려준다. slug 가 아닌 곳에서 맞았을
  때만 목록에 `본문` / `태그` 뱃지와 발췌를 보여준다.
- `excerptAround` — 문자 단위로 잘라 한글이 깨지지 않게.

발췌를 넣은 이유: 사용자가 겪은 실제 문제가 "도서관에서 DEV-001 로 검색하니
BOOK-002 가 나오는데 본문에서 못 찾겠다" 였다. 542행 문서의 287행, 줄바꿈
직전에 있었다. 이유와 발췌를 같이 보여주면 그 상황이 안 생긴다.

## 테스트

- `rule-filter` 12건 — slug/본문/태그 매치, 대소문자, 입력 순서 유지,
  태그 AND, 태그+검색어 AND, 발췌 경계·한글 안전성
- 태그 AND 필터는 이 길드의 규칙에 태그가 없어 **브라우저로는 확인 못 했다**.
  단위 테스트 4건이 기존 의미(전부 가져야 통과)를 그대로 고정한다.

`just test` 475건 통과 (48 파일), svelte-check 0 errors.
