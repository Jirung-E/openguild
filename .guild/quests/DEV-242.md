admin 질문: `.guild/types/{PREFIX}.toml` 의 `[counter] last_number` 값이
어느 순간부터 업데이트가 안 되는 것 같다.

## 조사 결과
버그가 아니라 애초에 GUI 로는 절대 갱신되지 않는 값이었음:

- 퀘스트 생성 시(`services/quests.rs::create`) DB(`quest_counters` 테이블)
  만 갱신하고 파일은 안 건드림 — 주석 "last_number 파일 sync 는 별도"가
  최초 커밋(dba05c7)부터 있던 설계.
- GUI 의 reindex(⟲) 버튼(`reindex::reindex`)은 파일의 last_number 를
  **DB 로 읽어들이기만** 하지, DB 최신 값을 파일에 **써주지 않음**
  (core/src/reindex.rs 라이브러리/퀘스트 섹션 전부 file→DB 단방향).
- 파일에 실제 값을 반영하는 유일한 경로는 CLI `openguild check counters
  --fix`(core/src/ops/counter.rs) 뿐인데, GUI 어디에도 노출된 적이 없는
  순수 수동 유지보수 명령.

실측(이 길드): BUG 파일=13/실제=134, DEV 파일=58/실제=241, REQ 파일=0/
실제=1 — 오래전부터 크게 벌어져 있었음. **퀘스트 번호 할당 자체는 DB
쪽 self-heal 로직(create_quest 의 MAX(last_number, 실제 max)+1) 덕분에
이 drift 와 무관하게 항상 정상 동작** — 이 파일 값은 순수 표시/백업용
스냅샷일 뿐 기능적 영향 없음.

## admin 반응
"이건 사실상 필요 없는 값 아닐까?" — 이 파일 카운터 값의 필요성 자체를
재검토할 여지가 있다는 의견. 당장 `--fix` 로 맞추기보다 퀘스트로
등록해서 설계를 다시 보기로.

## 검토 방향(미결정 — 다음 작업 시 결정)
- (a) 있는 그대로 두고 GUI 에 "counter 동기화" 버튼만 추가(admin reindex
  옆) — 최소 변경, drift 는 여전히 발생 가능하나 눈에 보이게 관리 가능.
- (b) reindex 가 파일 last_number 도 DB 기준으로 write-back 하도록
  확장 — reindex 시점마다 자동 정합.
- (c) 파일의 counter 섹션 자체를 제거하고 DB(quest_counters)를 유일한
  진리원으로 — file-truth-db-cache 규칙(§1: "파일에서 파생되지 않는
  값을 DB 에만 저장 금지")과 정면 충돌하므로 신중한 재설계 필요(파일이
  진리원이어야 reindex 무손실 재구축이 성립 — 카운터를 DB-only 로
  바꾸면 reindex 시 카운터 정보가 사라짐, quest 파일들에서 max(number)
  로 재계산은 가능하지만 "재사용 방지"용 단조 증가 보장이 약해짐 —
  soft-delete 된 quest 도 파일이 남아있으면 문제없지만 파일까지 지워진
  경우엔 값을 잃음).
