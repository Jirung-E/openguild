캐시 헤더 부분만 먼저 처리했다(저위험). 목록 클라이언트 캐시는 무효화 설계가
필요해 남긴다.

## 수정

**첨부 (`/api/guild-files/*`)** — `admin::get_guild_file`
- `ETag` 추가. 값은 `(파일 크기, mtime)` 조합이다. 내용 해시는 대용량 첨부
  (BUG-168 의 1.5GB)에서 매 요청마다 전체를 읽어야 해 쓸 수 없다.
- `If-None-Match` 처리 — 같으면 **본문 없이 304**.
- `attachments/` 는 `public, max-age=31536000, immutable`. 업로드마다 고유
  접미사가 붙어(BUG-219) 같은 URL 이 다른 내용을 가리키지 않는다.
- `assets/` 는 `no-cache` — 같은 이름으로 교체될 수 있다. ETag 가 있으니 안
  바뀌었으면 304 로 끝난다.

**정적 자산** — `static_cache_headers` 미들웨어
- `_app/immutable/**`: `public, max-age=31536000, immutable`. 내용 해시가
  파일명에 들어간 파일이라 안전하다.
- 그 외(`index.html` 등): `no-cache`. **오래 캐시하면 안 된다** — 안에 새 해시
  파일명들이 들어 있어, 옛 index 가 캐시되면 업데이트 후에도 옛 번들을 계속
  물고 간다.
- `/api/**` 는 건드리지 않는다 — 내용이 바뀌는 데이터다.

## 검증 (실서버)

```
첨부 1차:  200  cache-control: public, max-age=31536000, immutable
                etag: "17c8-6a5c2f92"   content-length: 6088
첨부 2차:  304  (If-None-Match 동일) — 본문 없음
_app/immutable/*.js : cache-control: public, max-age=31536000, immutable
index.html          : cache-control: no-cache
/api/quest-statuses : cache-control 없음 (기존 그대로)
gzip                : 유지됨 (content-encoding: gzip)
```

수정 전에는 첨부에 cache-control·etag·last-modified 가 **전부 없어**
`If-Modified-Since` 를 붙여도 200 + 전체 본문이 왔다.

테스트 1건 추가 — 첨부를 올린 뒤 1차 응답의 immutable/ETag 를 확인하고,
같은 ETag 로 재요청하면 304 + **빈 본문**인지까지 검사한다.
워크스페이스 737 passed, clippy 통과.
