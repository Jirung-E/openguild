window.__TAURI__ 감지 → invoke 또는 fetch. Tauri 작업의 선행.

## 테스트 방법

### 자동 (완료)
- `cd gui/frontend && npm test -- --run` → transport.test.ts 10 tests 통과 (총 51 통과)
- `cd gui/frontend && npm run check` → 0 errors
- 회귀: 기존 client.test.ts 도 모두 통과
- SSR / Node 환경: `detectEnvironment()` 가 'http' 반환 (window 없음)

### 사용자 검증 필요 (수동)

DEV-002 의 본질: **두 환경 (브라우저 / Tauri) 을 자동 감지해서 다른 transport
로 분기**. 양쪽 모두 빠르게 확인.

#### A. 브라우저 (HTTP) 경로 — 5분

터미널 2개:
```
# 1번 터미널
openguild-server host

# 2번 터미널
cd gui/frontend && npm run dev
```

브라우저로 http://localhost:5173 접속:

1. **Quest 목록이 보임** — 빈 화면이 아니라 dogfood quest 들 (DEV-001, BUG-002 등)
   이 list / board 에 표시.
2. **F12 devtools → Console 탭**:
   ```js
   (await import('/src/lib/api/transport.ts')).transport.kind
   ```
   → `'http'` 반환. (모듈 path 가 바뀌었으면 콘솔에서 import 안 될 수 있음 — 그 경우
   2 와 3 만 확인하면 됨.)
3. **devtools → Network 탭** → quest list 페이지 새로고침 (Ctrl+R) →
   `localhost:3000/api/quests` 등 fetch 요청이 보여야 함 (HttpTransport 가 작동).

#### B. Tauri (invoke) 경로 — DEV-004 완료 후 검증 가능

DEV-004 가 done 처리되면서 invoke 핸들러 23개 등록 + `TauriTransport.call` 구현
완료. DEV-002 의 환경 감지가 올바로 동작했으면 Tauri 창에서 quest list 가 표시
되어야 함.

1. 사전: `cd gui/frontend && npm run build` (한 번).
2. `cargo run -p openguild-gui` 실행 — HTTP 서버 없이.
3. **Tauri 창에 quest 27개 표시되면 DEV-002 의 Tauri 분기 OK** — 다음이 다
   동작했다는 의미:
   - `detectEnvironment()` 가 `window.__TAURI_INTERNALS__` 감지 → 'tauri'.
   - `transport` 가 `TauriTransport` 인스턴스로 결정.
   - `TauriTransport.call` 이 invoke 호출 성공 (DEV-004 의 routeToInvoke 와 함께).
4. (선택) Tauri 창 우클릭 → Inspect Element → Console:
   ```js
   (await import('/src/lib/api/transport.ts')).transport.kind
   ```
   → `'tauri'` 반환.

#### 통과 기준
A (브라우저) + B (Tauri) 모두 데이터 표시되면 DEV-002 완료.

DEV-004 검증 시 Tauri 창에 quest 가 보였다면 B 는 사실상 같이 확인된 셈
(검증 의존성: DEV-004 통과 ⊆ DEV-002 통과).
