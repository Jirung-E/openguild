## core

- `AppError::Cancelled` 추가. 서버 매핑은 499(클라이언트가 스스로 끊은 요청).
- `save_attachment_from_file_cancellable(store, src, ext, on_progress, is_cancelled)`.
  기존 `..._with_progress` 는 `|| false` 로 위임 — 호출부 변경 없음.
- 복사 루프가 **4MiB 청크 경계마다** 취소를 확인한다(반응 지연은 한 청크 이내).
- 취소 시 **조각 파일을 지운다**. 반쪽 파일이 `.guild/attachments/` 에 남으면
  BUG-168 에서 겪은 고아 파일 문제(reindex/스냅샷 깨짐)를 다시 만든다.

## 데스크톱 (Tauri)

- `UPLOAD_CANCELS: upload_id → AtomicBool` 레지스트리 + `cancel_attachment_upload`
  커맨드. 업로드 시작 시 등록하고 끝나면 반드시 제거한다.
- 이미 끝났거나 없는 id 는 조용히 무시 — 끝나는 순간에 눌러도 에러가 안 뜨게.
- `signal` 이 있으면 uploadId 경로를 타도록 했다(플래그를 걸 대상이 필요).

## 브라우저

- `postWithUploadProgress` 에 `AbortSignal` 추가 → `xhr.abort()`.
  서버가 body 를 다 받지 못하므로 첨부 자체가 저장되지 않는다(조각도 없음).
- abort 는 `DOMException('AbortError')` 로 reject — 일반 실패와 구분.

## 대기열 / UI

- 진행 중은 abort, **아직 시작 안 한 항목은 시작 자체를 막고** 바로 '취소됨'.
- 취소된 항목은 목록에 취소선으로 남는다. 무엇이 올라갔고 무엇이 안 올라갔는지가
  사용자에게 필요한 정보라, 취소가 있으면 목록을 걷지 않는다.
- 취소 버튼은 업로드가 도는 동안만 보인다.

## 검증

- core: `cancel_removes_partial_file` — 12MB 파일을 두 번째 청크에서 취소하면
  `AppError::Cancelled` 이고 attachments 디렉터리 파일 수가 **취소 전과 동일**.
  대조군 `not_cancelled_completes` 도 함께.
- 프런트: 취소 버튼이 손잡이를 호출하는지, 취소 항목이 실패로 오분류되지 않는지
  (`.upq-item.failed` 가 없어야 함) 2건 추가.
