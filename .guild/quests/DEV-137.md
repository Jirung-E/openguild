## 왜 필요한가 (배경 / 동기)

- **파일이 진리원, GUI 는 DB 캐시(index.db) 를 읽음.** 그래서 사용자가 외부에서
  파일을 바꾸면 (CLI `openguild quest new/edit`, 에디터로 `.guild/quests/*.md`
  직접 수정, `git pull` 로 변경분 유입) GUI 의 캐시는 stale 이 된다.
- **DEV-121 Phase 1 (시동 sync) 만으로는 부족.** Phase 1 은 *앱 시작 시 1회* 만
  변경 파일을 동기화한다. 즉 **GUI 를 켜 둔 채** 외부에서 quest 를 고치면, 그
  변경은 *재시작(또는 Nav 의 ⟲ reindex) 전까지* 안 보인다.
- **전체 reindex 는 매번 돌리기엔 비싸다** (DELETE all + INSERT all). 그런데
  실사용에선 "지금 내가 열어 보는 그 quest 하나" 만 최신이면 충분한 경우가
  대부분이다.
- **`stat()` 로 mtime 읽기 = microsecond 수준 (사실상 공짜).** 파일을 매번 다시
  파싱하는 게 아니라, *수정시간만* 비교해서 바뀐 경우에만 그 한 파일을 읽으면
  된다. → 이게 이 quest 의 핵심: **"파일 내용은 상세 페이지 들어갈 때만(그것도
  바뀌었을 때만) 읽는다."**

## 어떻게 동작하는가 (설계)

상세 read 경로(`get_quest_by_slug`) **맨 앞**에서 그 slug 한 건만 lazy 체크:

```
refresh_quest_if_stale(store, slug):
    path = .guild/quests/{slug}.md
    if not path.exists(): return false          # 신규/삭제는 범위 외
    file_mtime = stat(path).mtime_unix_nanos     # ~1ms, 내용 안 읽음
    (id, cached_mtime) = SELECT q.id, q.cached_mtime FROM quests ... = slug
    if row 없음: return false                    # DB 에 없음 → 시동 sync/reindex 영역
    if file_mtime <= cached_mtime: return false  # DB 가 이미 최신 → 내용 안 읽음
    # 여기서야 비로소 파일 내용 읽음 (바뀐 그 한 파일만)
    qf = parse(path)
    status_id = lookup(qf.status); if 없음: return false   # unknown status → reindex 영역
    UPDATE quests SET title, description, status_id, urgency,
                      created_at, updated_at, deleted_at,
                      desired_due, required_due, cached_mtime
        WHERE id = ?
    return true
```

호출자는 반환값과 무관하게 곧바로 평소대로 DB read 를 이어가면, 방금 갱신된
최신 행을 응답하게 된다.

### 동작 흐름 (코드 매핑)

1. `gui/src/commands.rs` 의 `get_quest_by_slug` → `incremental::refresh_quest_if_stale(&store, &slug)` 호출 후 기존 detail read.
2. `core/src/incremental.rs::refresh_quest_if_stale` — 위 의사코드.
3. mtime 단위 = **Unix nanoseconds (`cached_mtime`, INTEGER)** — DEV-121 과 동일 규약.

## 범위와 의도적 한계

- **quest 파일만.** 목록 / 보드는 여러 파일을 한꺼번에 봐야 하므로 lazy 대상이
  아님 — 그건 시동 sync(DEV-121 Phase 1) 또는 Nav 의 ⟲, 또는 fs watcher
  (DEV-122) 영역.
- **표시 필드 중심 UPDATE.** title / description / status / urgency / due /
  created·updated·deleted 만 갱신. **prereq / tags / parent cascade(다른 quest
  파일의 auto-block, `quest_dependencies` 재계산) 는 안 함** — 그건 풀 reindex
  의 일. 즉 외부에서 *관계(prereq/parent)* 만 바꾼 경우는 lazy 로 안 잡히고 ⟲
  /재시작 필요.
- **신규 / 삭제 파일은 대상 아님** (상세 진입 = 기존 quest 열기). 신규/삭제는
  시동 sync 의 `needs_full_reindex` → 풀 reindex fallback.
- **sibling(`.comments.md` / `.memo.md`) 은 별도** (DEV-102 / DEV-134 의 캐시
  경로). 본 함수 범위 아님.
- **안전 우선 — 애매하면 skip.** 파일 없음 / DB 에 없음 / unknown status →
  panic 없이 `false` 반환하고 기존 캐시로 응답.

## timezone 안전성

`cached_mtime` 은 `SystemTime → duration_since(UNIX_EPOCH).as_nanos()` 의 절대
시각(epoch 기준)이라 local time / TZ / DST / 길드를 다른 PC 로 옮김에 무관.
naive ISO string 비교 금지 (DEV-121 의 결정과 동일).

## 엣지 케이스

- **clock skew (사용자 시계 변경)**: 뒤로 → 불필요 re-parse 1회(무해). 앞으로 →
  그 행이 stale 처럼 보여 한 번 re-parse(정확).
- **FAT32 등 2초 정밀도**: 같은 초 안 편집은 못 잡음 → ⟲ 로 우회. NTFS/APFS/ext4
  는 sub-second 라 무관.
- **mtime 보존 복사 (`git checkout`, `rsync -t`)**: 내용은 바뀌었는데 mtime 이
  옛것일 수 있음 → 못 잡음. fallback = ⟲(reindex). (size/hash 까지 보려면 비용
  증가 — DEV-121 의 '결정 보류' 참고.)
