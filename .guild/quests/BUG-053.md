사용자: 'GUI 에서 상태 바꾼 quest 들이 되돌아오는 경우가 있다, 기준 모르겠음'.

## 재현 확인
BUG-046 의 quest_history 에 testing→done 이 두 번 기록. 두 기록 사이에 done→testing 의 reverse 가 history 에 없음. 즉 DB 가 reverse 됐는데 그게 change_status mutation 이 아님.

## 원인 (2 종류 — 정정 후)

### 1. `git restore` (이번 라운드 직접 trigger)
- 사용자가 GUI 에서 변경 → DB + file 갱신, working tree 에 변경분 stage 안 됨.
- 누군가 `git restore <quest.md>` 호출 → working tree 의 file 이 last commit 의 옛 status 로 wipe.
  - 단 그 자체로 DB 는 안 바뀜 (file 만 wipe).
- 다음 reindex (직접 호출 또는 drift::auto_resync) 가 file → DB sync → DB 도 옛 status 로.
- GUI 본 변경이 사라짐. quest_history 에 reverse 안 적힘.

### 2. branch switching 자체는 무해 (사용자 추측 검증 결과)
- 모든 feature branch tip 의 quest .md 들이 develop 의 latest 와 동일 (이번 raid 검증).
- 즉 `git checkout <branch>` 자체는 file 변경 X.
- 단 branch 작업 준비 단계로 `git restore` 또는 `git stash` 가 호출되면 (1) 의 path.

### 3. reindex / drift::auto_resync 일반 case
- file 이 외부 (직접 편집 / git pull / restore) 로 옛 상태로 됐을 때 reindex 가 그 옛 상태를 DB 에 강제 sync.
- BUG-049 의 시동시 자동 reindex 가 본 issue 의 잠재 trigger.

## 영향
- AGENTS.md 의 '직접 편집 금지' 정책은 file 편집만 다룸. **commit 안 한 GUI 변경 + git restore** 의 조합은 정책 외 case.
- BUG-051 (BUG-040 file/DB drift) 와 같은 family.

## 해결 후보
1. reindex 가 status 변경 시 quest_history 에 op='reindex_status_sync' 같은 entry 추가 — at least 흔적.
2. drift::auto_resync 호출 시 fresh_files 의 status 변경을 stderr / GUI banner 로 명시 알림 (현재는 tracing::info! 만).
3. write_quest_file 시 frontmatter 와 DB 의 status 가 다르면 경고 + 명시적 우선순위 선택 prompt.
4. change_status 의 BUG-011 early return — file 도 검사해서 file status != DB status 면 file 갱신 강제.
5. snapshot 의 시점이 사용자 변경 직전 + 직후 둘 다 — 'pre-revert' snapshot 자동.

## 우선 검증 (이번 라운드 결과)
- BUG-040 의 history 도 같은 양상 — 확인 필요.
- 이번 라운드 BUG-046 / DEV-068 / DEV-070 / DEV-101 working tree 변경분 → 사용자 GUI 변경 결과로 확인됨 (history 일관).
- BUG-046 만 두 번 done 변경된 이유 = 내가 `git restore .guild/quests/BUG-046.md` 한 직후 사용자가 GUI 에서 다시 done 클릭.
- 결론: 본 trigger 의 한 instance 가 실제 발생함. silent revert 자체 (reindex 가 history 안 적음) 는 별개 문제 — 그것도 해결해야 GUI 의 silent reverse 방지 가능.
