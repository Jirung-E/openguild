앱 전반의 둥근 모서리를 일반 원호 대신 **연속 곡률**로 바꾼다. Figma 의 Corner smoothing 과 같은 방식 (사용자 요청, 2026-10-09).

## 범위 — 모양만. **반경은 지금 값 그대로**

요청서는 두 가지를 같이 적어 보냈는데 성격이 다르다.

| | 무엇 | 이번에 |
|---|---|---|
| **반경** (`border-radius`) | 모서리가 **얼마나 크게** 둥근가. 지금 5~10px, 요청은 카드 20 · 버튼 12 | **안 한다** — [[DEV-427]] · [[DEV-428]] |
| **스무딩** (`corner-shape`) | 그 둥근 부분의 **모양**. 원호냐 끊김 없는 곡선이냐 | **이번 작업** |

반경을 뺀 이유 둘 — 버튼류가 스스로 `border-radius` 를 정하는 곳이 49곳이라 [[DEV-428]] 이 버튼을 부품
하나로 모은 뒤에 해야 한 곳에서 끝나고, [[DEV-427]] 이 "성격은 지금 것을 유지, 새 방향을 잡지 않는다" 로
정해 둔 것을 뒤집는 일이라 거기서 같이 정해야 한다.

## 한 일

`global.css` 에 토큰 `--corner-smooth: superellipse(1.5)` 와 `@supports (corner-shape: squircle)` 안의
전역 규칙 하나. `border-radius` 352곳 중 339곳이 이미 `var(--r-*)` 토큰을 지나지만 CSS 는 "반경이 얼마인
요소" 를 고를 수 없어 전역으로 걸고, 캡슐·원만 자기 규칙에서 `--corner-smooth: round` 로 빠져나간다(41곳).

지원 안 하는 웹뷰는 `@supports` 덕에 지금 모양 그대로다. JS 도 SVG 마스크도 없는 네이티브 페인트라
비용은 `border-radius` 와 같다 — 요청서의 "애니메이션 · 성능 부담되는 곳은 일반 모서리로" 는 필요 없다.

## 실측 (2026-10-09 ~ 10, 맥 WebKit 26.6 · Chromium 153)

**엔진** — 둘 다 `corner-shape: squircle` · `superellipse()` 지원. caniuse 는 아직 사파리 미지원으로
적어 두었지만 밀린 것으로 보인다. 눈금은 `round` = `superellipse(1)`, `squircle` = `superellipse(2)`,
`bevel` = `superellipse(0)`.

**동작** — 퀘스트 목록에서 센 것: 원·캡슐 2,344개가 전부 원호로 남고(어긋난 것 0), 나머지 2,220개에 스무딩이
걸린다. 검색 입력칸 `6px` → `superellipse(1.5)`.

**그런데 이 앱 반경에서는 눈에 안 보인다.** 같은 화면을 켜고 끄고 찍어 나란히 놓아도 구별이 안 된다.
반경 6 · 8 · 10 에서는 차이를 못 찾겠고 **반경 20 부터** 들어온다. 보드 노드는 `--r-xl`(10px)인데 보드
배율이 0.021(퀘스트 814개 기준 화면 맞춤)이라 모서리가 0.2px 로 그려진다 — 보드는 이 작업으로 달라질 수
있는 화면이 아니다.

## 캡슐 — **CSS 로는 안 된다** (admin 지적, 2026-10-10)

admin: "캡슐을 스퀘어클로 만들면 안 되지. 캡슐 곡선과 직선이 이어지는 부분에 적용하라는 거잖아."

맞다. 그리고 **Figma 스무딩과 superellipse 는 다른 도형이다.**

- **Figma 스무딩** — 가운데 **원호를 그대로 두고** 양쪽 어깨만 베지에로 직선에 잇는다. 반원은 안 건드린다.
- **`corner-shape: superellipse()`** — 모서리 곡선 **전체를 통째로** 다시 그린다. 원호가 안 남는다.

일반 모서리에서는 둘이 비슷해 보여 같은 것으로 다뤄도 되지만, 캡슐에서는 결과가 갈린다. 세 가지로 확인했다.

| 시도 | 결과 |
|---|---|
| 캡슐 그대로 + `superellipse(1.1~2.0)` | 끝이 네모. 1.1 만 걸어도 납작해지고 1.35 면 이미 캡슐이 아니다 |
| 가로 반경만 늘림 (`1.6em / 50%`) | 이음새는 완만해지지만 **반원이 타원으로** 늘어난다 |
| 반경을 46 · 44 로 살짝 줄임 | 직선 구간이 생겨도 끝은 여전히 납작하다 |

(`999px / 50%` 는 애초에 못 쓴다 — 세로 합이 높이를 넘으면 CSS 클램프가 가로까지 같은 비율로 줄여 거의 사각이 된다.)

**되는 길은 외곽선을 직접 그리는 것뿐이다.** 원호 + 베지에 두 조각을 `clip-path: shape()` 로 그린다
(WebKit · Chromium 둘 다 지원 확인). 비용:

- 어깨 위치를 **높이에서 계산**해야 한다 — 칩마다 padding 이 달라 높이가 제각각이면 규칙이 여러 벌 필요하다.
- **테두리가 잘린다.** 캡슐 27곳 중 **11곳에 테두리**가 있고 `clip-path` 는 테두리까지 자른다. 가짜로 다시 그려야 한다.
- 효과는 칩에만 난다. 일반 모서리는 `corner-shape` 로 충분하다.

반나절 이상. **별도 퀘스트로 떼는 것이 맞다** — admin 판단 대기.

## 반경을 두 배로 — 곡률 인상을 맞춘다 (admin, 2026-10-10)

admin 이 보드 노드 비교에서 **"반경 20 스무딩이 지금과 제일 유사한 곡률"** 이라고 골랐다.
스퀘어클은 같은 반경에서 더 각져 보이므로, 지금껏 보던 곡률을 유지하려면 반경을 키워야 한다.

토큰마다 맞는 배수를 픽셀로 찾았다 — 모서리 한 귀퉁이를 8배 해상도로 그려
`(round, R)` 과 가장 비슷한 `(superellipse(k), R')` 을 전수 탐색:

| k | 배수 | 비고 |
|---|---|---|
| 1.3 | ×1.18 | 잔차 가장 작음 |
| 1.5 | ×1.32 | |
| 1.8 | ×1.57 | |

배수는 크기와 무관하게 일정했다(2~10px 전부). 픽셀로만 보면 k=1.5 의 최적은 ×1.32 지만,
**admin 이 눈으로 고른 것은 ×2.0** 이다 — 면적 차이를 줄이는 것과 사람이 "같은 둥글기" 로
보는 것이 다르다. 사람 쪽을 따른다.

### 적용

| 토큰 | 전 | 후 | 쓰는 곳 |
|---|---|---|---|
| `--r-xs` | 2px | 4px | 23곳 |
| `--r-sm` | 4px | 8px | 90곳 |
| `--r-md` | 6px | 12px | 147곳 |
| `--r-lg` | 8px | 16px | 27곳 — 카드 · 패널 |
| `--r-xl` | 10px | 20px | 25곳 — 모달 · 큰 카드 |

**요청서 기준값과 그대로 맞는다** — 카드 20(`--r-xl`) · 버튼 12(`--r-md`). 우연이 아니라,
"같은 곡률로 보이게" 가 곧 그 값이기 때문으로 보인다.

캡슐(`--r-pill`)과 원(50%)은 그대로다 — 반경을 안 키우고 스무딩도 안 건다.

### 결과

퀘스트 목록 화면에서 **지금 모습 vs 반경 2배+스무딩** 의 픽셀 차이가 **0.137%** 다.
인상은 거의 같고 모서리만 연속 곡률이 됐다 — [[DEV-427]] 의 "성격은 지금 것을 유지" 와 어긋나지 않는다.

**스무딩과 반경은 한 쌍이다.** 스무딩을 끄려면 반경도 반으로 되돌려야 한다. 안 그러면 모서리가 두 배로 둥글어진다.

## 맥 앱의 WKWebView 는 `corner-shape` 를 **지원하지 않는다** (2026-10-10, admin 보고 → 실측)

admin: "곡률만 늘어났고 스무딩은 적용 안돼있음. 나는 openguild-gui 씀."

맞다. **내가 엉뚱한 엔진으로 재고 있었다.** Playwright 의 WebKit 26.6 은 WebKit 트렁크 빌드라
시스템 WKWebView 보다 앞서 있다. 앱(Tauri)이 쓰는 것은 시스템 WKWebView 다.

시스템 WKWebView 로 직접 쟀다(Swift + WKWebView, 맥 26.6.2):

```
corner-shape: squircle        false
corner-shape: superellipse()  false
corner-shape: round           false   ← 키워드조차 없다
clip-path: shape()            true
```

그래서 앱에서는 `@supports` 가 통째로 걸러지고, **반경 2배만 먹어 그냥 두 배로 둥글어졌다.**
admin 이 본 것이 정확히 그 상태다.

## 고침 — 반경도 `@supports` 안으로

반경과 스무딩은 **한 쌍**이라 따로 움직이면 안 된다.

- 반경만 커짐 → 그냥 두 배로 둥글어진다 (맥 앱에서 실제로 그랬다)
- 모양만 바뀜 → 각져 보인다

이제 바깥 `:root` 는 **지금 값 그대로**(2·4·6·8·10)이고, `@supports (corner-shape: squircle)`
안에서만 두 배(4·8·12·16·20) + 스무딩이 함께 걸린다.

시스템 WKWebView 로 재확인: `--r-xl` = `0.625rem`, 실제 반경 `10px` — **지금 모습 그대로**.

## 그래서 지금 이 작업이 실제로 먹는 곳

| 플랫폼 | 웹뷰 | `corner-shape` |
|---|---|---|
| 맥 앱 | 시스템 WKWebView | **없음** (실측) |
| 윈도우 앱 | WebView2 (Chromium) | 있을 것 — Chromium 139+ 지원. **윈도우에서 확인 필요** |
| 리눅스 앱 | WebKitGTK | 없을 가능성이 높다 — 확인 필요 |
| 웹(크롬) | Chromium | 있음 |

**즉 지금 당장 달라지는 곳은 윈도우 앱과 웹브라우저뿐이다.** 맥·리눅스 앱은 `@supports` 덕에
지금 모습 그대로 안전하게 남는다.

## 남은 선택지

1. **이대로 둔다** — 안전하다. 맥·리눅스 웹뷰가 따라오는 날 저절로 켜진다. 윈도우에서는 지금부터 먹는다.
2. **`clip-path: shape()` 로 간다** — 시스템 WKWebView 도 지원한다(실측). 모든 플랫폼에서 지금 당장
   먹고 캡슐의 Figma 식 이음새까지 된다. 대신 외곽선을 직접 그려야 하고 테두리가 잘린다(캡슐 27곳 중 11곳).
   반나절 이상. 별도 퀘스트.
3. **접는다** — 되돌리고 알아낸 것만 남긴다.

admin 판단 대기.

## 되돌림 — 코드는 전부 뺐다 (admin, 2026-10-10)

admin: "그냥 오늘 곡률 관련 수정한거 완전히 되돌리자."

프런트 변경 전부(토큰 `--corner-smooth`, `@supports` 전역 규칙, 반경 2배, 원·캡슐 옵트아웃 41곳)를
revert 했다. `--r-*` 는 2 · 4 · 6 · 8 · 10px 로, 모든 화면이 작업 전 모습 그대로다. 코드에 `corner-shape`
흔적은 하나도 없다. `just test` 822 통과.

**퀘스트 기록은 남긴다** — 아래 실측이 이 작업의 유일한 소득이고, 다시 할 때 조사를 반복하지 않기 위해서다.

### 알아낸 것 (요약)

1. **맥 앱은 `corner-shape` 를 못 쓴다.** Tauri 가 쓰는 시스템 WKWebView 에 아예 없다
   (Swift + WKWebView 실측: squircle · superellipse · round 전부 `false`). `clip-path: shape()` 는 된다.
   Playwright 의 WebKit 은 트렁크 빌드라 지원한다 — **앱 엔진으로 착각하면 안 된다.**
2. **반경과 스무딩은 한 쌍이다.** 스퀘어클은 같은 반경에서 더 각져 보여, 지금 곡률을 유지하려면 반경을
   키워야 한다. 배수는 크기와 무관하게 일정(k=1.3 → ×1.18, k=1.5 → ×1.32, k=1.8 → ×1.57), 단 admin 이
   눈으로 고른 값은 ×2.0 이었다. 둘 중 하나만 적용하면 화면이 망가진다 — 반경만 커지면 두 배로 둥글어지고,
   모양만 바뀌면 각져 보인다. 반드시 같은 `@supports` 블록 안에 둘 것.
3. **캡슐은 `corner-shape` 로 안 된다.** Figma 스무딩은 *원호를 남기고 어깨만 베지에로 잇는* 구성이고
   `superellipse()` 는 *모서리 곡선 전체를 다시 그리는* 것이라, 캡슐에서는 반원이 사라진다. 세 가지로 확인
   (캡슐 그대로 / 가로 반경만 늘림 / 반경 축소). 하려면 `clip-path: shape()` 로 외곽선을 직접 그려야 하고,
   캡슐 27곳 중 **11곳에 테두리**가 있어 클립에 잘린다.
4. **지금 반경(5~10px)에서는 효과가 거의 안 보인다.** 목록 화면 전체 픽셀 차이 0.03%, 보드 노드 하나
   기준 0.5%. 반경 20 부터 눈에 들어온다.

### 다시 하려면

- 맥·리눅스 웹뷰가 `corner-shape` 를 지원하기 시작하면 2번 규칙대로 `@supports` 한 블록에 반경 2배 + 스무딩.
- 그 전에 맥에서도 보이게 하려면 `clip-path: shape()` 뿐이다(테두리 처리 설계 필요, 반나절 이상).
- 어느 쪽이든 반경을 키우는 것은 [[DEV-427]] · [[DEV-428]] 과 같이 간다.

상태를 **보류**로 옮긴다 — 할 일이 없어서가 아니라 웹뷰 지원을 기다리는 것이다.
