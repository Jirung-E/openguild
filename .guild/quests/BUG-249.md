## 증상

강화 검색 중 서버가 **패닉**한다. 연결이 그대로 끊겨(`ERR_EMPTY_RESPONSE`)
검색 결과가 0건으로 보인다.

```
thread 'tokio-rt-worker' panicked at core/src/ops/search.rs:109:24:
end byte index 2360 is not a char boundary; it is inside '근' (bytes 2359..2362)
```

CLI 로도 같은 문서를 검색하면 같은 자리에서 죽는다.

## 원인 (확인함)

`excerpt_around` 이 **소문자 문자열에서 찾은 바이트 위치를 원문에 그대로**
쓴다.

```rust
let lower = text.to_lowercase();
let byte_pos = lower.find(needle_lower).unwrap_or(0);
let char_pos = text[..byte_pos].chars().count();   // ← lower 의 인덱스로 text 를 자른다
```

`to_lowercase()` 는 **바이트 길이를 바꿀 수 있다.** 그런 문자가 앞에 하나라도
있으면 이후 인덱스가 전부 밀리고, 밀린 위치가 한글 중간이면 그 자리에서
패닉한다.

실제 원인 문자: **`İ` (U+0130 LATIN CAPITAL LETTER I WITH DOT ABOVE)** —
2바이트인데 소문자는 `i̇` 3바이트다. 이 길드에서는 [[REQ-014]] 댓글에 이
함정을 설명하며 예시로 적은 글자가 그대로 지뢰가 됐다.

함수 주석은 "**char 단위로 자른다** — 바이트로 자르면 한글이 깨진다" 라고
적혀 있다. 잘라내는 부분은 실제로 char 단위인데, **위치를 구하는 부분**이
바이트 인덱스를 섞어 쓴 것을 놓쳤다.

## 영향

- 서버: 그 요청의 연결이 끊긴다. axum 에 catch-panic 계층이 없어 500 도 아니고
  빈 응답이다. 프런트는 실패로 처리해 로컬 매치만 보여준다(조용한 오작동).
- CLI: 프로세스가 죽는다.
- 대상 문자가 문서에 하나만 있어도, 그 문서가 검색 후보에 들어가는 **모든**
  검색어에서 재현된다.

## 수정 방침

소문자화하면서 **소문자 char 인덱스 → 원문 char 인덱스** 대응표를 함께
만든다. `char::to_lowercase()` 가 여러 글자를 낼 수 있으므로 1:1 이 아니라
매핑이 필요하다.

프런트의 `highlight.ts` 는 같은 함정을 "길이가 달라지면 표시를 포기" 로
피했는데, 여기는 발췌를 못 만들면 결과 자체가 쓸모없어지므로 정확히 대응한다.

## 재발 방지

`İ` 를 포함한 문자열로 발췌를 만드는 테스트를 붙인다. 이 함수는 이미 한글
안전성 테스트가 있었지만 **소문자화로 길이가 변하는 경우**가 빠져 있었다.
