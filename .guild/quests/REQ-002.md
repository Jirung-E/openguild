전체 코드베이스 리뷰(8개 영역 병렬)에서 발견. 실제 코드 확인으로 검증 완료.

## 문제

`resolve_guild_rel` (gui/src/commands.rs:2134) 의 traversal 가드가 `rel.contains("..")` 뿐이다.

```rust
if rel.contains("..") { return Err("잘못된 첨부 경로".into()); }
let path = store.paths.dot_guild().join(rel);
```

Rust 의 `Path::join` 은 **인자가 절대경로면 base 를 통째로 버린다.** 따라서
`rel = "/etc/passwd"` (Windows 는 `C:\...`) 는 `..` 검사를 통과하고 `.guild/`
바깥으로 완전히 벗어난다.

이 경로는 두 command 에 그대로 들어간다:
- `open_guild_file` (commands.rs:2147) — OS "open" 동사로 임의 파일 열기/실행
- `copy_guild_file` (commands.rs:2161) — 임의 파일 복사

## 공격 성립 경로 (검증함)

`add_attachment` (core/src/ops/attachments.rs:398) 는 `path` 가 **비어있지
않은지만** 검사하고 문자열을 그대로 사이드카 JSON 에 저장한다. 상대경로 여부나
`.guild/` 내부인지 전혀 검증하지 않는다.

그 사이드카는 `.guild/` 아래에 있고 git-tracked = 공유 대상이다(AGENTS.md).
즉 **악의적 커밋이 절대경로를 가리키는 첨부 항목을 심을 수 있고**, 길드를 연
동료가 그 첨부의 "열기" 를 누르면 확인 절차 없이 임의 파일이 OS 핸들러로
열린다.

## 제안 수정 (2겹)

1. `resolve_guild_rel` 에서 `Path::new(rel).is_absolute()` 거부 + Windows 드라이브/UNC 접두 거부. 정규화 후 `dot_guild()` 하위인지 `starts_with` 로 재확인.
2. `add_attachment` 쓰기 시점에서도 동일 검증 — 이미 심어진 데이터도 읽기 시점에 막히도록 양쪽 다.

## 테스트 방법

- `add_attachment` 에 절대경로 넣으면 BadRequest 인지
- 사이드카에 절대경로가 이미 있을 때 `open_guild_file` 이 거부하는지
- 정상 상대경로 첨부는 그대로 열리는지 (회귀 없음)

## 수정 내용 (2026-08-20)

검증 로직이 **두 벌**이었던 것이 근본 원인이었다. server 의 `get_guild_file`
은 처음부터 올바른 allowlist(`attachments/` · `assets/` 접두 강제 + `..` /
빈 세그먼트 거부)를 쓰고 있었는데, GUI 의 `resolve_guild_rel` 만 약한
denylist(`..` 포함 검사)를 써서 절대경로가 빠져나갔다.

- `core/src/ops/attachments.rs` 에 `validate_guild_rel()` 신설 — server 가
  쓰던 allowlist 를 그대로 옮긴 **단일 구현**. `/` 정규화한 rel 을 반환.
- `gui/src/commands.rs` `resolve_guild_rel` — denylist 제거, 위 함수 사용.
- `server/src/routes/admin.rs` `get_guild_file` — 인라인 검증 제거, 위 함수 사용.
- `core/src/ops/attachments.rs` `add_attachment` — **쓰기 시점에도** 검증.
  (읽기만 막으면 이미 심어진 항목은 못 거른다. 양쪽 다 필요.)
- 단위 테스트 3종 추가: 정상 접두 통과 / 절대경로·드라이브문자·UNC 거부 /
  traversal·타 접두·빈 세그먼트 거부.

기존 데이터 회귀 확인: 이 길드의 첨부 경로 3건 전부 `attachments/` 접두를
지키고 있어 강화된 검증에 걸리지 않는다.

## 테스트 방법

프로젝트 규칙상 에이전트가 빌드/테스트를 임의 실행하지 않으므로 아래를 직접
실행해 확인할 것.

```
cargo test -p openguild-core attachments
cargo build --workspace
```

기능 확인:

1. 첨부가 있는 퀘스트에서 첨부 **열기** / **다운로드** 가 정상 동작하는지
   (회귀 없음 확인 — 정상 경로는 그대로 열려야 한다).
2. GUI 브라우저 모드에서 첨부 이미지가 그대로 보이는지
   (`/api/guild-files/attachments/...` 서빙 회귀 확인).
3. 차단 확인 — 사이드카(`.guild/quests/{slug}.attachments.json`)의 `path` 를
   임시로 `/etc/passwd` 로 바꾼 뒤 GUI 에서 그 첨부의 열기/다운로드를 누르면
   "허용되지 않은 첨부 경로" 로 거부돼야 한다. 확인 후 사이드카 원복.
