BUG-210 조사 중 발견: 서버가 응답을 **전혀 압축하지 않는다**.

- `curl -H "Accept-Encoding: gzip"` 에도 `content-encoding` 헤더 없음,
  본문 크기 동일(1,156,414 바이트).
- `server/Cargo.toml` 의 tower-http features 는 `cors, trace, fs, set-header`
  — `compression-gzip`/`compression-br` 미포함.

우리 응답은 대부분 한글 JSON/마크다운이라 gzip 압축률이 특히 좋다. 원격
접속(Tailscale 경유 폰)에서 체감이 큰 부분이고, 정적 자산(_app/*.js)에도
같이 적용된다.

## 할 일

- tower-http `compression-gzip`(+ 가능하면 br) feature 추가,
  `CompressionLayer` 를 라우터에 부착.
- 이미 압축된 응답(첨부 다운로드 등)은 제외 대상인지 확인 —
  이미지/zip 을 다시 압축하면 CPU 만 쓴다.
- 압축 전/후 크기와 응답 시간 측정해 댓글로 기록.

주의: 첨부 스트리밍 경로가 있다면 압축 레이어가 버퍼링을 유발하지 않는지
확인할 것(1.5GB 첨부 — BUG-188 참고).
