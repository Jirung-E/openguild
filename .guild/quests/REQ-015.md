## 요청

도서관 리스트뷰와 규칙 페이지에서 **구분선을 드래그해 좌우 영역 폭을 조절**할
수 있게 한다.

## 현황

둘 다 `grid-template-columns` 로 좌측 폭이 고정이다.

| 화면 | 현재 |
|------|------|
| 도서관 | `grid-template-columns: 16.25rem 1fr` |
| 규칙 | `grid-template-columns: 15rem 1fr` |

[[BUG-254]] 에서 px → rem 으로 바꿔 UI 배율은 따라가게 됐지만, 사용자가 직접
조절할 수단은 없다.

## 참고 — 이미 있는 구현

검색 팔레트의 미리보기 영역에 **세로 크기 조절 핸들**(`.dp-resize`)이 있다.
아래 가장자리를 드래그해 높이를 바꾸는 방식이고, 값은 저장하지 않는다.

이번 건은 **가로**이고 두 페이지에 공통이므로, 그 코드를 그대로 쓰기보다
공용 액션/컴포넌트로 뽑는 편이 낫다.

## 정할 것

1. **폭을 기억할지** — `localStorage` 영속(팔레트의 `worklogViewMode` 선례)
   vs 세션 한정. 영속이면 길드별로 나눌지도.
2. **최소/최대 폭** — 너무 좁히면 목록이 못 읽히고, 너무 넓히면 본문이 죽는다.
3. **모바일** — 두 페이지 모두 좁은 폭에서 `grid-template-columns: 1fr` 로
   한 줄이 된다. 그때는 핸들을 숨겨야 한다.
4. **배율과의 관계** — 저장값을 px 로 두면 배율을 다시 안 따라간다. rem 으로
   저장하거나, 저장은 px 로 하되 배율 변경 시 비례 조정이 필요한지 판단.

## 정한 것 (본문의 "정할 것" 4가지)

### 1. 폭을 기억한다 — localStorage, **pane 별로 따로**

`openguild.paneWidth.{library|rules}`. 도서관은 폴더 트리, 규칙은 slug 목록
이라 적당한 폭이 다르다. 길드별로는 나누지 **않는다** — "이 화면을 어떻게
보고 싶은가" 라는 표시 설정이지 길드 데이터가 아니다([[DEV-101]] 의
`uiScale` / `contentWidth` 와 같은 취급).

### 2. 최소 10rem / 최대 30rem

10rem 아래면 도서관 폴더 이름이 두세 글자만 보여 목록 구실을 못 하고,
30rem 위면 본문이 눌린다. **rem 이라 배율을 올려도 "글자 기준으로 같은 정도"**
를 유지한다.

### 3. 모바일에서는 핸들을 숨긴다

두 페이지 모두 `max-width: 640px` 에서 한 열로 쌓이는데, 그러면 좌우 구분선
자체가 없어져 조절할 대상이 사라진다. 도서관의 **아이콘 보기**(explorer)도
사이드바가 없으므로 핸들을 아예 렌더하지 않는다.

### 4. **rem 으로 저장한다** — 이게 핵심이다

px 로 저장하면 [[BUG-254]] 가 고친 문제가 사용자 값에서 그대로 되살아난다
(배율을 올리면 칸은 그대로인데 안의 버튼·태그·제목이 경계를 넘음).

드래그의 px 이동량을 **그 시점의 root font-size 로 나눠** rem 으로 바꾼다.
그래서 배율이 2배면 같은 픽셀을 끌어도 rem 증가량은 절반이고, **화면에서 손이
움직인 거리와 칸이 넓어지는 거리가 항상 일치한다.**

## 수정

- `lib/stores/paneWidth.ts` — pane 별 싱글턴 store. `uiScale` 과 같은 rAF
  병합으로 localStorage 쓰기를 프레임당 1회로 묶는다(드래그 중 동기
  `setItem` 이 매 프레임 메인 스레드를 막는 [[BUG-141]] 과 같은 이유).
- `lib/components/PaneResizer.svelte` — 공용 핸들. **레이아웃의 가운데 열**로
  들어가 예전 `gap: 1.25rem` 자리를 그대로 차지하므로 기존 간격·배치가 하나도
  안 바뀐다.
- 두 페이지: `grid-template-columns: var(--pane-w, …) 1.25rem 1fr; gap: 0`.

**키보드로도 조절된다.** 드래그는 포인터가 있어야만 가능한 조작이라 그것만
두면 키보드 사용자는 이 기능을 아예 못 쓴다. `role="separator"` +
`tabindex="0"` 은 ARIA 의 window splitter 패턴이다 — 방향키 1rem,
Shift+방향키 0.25rem, Home/End 는 최소/최대, 더블클릭은 기본값.

## 검증 (브라우저 실측, 1400×900, test-guild)

| 조작 | 결과 |
|------|------|
| 기본값 | 도서관 16.25rem / 규칙 15rem (BUG-254 값 그대로) |
| 오른쪽 160px 드래그 | 16.25 → **26.25rem** (160/16 = 10) |
| 왼쪽 80px | 26.25 → **21.25rem** |
| 끝까지 오른쪽 | **30rem** 에서 멈춤 |
| 끝까지 왼쪽 | **10rem** 에서 멈춤 |
| 방향키 → | +1rem |
| Shift+방향키 → | +0.25rem |
| 더블클릭 | **16.25rem** (기본값 복귀) |
| 새로고침 | 저장값 `25` → **25rem 그대로** |

**배율 대응** — 같은 160px 드래그를 두 배율에서:

| 배율 | 시작 | 드래그 후 | 화면상 증가 |
|------|------|-----------|------------|
| 100% (root 16px) | 16.25rem = 260px | 26.25rem = 420px | **+160px** |
| 200% (root 32px) | 16.25rem = 520px | 21.25rem = 680px | **+160px** |

200% 에서는 같은 픽셀을 끌어도 rem 증가가 절반(10 → 5rem)이라, **손이 움직인
거리와 칸이 넓어진 거리가 양쪽 다 정확히 160px** 이다. 저장값은 rem 이므로
배율을 바꿔도 칸이 계속 따라간다.

**pane 분리**: 도서관을 25rem 으로 바꾼 뒤 규칙을 열면 15rem(기본값)이고,
규칙을 19rem 으로 바꿔도 도서관 저장값은 25 그대로다.

**모바일(375×812)**: 두 페이지 모두 핸들 `display: none`, 레이아웃 한 열
(`327px`). **아이콘 보기**: `.layout` 자체가 없어 핸들도 렌더되지 않는다.

## 후속 — 규칙 목록의 긴 slug 가 경계를 넘었다 (admin 보고)

> 도서관은 잘 되는데, 규칙페이지는 글자가 경계를 넘어감

폭을 줄일 수 있게 되니 드러났다. 원인은 폭이 아니라 **말줄임 처리가 없던
것**이다.

`global.css` 는 버튼을 `white-space: nowrap` 으로 둔다([[BUG-143]] — CJK
라벨이 글자 단위로 꺾여 2줄이 되는 것을 막으려고). `.rule-item` 은 버튼인데
`overflow`/`text-overflow` 가 없어서, 긴 slug 가 **줄바꿈도 생략도 없이**
그대로 삐져나왔다.

도서관 쪽은 처음부터 갖고 있었다 — `LibraryFolderTree` 의 `.folder-name` /
`.book-title` 이 `overflow: hidden; text-overflow: ellipsis`. 그래서 "도서관은
잘 되는데" 였다. 같은 방식으로 맞췄다.

**[[BUG-254]] 가 못 잡은 부분이다.** 그때는 사이드바 **폭**을 px → rem 으로
바꿔 넘침을 줄였는데, 폭과 무관하게 긴 이름은 여전히 넘쳤다.

### 실측 (최소 폭 10rem = 160px)

| | 수정 전 | 수정 후 |
|---|---|---|
| `.rule-slug` 내용 폭 | 상자보다 8px 넓음, `overflow: visible` | 말줄임(`cli-command-nam…`) |
| 사이드바 경계를 넘는 요소 | 있음 | **0건** |

도서관도 같은 조건에서 **0건**이다.

## 남는 것

- **터치 드래그는 실측하지 못했다.** `pointerdown` 기반이라 터치에서도 같은
  경로를 타고 `touch-action: none` 으로 스크롤과 충돌하지 않게 해 뒀지만,
  실제 터치 기기에서 끌어본 것은 아니다.
- Windows / Linux 실측 없음(개발 환경이 macOS).
