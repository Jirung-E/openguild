## 목표
릴리즈/호스팅 시 **링크 하나**로 웹 접근. 즉 `openguild-server host` 하나가 SPA + API 를 같은 origin 으로 서빙. (dev 의 2-포트 :5173+:3000 은 개발 전용.)

## 갭 (전수)
1. **FRONTEND_DIST 기본값 불일치**: 서버 기본 `gui/frontend/dist` ↔ 실제 SvelteKit(adapter-static) 출력 `gui/frontend/build`. 기본 상태로는 정적 서빙이 절대 안 켜짐 → API-only.
2. **SPA fallback 없음**: `app.fallback_service(ServeDir::new(dist))` 만 → 루트(`/`)는 index.html 서빙되지만 `/quests/DEV-001` 같은 클라이언트 라우트 직접 접근/새로고침은 404.
3. **바인드 호스트 고정**: `SocketAddr::from(([127,0,0,1], port))` → localhost 전용. 다른 기기에서 링크로 접근하려면 `0.0.0.0` 또는 host 지정 필요.
4. **릴리즈 번들 부재**: release.yml 은 NSIS 인스톨러만 산출. 받아서 바로 호스팅할 `server.exe + frontend(build)` 묶음이 없음.

## 접근안 / 결정 필요

### A. 프론트엔드 서빙 방식
- **A1. 서버 바이너리에 임베드** (rust-embed 등): `openguild-server.exe` 단독으로 SPA+API 완결 → 진짜 "받아서 실행하면 끝". 빌드 시 `frontend/build` 를 바이너리에 포함. (권장 — 단일 링크 UX 에 가장 부합)
- **A2. build/ 동봉 + 기본 경로 수정**: 기본값 `dist`→`build`, 릴리즈에 `build/` 폴더 동봉. 임베드보다 단순하나 폴더 배치 의존.
- **A3. 최소 수정**: 기본값만 `dist`→`build`. (개발/로컬 단일 origin 테스트는 즉시 해결, 배포 번들은 별도)

### B. SPA fallback
- ServeDir 의 not-found → `index.html` 로 fallback (deep link 지원). 단, `/api/*` 는 그대로 API. (간단한 fallback 핸들러 또는 ServeDir `.fallback`/`.not_found_service` 구성)

### C. 바인드 호스트
- `--host`(또는 `HOST` env) 추가. **기본은 127.0.0.1 유지**(openguild 는 인증이 없음 → 의도치 않은 네트워크 노출 방지), 원격 호스팅은 `--host 0.0.0.0` 명시 opt-in. 시작 로그에 노출 경고 1줄.
- ⚠️ 보안: 인증/권한 계층이 없으므로 0.0.0.0 노출은 신뢰된 네트워크/리버스 프록시 뒤에서만 권장. (별도 인증 퀘스트 검토 여지)

### D. 릴리즈 산출물
- A1 채택 시: 릴리즈에 `openguild-server.exe`(frontend 임베드) 추가 업로드 → 사용자는 받아서 `openguild-server host --host 0.0.0.0` 후 링크 공유.
- A2 채택 시: `server.exe + build/` zip 번들 업로드.

## 권장
**A1(임베드) + B(fallback) + C(127.0.0.1 기본 + --host opt-in) + D(server 산출물 추가)**. 단일 바이너리라 배포/링크 UX 가 가장 깔끔하고, 보안 기본값은 보수적으로.

최소만 빨리 원하면 **A3 + B** 만 먼저 적용해 로컬 단일 origin 부터 정상화하고, 원격/번들(A1·C·D)은 후속으로 분리 가능. 어떤 범위로 갈지 의견 주세요.
