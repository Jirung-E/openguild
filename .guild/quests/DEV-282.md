DB 투영 불변식(BOOK-001) 구현 — 역류 경로 A2. DEV-242 대체.

reindex 의 counter self-heal([reindex.rs] DEV-242)이 DB 카운터가 파일보다
크면 types/*.toml 에 되쓴다. index.db 는 branch-blind 라, 다른 브랜치에서
오염된 카운터가 현재 브랜치 파일로 역류한다(실사고: 잘못된 브랜치 quest
new → ID 어긋남).

## 수정 방향
DB→파일 역류 제거. 다음 ID 는 **디스크 파일만으로**
`max(파일 카운터, 디스크 실존 최대번호)+1`. 파일 카운터가 실제 최대번호보다
낡았을 때만 파일-로컬 heal(브랜치-safe). DB 카운터는 순수 파생.

## 구현 (2026-07-27)

DEV-242 의 양방향 self-heal 을 **파일-로컬 heal + 파일→DB 재투영**으로 교체.

- 파일 카운터(`types/*.toml` 의 `[counter].last_number`)는 **디스크 실존 최대
  번호**로만 올린다. DB 를 전혀 참조하지 않으므로 DB→파일 역류 경로가 사라졌다.
  실존 최대는 reindex 가 이미 읽은 퀘스트 파일에서 접두사별로 집계한다.
- **낮추지는 않는다** — 파일 카운터가 실존 최대보다 크면(과거에 발급했다가
  삭제된 번호) 그대로 둔다. 낮추면 삭제된 ID 를 재발급하게 된다.
- DB 카운터는 파일 값으로 맞춘다(파일 → DB 방향만). 이전처럼 DB 의
  `MAX(number)` 로 끌어올리지 않는다 — 그 값이 파일로 역류하던 경로를
  없앴으므로 불필요하고, 남겨두면 같은 오염이 DB 쪽에 다시 고인다.

발급 시 다음 ID 는 여전히 `max(파일 카운터, 실존 최대번호) + 1` 이라 동작 변화
없음(services/quests.rs 의 self-heal 은 DB MAX 기준이므로 DEV-282 범위에서는
그대로 — DB 가 이제 파일에서만 채워지므로 오염원이 사라진다).

## 회귀 테스트

- `counter_heal_is_file_local_not_db_writeback` — DB 카운터를 900 으로 오염시킨
  뒤 reindex → 파일은 실존 최대(2) 유지, DB 도 2 로 재투영.
- `counter_heal_never_lowers_file_counter` — 파일 카운터 50, 실존 퀘스트 0건에서
  reindex → 50 유지(삭제된 ID 재발급 방지).

## 실제 길드 확인

reindex 후 `check counters` = 0 (file) + 0 (SQL), `check drift` clean.

## Test plan

1. 다른 브랜치에서 퀘스트를 여러 개 만들고 develop 으로 checkout → reindex →
   `types/*.toml` 의 카운터가 **올라가지 않아야** 한다(`git diff` 깨끗).
2. `check counters` 로 file/SQL 드리프트 0 확인.
3. 퀘스트를 삭제한 뒤 reindex → 카운터가 낮아지지 않고, 새 퀘스트가 삭제된
   번호를 재사용하지 않는지.
4. git pull 로 큰 번호 퀘스트가 들어온 경우 → 카운터가 그 번호까지 올라가는지
   (원래 DEV-242 가 해결하려던 케이스가 유지되는지).
