## 고친 것

- 문서를 고치기 전에 잠근 그 문서를 파일에서 다시 읽는다(`Store::lock_docs`). 못 읽으면 쓰지 않고, 밖에서 지워졌으면 되살리지 않는다.
- 새 번호는 번호 파일과 문서 파일에서 정한다. `index.db` 가 비어 있어도 있는 번호 · 지운 번호를 다시 주지 않는다.
- CLI 는 명령마다 바뀐 파일만 읽고, 서버는 시작할 때 · 상세를 열 때 읽는다.
- 캠페인 · 도서관 문서는 파일이 새로 생기거나 지워져도, `index.db` 를 지운 뒤에도 CLI 가 알아챈다.

## 속도 (퀘스트 파일 1,292개, LTO 끈 같은 빌드로 비교)

- CLI: `quest show` 24ms → 약 31ms, `quest list` 31ms → 약 38ms. 명령마다 약 7ms 늘었다.
- 시각만 전부 바뀐 뒤 첫 동기화: 760~1200ms → 약 325ms(한 트랜잭션으로 기록). 바뀐 것이 없으면 약 8ms.

## 확인

- `just test` 통과. 새 테스트 10개. 번호 · 외부 수정 · 못 읽는 파일 테스트는 수정을 끄면 6개가 실패한다.
- 임시 길드 시험: 외부 수정 58, v0.5.3 업그레이드 39, 전체 흐름 95 모두 통과.
- 도서관 외부 수정 · 번호는 임시 길드에서 CLI 로 확인. 도서관은 원래 파일에서 읽어 쓴다.

## 남은 것

- 켜 둔 앱 · 서버의 **목록**은 새로고침 전까지 옛 내용일 수 있다(쓰기와 상세는 파일 기준).
- 앱에서 직접 확인은 아직 안 했다. 코어 · 서버 경로만 시험했다.
- 앱 시작 시 동기화가 창을 띄우기 전에 돈다(`gui/src/lib.rs`). 창을 먼저 띄우는 건 동작 변경이라 물어보고 한다.

## 빈틈 보완

타입 · 상태 이름 바꾸기, `quest retype` 는 길드 독점 잠금을 잡고 DB 값으로 여러 파일을 다시 쓴다. 문서 잠금에 넣은 다시 읽기를 안 지나서,
켜 둔 앱 · 서버에서 밖에서 고친 내용을 지웠다. retype 에서 재현했다. 이제 먼저 바뀐 파일을 읽고, 못 읽는 파일이 있으면 거부한다.

문서 잠금 쪽은 다시 쓰는 문서가 잠금 목록에 있는지 코드를 봤고 빈틈을 못 찾았다. 작업마다 재현해 본 것은 아니다.

알려진 좁은 경우: 켜 둔 앱에서 밖에서 관계까지 바뀐 문서를 고치면, 잠글 목록을 옛 관계로 정한다.
