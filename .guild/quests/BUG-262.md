## 증상

퀘스트 상세 페이지에서 상태를 바꾸면 반영까지 눈에 띄게 걸린다(admin 보고,
"아직도 느리다").

## 원인 — 백엔드가 아니라 화면이 왕복을 세 번 한다

먼저 백엔드를 쟀다. **거의 공짜다:**

```
$ time openguild quest move DEV-001 in_progress
real 0.01 / 0.00 / 0.00  (6회, 테스트 길드)
```

느린 쪽은 `routes/quests/[id]/+page.svelte` 의 `changeStatus()` 다:

```js
changingStatus = true;                              // ← 버튼 잠금 시작
await questsApi.changeStatus(detail.id, {...});     // ① PATCH
detail = await questsApi.getBySlug(slug);           // ② 퀘스트 전체 재조회
historyVersion += 1;                                // ③ 이력 컴포넌트 재마운트
```

- ②는 **방금 바꾼 필드 하나 때문에 본문·관계·태그를 통째로 다시 받는다.**
  응답이 오기 전까지 화면은 옛 상태 그대로다.
- ③은 `{#key `${detail.id}:${historyVersion}`}`(1248행) 이라 이력 컴포넌트를
  **파괴 후 재생성**한다 — 또 한 번의 조회.
- 셋이 직렬이고 그동안 `changingStatus` 로 버튼이 잠겨 있다. 사용자가 보는
  지연은 셋의 합이다.

## 보드는 이미 제대로 하고 있다

같은 동작을 `QuestBoard.svelte:1604` 는 이렇게 한다:

```js
await questsApi.changeStatus(questId, { status_slug: newStatus.slug });
node.data('statusId', newStatus.id);
applyStatusChange(questId, newStatus.id);           // 재조회 없음
```

**재조회가 없다.** 서버가 성공을 돌려주면 알고 있는 값으로 로컬을 갱신한다.
즉 이건 설계 판단이 갈린 게 아니라 **상세 페이지만 안 맞춰진 것**이다.

## 할 것

1. 상세 페이지도 보드처럼 — 성공 응답으로 `detail` 의 상태 필드만 갱신하고
   전체 재조회를 없앤다.
2. 이력은 **화면을 막지 않고** 갱신한다. `{#key}` 재마운트 대신 이력만
   따로 새로 고친다(실패해도 상태 변경은 이미 끝난 일이다).
3. 낙관적 갱신 여부는 구현하며 판단한다 — PATCH 가 10ms 대라 성공 응답을
   기다려도 체감이 없을 수 있다. 재조회 제거만으로 충분한지 먼저 잰다.

## 테스트 방법

1. 상세 페이지에서 상태 버튼을 누르면 뱃지/버튼이 곧바로 바뀐다.
2. 이력 섹션도 새 행이 뜨는데, 그것 때문에 상태 반영이 늦지 않는다.
3. 실패(서버 중단)시 토스트가 뜨고 상태가 원래대로 남는다.
4. 보드에서의 상태 변경은 기존과 동일하게 동작한다(회귀 없음).
