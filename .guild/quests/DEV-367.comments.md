## 구현

- `server/Cargo.toml` — tower-http `catch-panic` feature.
- `server/src/error.rs` — `panic_to_500`. 응답 형식과 노출 수위를
  `AppError::Internal` 과 **똑같이** 맞췄다: 로그에는 전부, 응답에는 고정 문구
  `{"error":"internal server error"}`. 이 서버는 인증이 없고 LAN/Tailscale 로
  열어 쓰므로 패닉 메시지(내부 경로·변수)를 본문에 실으면 안 된다.
  페이로드가 `&str` / `String` / 그 외인 경우를 모두 처리한다.
- `server/src/main.rs` — `CatchPanicLayer` 를 **압축보다도 바깥**에.

## 계층 순서

압축이 "가장 바깥" 이었던 이유(DEV-332: 정적 fallback 까지 덮으려고)가
catch-panic 에도 그대로 적용된다. 더해서 **압축 계층 자체가 패닉해도** 잡으려면
그보다 바깥이어야 한다. 그래서 압축 → catch-panic 순으로 얹었다.

## 검증 — 실제 서버에 패닉을 심어 확인

단위 테스트만으로는 "계층이 실제로 걸려 있는지" 를 못 본다. 검색 진입점에
임시 패닉을 심고 서버를 띄워 확인한 뒤 제거했다.

| | 수정 전 | 수정 후 |
|---|---------|---------|
| 패닉 요청 | `HTTP 000` (연결 끊김) | **`HTTP 500`** + `{"error":"internal server error"}` |
| 서버 로그 | 패닉 스택만 | `handler panicked: …` (추적 로그와 같은 자리) |
| 이후 요청 | — | `/api/rules` 200, 정상 검색 200 (**서버 계속 살아있음**) |

임시 패닉이 소스에 남지 않은 것을 grep 으로 확인했다.

단위 테스트 3건 — `&str` / `String` / 비문자열 페이로드. 모두 500 이고
**패닉 내용이 본문에 새지 않는지**를 함께 단언한다.

`just test` 499건 + 서버 213건 통과.

## 확인한 것들 (퀘스트 본문의 3항목)

1. **정적 fallback** — 계층이 가장 바깥이라 구조상 덮인다. 다만 정적 서빙에서
   패닉을 일으킬 방법이 마땅치 않아 **실측하지는 못했다.**
2. **스트리밍 응답** — 헤더 전송 후 패닉하면 상태 코드를 바꿀 수 없어 연결
   끊김이 그대로다. catch-panic 의 한계이지 설정 문제가 아니다. 주석에 남겼고
   그때도 로그에는 남는다.
3. **Tauri 경로** — GUI 쪽엔 패닉 훅도 `catch_unwind` 도 없다. 커맨드가
   패닉하면 어떻게 되는지는 **확인하지 못했다**(웹뷰를 외부에서 조작할 수단이
   없다). 서버와 같은 조용한 실패가 될 소지가 있으므로 별도 퀘스트가 필요해
   보인다 — 이번 범위 밖으로 남긴다.

## "확인 못 했다" 고 남긴 3건을 전부 실측했다

### 1. 정적 fallback — **덮인다** ✓

`static_cache_headers` 미들웨어(모든 요청을 지나간다)에 쿼리 파라미터로
발동하는 임시 패닉을 심어 확인했다.

| 요청 | 결과 |
|------|------|
| `/_app/immutable/entry/start.*.js` (실제 자산) | **500** + `{"error":"internal server error"}` |
| `/quests` (SPA fallback) | **500** + 같은 본문 |
| 로그 | `handler panicked` 2건 |

계층이 압축보다 바깥이라 정적 자산과 fallback 둘 다 덮인다는 구조적 추론이
실제로 맞았다.

### 2. 스트리밍 응답 — **내 서술이 틀렸다** ✗

"헤더 전송 후 패닉하면 연결 끊김이 그대로" 라고 적었는데, 실측은 다르다.

첨부 zip 은 `tokio::spawn` 된 태스크에서 쓰므로 **catch-panic 계층을 아예
거치지 않는다.** 첫 항목을 쓴 뒤 패닉시킨 결과:

- HTTP **200**, 크기 9,601 → 6,180 (잘림)
- **curl 종료 코드 0** — 클라이언트는 성공으로 본다
- `handler panicked` 로그 **0건**
- `unzip`: `cannot find zipfile directory`

연결이 끊기는 게 아니라 **200 으로 깨진 파일이 조용히 전달된다.** 내가 적었던
것보다 나쁘다. 커밋 주석을 실측 내용으로 정정했다.

### 3. Tauri 커맨드 — **서버보다 나쁘다** ✗

임시 커맨드 2개(패닉용 / 파일 로그용)를 추가하고 `+layout.svelte` 에서
invoke 한 뒤 결과를 파일로 받았다.

```
--- probe 시작 ---
rejected after 5042ms: Error: TIMEOUT 5s     ← 내가 건 5초 타임아웃
패닉 후 list_rules 성공 — 앱 살아있음
--- probe 끝 ---
```

**invoke 가 거부되지 않는다. 응답 자체가 오지 않는다.** 앱과 다른 커맨드는
멀쩡하다. 서버는 이제 500 이라도 주지만 데스크톱은 promise 가 pending 으로
남아 UI 가 로딩 상태로 굳는다 — 강화 검색이라면 `wideLoading` 이 영영 true 다.

## 정리

2·3 은 [[DEV-368]] 로 등록했다. 임시 코드(서버 미들웨어·zip 태스크·Tauri
커맨드 2개·프런트 probe)는 전부 제거했고 `grep` 으로 잔여가 없음을 확인했다.
검증용으로 띄운 앱만 종료했고 사용자가 쓰던 `/Applications` 인스턴스는
건드리지 않았다.
